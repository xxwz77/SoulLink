# 多标签 + 多画面监控 共存方案（设计稿）

> 2026-11-17 · 基于当前 v1.13.2 + 0d12968 基线
> 目标：**同一窗口内**既能「多标签（同屏一个）」，又能「多画面（同屏多个）」，缩放沿用现有
> 「跟随窗口 / 拉伸 / 原大小」三档；每个画面独立保持自己的缩放模式与位置。
> 本文是**设计**，不含功能代码。所有实现都必须在 0x119 事故约束下推进。

## 一、先说现状：地基已经有 70%

读完 `Views/ConsolePage.xaml.cs` + `Controls/RdpConsole.cs` 后可以确认：

| 能力 | 现状 | 位置 |
|---|---|---|
| 每账号一个 `RdpConsole`（含 ActiveX） | 已实现，账号间互不复用 | `InitializeConsole` |
| 非当前画面保持连接（不重建、不重协商） | 已实现 | 控件移出视觉树但**不 Dispose** |
| 标签条 | 已实现，但只显示「打开过」的账号 | `RenderTabs` / `MakeChip` |

**结论：多标签这条线基本已经通了；缺的是「同屏多画面」的容器 + 保护层/缩放的按画面拆分。**

## 二、必须先解决的三个硬问题

### 2.1 跟随窗口模式现在是「切一次标签改一次分辨率」

`RdpConsole.HookInput()`：

```csharp
_host.SizeChanged += (s, e) => { RefreshViewport(); RequestResize(); };
```

`RequestResize()` 直接调 `_ocx.UpdateSessionDisplaySettings(...)`，**没有防抖**。后果：

1. 拖动主窗口边缘 → 每帧一次 `UpdateSessionDisplaySettings`。
2. 切标签时 `ViewportHost.Children.Clear()` + 重新加入 → `SizeChanged` 连续触发 → 每个账号都被改一次远端分辨率。
3. 这正是事故报告列为高风险的第 2 条：「拖动/缩放时反复 UpdateSessionDisplaySettings」。

**多画面下这个问题会被放大 4 倍**（4 个画面同时改），必须先修。

1Remote 的做法（`1REMOTE-WINDOWING-RESEARCH` 已记录）：**500ms resize-end 防抖 + 全局重入锁 + 等待鼠标释放 + 尺寸去重**。
建议直接照搬，并补一条「同屏多画面时全局串行」。

### 2.2 保护层是「一个全局单例」，多画面下语义不成立

现在 `_shieldOverlayWindow` 是 ConsolePage 上一个字段，锚定 `ViewportHost`；
`UpdateShield()` 用 `_shieldReleased` 一个布尔控制。多画面时有 4 个画面，用户只能操作一个 → **必须变成「每画面一个保护状态」**。

按 HANDOVER 记录的教训（保护层迭代的教训），不能靠叠加触发器修补。建议：

- 每个画面槽位持有自己的 `{ released, pendingAfterBusy, watchedConsole, watchedGeneration, watchedHandle }`。
- 只有一个全局「焦点画面」（`_focusSlot`），保护层只对它生效。
- 点击其他画面 = 转移焦点画面（并重新锁定该画面），不是「切换标签」。

### 2.3 缩放模式为 0（跟随窗口）在多画面下能不能用？

这是**架构问题，必须先定**。

`UpdateSessionDisplaySettings` 改的是**该 RDP 会话的远端分辨率**。同屏 4 个画面时：

- 若 4 个都是「跟随窗口」→ 4 个远端桌面各自被改成不同尺寸（比如 640×360）。原神这类游戏在 640×360 下体验很差，而且分辨率会随布局变化反复抖动。
- 若 4 个都是「拉伸」→ 远端分辨率固定（如 1280×720），本地缩放到格子大小。**这是监控场景的正确形态。**
- 若 4 个都是「原大小」→ 画面大于格子，需要滚动，监控场景基本不可用。

**建议语义（待你确认）**：

| 模式 | 单画面（标签） | 多画面（网格） |
|---|---|---|
| 跟随窗口 | 按视口改远端分辨率 | **自动降级为拉伸**（不改远端，只本地缩放），UI 标注「监控中已降级」 |
| 拉伸 | `SmartSizing` | `SmartSizing`（不变） |
| 原大小 | 1:1 + 滚动 | 1:1 + 画面内滚动 |

这样「沿用现在的缩放控制形式」成立：**用户还是选那三个，不需要学新东西**，只是多画面时「跟随窗口」不再去动远端。

## 三、容器架构：一套 Tile，两种排列

关键约束（事故报告）：**ActiveX 控件不能在容器之间反复重挂**。
所以**不要**为「标签」和「网格」各建一套容器再把控件搬来搬去。

### 3.1 只用一个 `ViewportHost`，只改布局参数

```text
ViewportHost (Grid)
 ├─ Tile 0  ← RdpConsole A
 ├─ Tile 1  ← RdpConsole B
 ├─ Tile 2  ← RdpConsole C
 └─ Tile 3  ← RdpConsole D
```

- **标签模式**：所有 Tile 都在，但只有「当前标签」那个 Tile 占满视口且 Visible，其余 Tile Visibility=Collapsed（控件仍在视觉树里、连接保持、不 Dispose）。
- **网格模式**：所有 Tile 按网格排列，全部 Visible。
- **切换模式 = 只改 Tile 的 Row/Column/Visibility，不从 Children 里增删控件。**

这一条是能不能安全落地的分水岭：**绝不 Children.Clear() 再 Add()**。
现在的 `ShowViewPageAsync` 正是这么做的（第 894、922 行），多画面下必须改掉。

### 3.2 布局只算矩形，不碰控件

做一个纯函数：

```csharp
// 输入：视口像素尺寸、画面数、布局模式
// 输出：每个槽位的 Rect（物理像素）
static IReadOnlyList<Rect> ComputeTiles(Size viewport, LayoutMode mode, int count);
```

- `Single`：1 个占满。
- `Grid`：1 / 2 / 4 分格；>4 时按 `ceil(sqrt(n))` 自动排。
- `Split`（可选，以后）：左右/上下二分布局，中间可拖分隔条。

纯函数 → **可以单元测试，不需要真实 RDP**，符合事故后「先做无 RDP 原型」的约束。

## 四、缩放：沿用现有三档，补三件事

### 4.1 防抖（必须）

```text
SizeChanged → 记录目标尺寸 → 重置 500ms 计时器
计时器到期 → 若鼠标左键仍按下则再等 → 取最终尺寸 → 去重 → 全局串行通道 → UpdateSessionDisplaySettings
```

全局串行 = 同一时刻只允许一个画面改远端分辨率，避免 4 个画面同时重协商（事故报告明确列为高风险组合）。

### 4.2 每画面独立的尺寸记忆

每个账号记住上次协商到的 `(w,h)`，切标签/切布局回来时若视口没变就**直接复用，不重新协商**。
现在 `RequestResize` 已有去重（比较 `_ocx.DesktopWidth`），但切标签导致的「先缩小到 0 再放大」会骗过它，需要一个中间层记忆。

### 4.3 网格下「跟随窗口」降级

见 2.3。实现上不必改 `RdpConsole` 内部逻辑，只需在 `RequestResize` 前判断当前容器模式：网格模式下直接 `return`，只保留 `SmartSizing`。

## 五、保护层：从「全局单例」改成「按画面」

### 5.1 现状

`_shieldOverlayWindow`（`OwnedOverlayWindow`，真实 Win32 Owner、非 Topmost）锚定 `ViewportHost`，通过 `_shieldReleased` 控制。

### 5.2 目标

```text
每个 Tile 一个保护层实例：
  · 锚定 Tile 的屏幕矩形（物理像素）
  · Created / Anchor / Show / Hide 全部由 Tile 自己的生命周期驱动
  · 只有 _focusSlot 对应的 Tile 处于「已释放」状态，其余全部锁定
```

**绝对不要**用一个覆盖整个 ViewportHost 的大保护层去挡 4 个画面 —— 那样点击谁都会被吞掉，而且锚点矩形一改就要和 4 个画面重新对表。

### 5.3 与事件的关系

- `RdpConsole.ShieldRearmRequested` / `ShieldVisibleRequested` 现在按 `ReferenceEquals(row, _viewing)` 过滤；多画面下改成按「该 Console 所属 Tile 是否为焦点 Tile」过滤。
- 保护层重建时机（注销、重连、句柄变化）按 Tile 独立进行，不再全局 `RecreateShieldAfterConsoleDisposal`。

## 六、标签与监控的共存交互

### 6.1 模式开关

顶部标签条右侧加一个「布局」按钮，三态：

```text
[单个]   ← 当前标签铺满（现在的行为）
[网格]   ← 所有已打开画面同时显示
[分屏]   ← （后续）可拖分隔条的 2 分/4 分
```

**标签永远都在**：网格模式下点标签 = 把该画面提到焦点并（可选）临时切回单个模式。
这样「多标签管理」和「多画面监控」不是两个页面，而是同一个容器的两种排列。

### 6.2 焦点画面

- 网格模式下，被点中的 Tile 高亮边框 + 获得输入（保护层释放）。
- 键盘/自由视角/热键只作用于焦点画面（`SetForegroundActive` 已按 Console 隔离，直接复用）。
- 焦点画面若被关闭 → 焦点转移给相邻 Tile，没有则回到配置页。

### 6.3 每账号布局持久化

按 HANDOVER 的需求 6（「每个账号位置、尺寸、Z 序按账号保存」）：

- 单个模式：记住标签顺序。
- 网格模式：记住每个账号在网格里的槽位。
- 若某个账号没打开，槽位空着（不放占位控件，避免多 HWND）。

## 七、落地顺序（每步都可单独验收）

| 步 | 内容 | 风险 | 验收方式 |
|---|---|---|---|
| **S0** | 修 `RequestResize` 防抖 + 全局串行 | 低 | 拖动窗口，日志里每次拖动只出现 1 条「热更新分辨率」 |
| **S1** | 布局纯函数 `ComputeTiles` + 单元测试 | 零 | 纯 WPF 无 RDP，跑测试即可 |
| **S2** | `ViewportHost` 改成固定 Tile 容器（不 Clear/Add） | 中 | **单画面**回归：切标签、保护层、缩放全部照旧 |
| **S3** | 网格布局 + 模式开关（仍只有一个画面有保护层） | 中 | 2 个画面同屏，点谁谁获得焦点 |
| **S4** | 保护层按 Tile 拆分 | 中高 | 4 个画面同屏，逐个点击验证首击不透传 |
| **S5** | 每账号布局持久化 | 低 | 重启后布局还原 |

**S2 是分水岭**：它先只改「单画面下的容器结构」，视觉和功能应当**完全不变**。
如果 S2 都做不到零回归，说明这套结构在当前代码里不适用，应当立即停下重新设计，而不是继续往上叠 S3/S4。

## 八、如果同进程多 ActiveX 最终被判定不安全

事故报告把「同进程多 ActiveX」列为高风险组合。本方案 S3/S4 正是这个组合。
所以在 S2 通过之后、S3 开始之前，必须先做一个**判定实验**：

- 用 2 个真实 RDP 画面同屏，**不做任何重挂、不拖动、不改分辨率**，静置 + 逐一点击焦点，观察 10 分钟。
- 通过 → 继续 S3/S4。
- 不通过 → 转 MobaXterm 路线（每账号一个子进程，主进程只给宿主 HWND）。此时 S1/S2 的布局与 Tile 容器**可以完全复用**，只是 Tile 里的内容从 `RdpConsole`（内置 ActiveX）换成 `HwndHost`（外部子进程窗口）。

这也是为什么第三节坚持「只改布局参数、不搬控件」—— 它同时为这两条路线留了后路。
