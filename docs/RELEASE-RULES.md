# 云端发布规则

> 本项目所有对外发布**只允许**通过 `scripts/publish-release.ps1` 完成。
> 手工上传、直接改 CDN 文件、绕过脚本的做法一律禁止。

---

## 1. 发布方式

> ★★ **2026-11-22 起：一律使用全量包** ★★
>
> ```powershell
> scripts\publish-release.ps1 -Full -Push
> ```
>
> 用户明确要求：「以后全用全量包，因为可能有人更新断档。全量包体积也不大。」

| 场景 | 命令 |
|---|---|
| **常规发布（唯一推荐）** | `publish-release.ps1 -Full -Push` |
| 仅检查不发布 | `publish-release.ps1`（不带 -Push，只打印清单） |

### 为什么改成默认全量

**① 断档更新会缺文件（这是主因）**

增量包只含「与上一版相比有变化的文件」。若用户从 v3.1.0 直接跳到 v3.2.2，
中间几版新增的文件（例如新加的 `README.md`、新的 tools 子脚本）在增量包里
可能已经「某次推送过」，于是本次增量不会再带上 —— **用户端就是缺文件**，
而且没有任何报错，表现为功能莫名其妙不可用。

**② 全量其实很小**

历史担忧来自「全量约 123 MB」。但那是因为早年把 `agent\SoulLink.Agent.exe`（64 MB）
和自包含 Broker 安装器（33 MB）算进去了。现在：

| 项 | 变化 |
|---|---|
| `agent\` | **已从打包排除**（是手动代理导出残留，不是运行必需品） |
| Broker 安装器 | 框架依赖单文件，**1.16 MB**（原 33 MB） |
| 实际全量包 | **约 2.85 MB** |

增量包 2.85 MB，全量包 2.85 MB —— 体积几乎相同，**没有理由再冒断档风险**。

### 旧的增量逻辑仍然保留

脚本仍支持不带 `-Full` 的增量模式（按 `filelist.json` 的哈希比对），
仅用于排查「为什么某个文件没更新」时对照，**不作为发布手段**。

### 什么时候必须用 `-Full`

1. **首次建立发布通道** —— 用户手里没有 `filelist.json` 的基线。
2. **新增文件** —— 增量包能携带新文件（`filelist.json` 里没有的会自动纳入），
   但如果新增的是一个全新目录结构，建议走全量，避免用户端目录缺失。
3. **删除文件** —— ★ **增量包无法删除文件**。旧文件会残留在用户机器上。
   若要移除某个文件，必须发全量包，且需在更新器里额外实现删除清单
   （目前**未实现**，见第 5 节）。
4. **怀疑用户端文件损坏** —— 全量包可强制覆盖所有文件。

### 增量比对原理

`artifacts/package/filelist.json` 记录上次推送时每个文件的 SHA256。
发布时逐个比对当前文件的哈希：

- 哈希不同 → 纳入增量包
- 哈希相同 → 跳过（即使 build 重新生成了文件、时间戳变了）
- 新文件（清单里没有）→ 纳入
- 清单里有、当前没有 → **警告并列出**，但不会自动删除

清单只在上传**成功之后**才更新。上传失败时清单不前进，
避免下次把「没推上去的文件」当成「已推送」而漏发。

## 2. 打包内容规则

### 包含

```
SoulLink.exe              主程序
SoulLink.Updater.exe      更新器（可自我更新）
agent\SoulLink.Agent.exe  代理
tools\*.exe, *.ps1        服务安装器与脚本
next\*                    辅助工具
7za.exe / sl-rescue.exe   随包工具
```

### 绝对排除（硬性要求）

| 排除项 | 原因 |
|---|---|
| `data\` 整个目录 | **用户配置、账号、备份、日志** —— 覆盖会毁掉用户数据 |
| `stable\` 整个目录 | 挂机测试版，不参与更新 |
| `*.log / *.bak / *.old / *.tmp / *.pdb` | 运行时产物与调试符号 |

> ★ 这条是**不可协商**的。曾经因为把 `data\config.json` 打进包，
> 导致用户升级后所有账号配置被清空的情况必须永不发生。

## 3. 发布顺序（不可颠倒）

```
1. 编辑 docs/RELEASE-NOTES.md   （更新说明，会显示在客户端）
2. 改 SoulLink.csproj 的 <Version>（版本号唯一来源）
3. build.bat                     （生成 dist\ 与 artifacts\dist-<ver>\）
4. publish-release.ps1 -Push     （打包上传刷新 CDN）
```

脚本内部顺序：

```
打包 → 上传 update.zip → HEAD 校验（5 次重试）→ 通过后才写 latest.json → 刷新 CDN
```

**为什么必须先校验 exe 再写清单**：一旦 `latest.json` 指向不可下载的包，
所有用户点「检查更新」都会失败，且**无法自愈**——只能再推一版覆盖。
这条规则来自 ATM 项目的教训，已在本项目固化。

---

## 4. 客户端行为约定

- 启动后 **6 秒**静默检查一次；有新版本时版本号变琥珀色 + 显示红点。
- 点击版本号 → 弹更新窗口（版本对比 + 更新说明 + 确认/取消）。
- 更新失败只显示中性提示（「网络连接失败」等），**不暴露任何发布地址**。
- `cdn.example.invalid` 只允许出现在 `Services/CloudUpdater.cs` 的两个常量里。
  界面上出现该域名属于**缺陷**。

## 5. 已知限制（当前未实现）

| 限制 | 影响 | 规避方式 |
|---|---|---|
| **增量包无法删除文件** | 废弃文件残留 | 发全量包；或后续实现删除清单 |
| **无差分/二进制补丁** | 主程序改动 1 行也要下 3.4 MB | 可接受，暂不优化 |
| **无回滚机制** | 推错版本只能再推一版 | `artifacts/dist-<旧版本>\` 保留着历史产物，可手工重推 |
| **更新器未签名** | 可能被杀软拦截 | 用户需手动放行；替换失败会自动回滚 |

## 6. 验证清单（每次发布后自查）

```
[ ] latest.json 里的 version 与 csproj 的 <Version> 一致
[ ] CDN 自检通过（脚本会打印 "CDN 已生效"）
[ ] 更新包大小合理（增量通常 < 5 MB，全量约 123 MB）
[ ] zip 内不含 data\ 任何文件
[ ] SoulLink.exe 位于包根（不带 stage\ 前缀）
```

## 7. 凭据

COS 凭据来自本机 **COSBrowser 登录态**（%APPDATA%\cosbrowser\），
不写入仓库、不写入脚本、不进入客户端。

临时凭据过期时脚本会尝试 OAuth 刷新；刷新失败需手动重新登录 COSBrowser。

## 8. 体积约束（2026-11-21 新增）

### 8.1 全量包目标体积

```
2026-11-21 之前：123 MB   ← 三个自包含产物 + agent 目录
2026-11-21 之后：2.69 MB  ← 全部改为框架依赖
```

**新增产物时必须守住这条线**：单个文件超过 5 MB 就要问一句「它为什么这么大」。

### 8.2 已知的体积陷阱

以下三个产物原来是**自包含**发布，把整个 .NET 运行时打了进去：

| 产物 | 原大小 | 现大小 | 为什么会踩 |
|---|---|---|---|
| `sl-rescue.exe` | 33.48 MB | 72 KB | 只做 5 个 Win32 调用 |
| `SoulLink.BrokerSetup.exe` | 33.60 MB | 1.16 MB | 只做复制文件/建服务/改 ACL |
| `dist\agent\` | 64 MB | 已排除 | 旧版本副本，不该分发 |

**判断原则**：如果用户能用它，说明主程序已经在跑，也就必然有 .NET 运行时。
此时自包含是纯浪费。

### 8.3 构建方式

`SoulLink.BrokerSetup.exe` 由 `SoulLink.csproj` 的 `PublishBrokerSetup` 目标
自动发布到 `artifacts\broker-build`，**不要再手工维护 dist 下的那个文件**。

`build.bat` 会同步 `tools\` 子目录到 `dist`。

## 9. 客户端更新行为

### 9.1 检查策略

| 时机 | 频率 | 说明 |
|---|---|---|
| 启动后 60 秒 | 1 秒 | 连 RDP、初始投送都在这段时间 |
| 投送前后 | 事件触发 | — |
| 稳定挂机 | 30 秒 | 只用来发现掉线 |

### 9.2 更新包命名

**必须带版本号**：`update-<version>.zip`

原因：固定名 `update.zip` 会被 CDN 缓存，导致「清单是新的、包是旧的」。
带版本号后内容与文件名一一对应，永不覆盖，CDN 缓存多久都对。

> 文件名用户永远看不到（下载到临时目录、解压后即删），
> 不影响安装目录里的 `SoulLink.exe` 固定名与桌面快捷方式。

### 9.3 发布域名不可见

`cdn.example.invalid` 只允许出现在 `Services/CloudUpdater.cs` 的两个常量里。
界面上出现该域名属于**缺陷**。

更新失败时只显示中性提示（「网络连接失败，请检查网络后重试」等），
不暴露任何内部地址。

## 10. 定时器与页面生命周期规范

### 10.1 新增周期任务

```csharp
// ✅ 正确：走统一节拍
_sub = Services.TickHub.Register("模块名", 秒数, () => { ... });

// ❌ 禁止：新建独立 DispatcherTimer
new DispatcherTimer { Interval = ... };
```

6 个各自独立的 1 秒级定时器曾让线程池长期自旋，
空闲 CPU 因此高达 27%（未连任何 RDP）。

### 10.2 页面可见性

`MainWindow.SetActivePage` **只切 Visibility，不会触发 Loaded/Unloaded**。

任何「只在页面可见时需要」的定时器/订阅/轮询，必须实现：

```csharp
public void OnPageActivated()   { /* 恢复 */ }
public void OnPageDeactivated() { /* 暂停 */ }
```

并在 `SetActivePage` 里调用。

> 已知案例：控制台页的 150ms 保护层看门狗因此空转了很长时间，
> 是「切菜单越来越卡」的主因之一。

## 11. 诊断代码规范

### 11.1 取句柄数

```csharp
// ❌ 每次约 3~5ms 系统查询，挂在 1Hz 循环里会自己吃掉 20% CPU
Process.GetCurrentProcess().HandleCount;

// ✅ 约 1 微秒，配合 1 秒缓存
[DllImport("kernel32.dll")] static extern bool GetProcessHandleCount(IntPtr, out uint);
```

### 11.2 采信数据前先确认工具开销

曾因为探针自身消耗导致误判「`RefreshOnce` 泄漏句柄」，
排查了好几轮才发现是工具本身的问题。

### 11.3 句柄增长的判别

| 特征 | 正常爬坡 | 真泄漏 |
|---|---|---|
| 趋势 | 上升后趋于平缓 | 持续线性上升 |
| 增长率 | 递减 | 恒定 |

.NET 应用启动时句柄单调上升是正常的（线程池、JIT、GC 分代），
**必须观察足够长时间（>15 分钟）才能断定是否泄漏**。
