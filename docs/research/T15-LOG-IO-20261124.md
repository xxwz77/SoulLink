## 2. 问题 B：AppendErrorLog 无上限、无轮转

### 2.1 三条纪律

| # | 纪律 | 实现 |
|---|---|---|
| ① | **有上限** | 超过 5 MB 轮转为 `error.log.old`（复用 `AsyncLog.RotateIfOversized`，与日志文件同一策略） |
| ② | **有降频** | 同一 `(source + 异常类型 + Message)` **60 秒内只写第一条**；被抑制的条数在下一条落盘时以「另有 N 条相同异常被抑制」一并写出 —— **信息不丢，只是不逐条刷屏** |
| ③ | **绝不抛** | 写日志失败最坏少一条记录，绝不让异常处理路径本身炸掉（`catch { }` 保留） |

### 2.2 关键设计：指纹**不含 StackTrace**

```
  internal static string ErrorFingerprint(string source, Exception? ex)
      => source + "|" + ex.GetType().FullName + "|" + ex.Message;
```

**为什么**：同一个调用点的栈是稳定的，纳入 StackTrace 会让「同一个异常」永远判不重，去重直接失效。
这条已由断言固定住（`指纹不含 StackTrace`）。

### 2.3 为什么不能只靠轮转

轮转只解决「文件不无限涨」，但**每秒一条完全相同的异常仍然是纯噪声** ——
日志被刷满后，真正有用的**第一条**反而被埋掉。所以上限和降频是两件事，都要做。

### 2.4 可单测性

本类继承 `Application`，跑测试要拖 WPF。所以把判定逻辑抽成两个 `internal` 纯函数：

| 函数 | 职责 |
|---|---|
| `ErrorFingerprint(source, ex)` | 生成指纹 |
| `ShouldWriteError(fp, lastFp, lastAtUtc, nowUtc, window)` | 纯函数：这次要不要写 |

调用方（`AppendErrorLog`）只负责读/更新状态，判定本身可脱离 WPF 验证。

## 4. 顺带发现（未改，仅供参考）

抽 `RotateIfOversized` 时注意到：`AsyncLog` 用**一个** `Rotated` 集合，而 `AppendErrorLog` 用**另一个** `ErrorLogRotateSeen`。
这是有意的 —— 两个文件独立判限，互不影响。但如果将来要加第三个日志文件，
建议直接把 `seen` 集合收进一个 `ConcurrentDictionary<string,byte>`，避免每个调用方各自维护。
