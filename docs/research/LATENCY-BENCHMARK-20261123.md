## 0. 先回答用户那一句：「为什么还是卡」

用户的体感是准的，而之前「我们链路只占 12~20ms」的结论**没抓住痛点**，原因是那次测量只覆盖了「抓屏 → 编码 → HTTP 写出」这一小段，且用的是 ffplay 当播放端。**用户实际用的是浏览器里的网页**，那条路上有两段完全没被测量：

1. **采集和推流是「串行双节拍」**：帧先要在环形缓冲里等下一次抓帧（实测 82ms），推流循环再等一次 `Task.Delay(66)`（实测 74ms）。两段相加 ≈ **157ms**，这还没算解码和上屏。**【实测】**
2. **编码器选的是「软件同步 MFT」，不是硬件**：代码里 `swColl` 优先于 `hwColl`。软编是同步阻塞、且流水线会累积（交接文档记录过「30 帧入只出 13 帧」）。**【代码事实】**

所以「一手 157ms 起步 + 软编流水线 + 浏览器解码上屏」才是用户看到的那一坨。**66ms 的硬编码延迟上限，恰好等于「每秒 15 帧」的帧间隔；用户看到的「像 PPT」本质是这个 15fps 上限，不是网络慢。**

## 1. 延迟分段表（逐段实测或明确标注未实测）

### 1.1 当前真实通路（WGC → 软编 → chunked HTTP → 浏览器）

| # | 段 | 我们的实测值 | 证据等级 | 说明 |
|---|---|---|---|---|
| ① | 画面变化 → WGC 抓到 | **未实测** | — | 需要外部时钟/高帧相机。WGC 只在上层有变化时更新缓存纹理，静止画面不产新帧 |
| ② | 抓帧等待（帧进 Ring） | **82ms**（= 12.14 fps） | **【实测】** | 配置是 15fps，但实测只到 12.14fps：`Loop()` 里 `Thread.Sleep(interval - 耗时)` 是「抓完再睡」，实际周期 = 抓帧耗时 + 66ms |
| ③ | JPEG 解码 → BGRA → NV12 | **未单独实测** | — | 纯 C# 逐像素 `BgraToNv12()`，1080p 量级按交接文档估 10~20ms |
| ④ | H.264 编码（软编同步 MFT） | **未单独实测** | — | 交接文档实测软编 4~8ms/帧，但**流水线累积**才是真问题（30 入只出 13） |
| ⑤ | 推流等待 `Task.Delay(66)` | **74ms** | **【实测】** | 实测推流 13.56 fps；与 `frames < 450 && elapsed < 30000` 共同构成硬上限 |
| ⑥ | HTTP 传输（本机） | **0.8ms** | **【实测】** | `/live` 请求往返 平均 0.8 / p95 4.6 ms。**传输不是瓶颈** |
| ⑦ | 浏览器 WebCodecs 解码 | **未实测** | — | 需页面内埋点，见 §5.1 |
| ⑧ | 浏览器合成上屏 | **未实测** | — | 受 vsync/合成器影响，通常 1~2 帧间隔 |

**可叠加的确定性下限（连续最坏情况）**：
```
② 82ms + ⑤ 74ms + ⑥ 0.8ms ≈ 157ms
```
再叠加 ③+④（编码转换，保守 15~30ms）与 ⑦+⑧（解码上屏，保守 2 帧 ≈ 66ms 若按 30Hz 显示器），
**合理估计 240~260ms 起步**；若软编流水线累积（历史上 30 入 13 出），会再被拉长。

> ⚠ 上一份交接的「636~742ms」是 **ffplay** 播放的端到端数字，其中约 500ms 是 ffplay 自身缓冲。
> 那个数字**不能**代表浏览器体验，也**不能**证明「我们不慢」。两个播放端的缓冲行为完全不同。

### 1.2 关键量化：码率低得反常

| 指标 | 实测值 | 判读 |
|---|---|---|
| /stream 平均码率 | **0.033 ~ 0.06 Mbps** | 极低 |
| NAL 数 | 642（25 秒） | 约 26 NAL/s |
| IDR 数 | 20（25 秒） | 约 0.8 IDR/s，GOP 未显式配置 |
| 单块平均大小 | 324 B | **大部分块是空 NAL / 极小 NAL** |

**这说明两件事（都是问题）**：
1. 码率 0.03Mbps 对 1734×927 的画面来说低到不可能有可用画质——**画面内容大概率几乎没有变化**（我测试时是静态桌面）。所以这些数字**只能用于验证「节拍」，不能用来评估「画质」或「游戏场景带宽」**。
2. 642 NAL / 320 块 = 每块约 2 个 NAL，而每帧至少 1 个 NAL。**块数（320）比 NAL 数（642）的一半还多**，说明推流循环在「没有新帧」时也照样每 66ms 写一次 —— 存在**空转写出**，纯浪费。

### 1.3 采集帧率为什么到不了配置的 15fps

**【代码事实】** `SessionRecorder.Loop()`：
```csharp
int interval = Math.Max(1, 1000 / fps);       // fps=15 → 66ms
var sw = Stopwatch.StartNew();
var jpeg = Capture.CaptureJpeg(...);           // 抓帧耗时 T
...
int wait = interval - (int)sw.ElapsedMilliseconds;
if (wait > 0) Thread.Sleep(wait);              // 只睡 (66 - T)
```
真实周期 = `T + max(0, 66 - T)`。若 `T < 66`，周期恰好 66ms（15fps）。
但**实测只有 12.14fps（周期 82ms）**，意味着 `T` 在部分帧里**超过了 66ms**（抓帧+JPEG 编码超过预算），此时 `wait ≤ 0` 不睡，周期 = `T` > 66ms。
**结论：抓屏+JPEG 编码这一跳已经吃满了 15fps 的预算，且不时超标。这是参数与实现的双重问题，不是网络问题。**

### 3.2 那个具体问题的正面回答：「裸 chunked HTTP 没拥塞控制，是架构还是参数？」

**是架构问题，但它的危害被高估了——在你当前的使用场景里它几乎不咬人。** 理由要分开说：

**为什么是架构的**：TCP 本身有拥塞控制（慢启动、Reno/CUBIC），所以「完全没有拥塞控制」的说法不准确。真正缺的是**应用层对延迟的主动管理**：
- **没有丢帧语义**：TCP 保证有序，丢一个包后续全部阻塞（head-of-line blocking）。视频流希望的是「丢一个包就丢掉这一帧的画面部分」，而不是等重传。
- **没有帧边界与优先级**：所有 NAL 共享一条有序字节流，一个关键帧被卡住，后面的 delta 帧全部堵在后面。
- **没有带宽自适应**：不知道链路有多快，码率是写死的 8000kbps。

**为什么现在不咬人**：
1. **传输实测 0.8ms**（本机）。局域网/本机场景下 TCP 的重传与 HOL 阻塞几乎不触发。
2. 云游戏厂商用 UDP + FEC 是因为他们要跑**公网、高码率（15~50Mbps）、高帧率（60fps）**。你现在是 **0.03Mbps、15fps、局域网**，两者不在同一个问题域。
3. 交接文档记录的「丢一包画面就花」在当前码率下**几乎不可能被观测到**——因为总共才 0.03Mbps。

**结论**：**先把节拍、编码器、去重这三件「参数+实现」的事做完（低风险、几天内、收益立刻可见）；等真的跑公网、跑 60fps、码率上到 8Mbps 以上，再谈 WebRTC/QUIC。** 现在换传输协议属于「用大型架构改造解决一个还没发生的问题」。

## 4. 可落地建议（按性价比排序）

> 人日是按熟悉本代码的人粗估，含验证，不是承诺。收益依据都写明。

### 建议 1：去掉两个硬编码上限 + 让推流跟随真实新帧（收益最大、成本最低）

**做什么**：
- 删掉 `frames < 450 && elapsedMilliseconds < 30000`（演示用上限）
- 把 `Task.Delay(66)` 改成「有新帧就推，没新帧就等信号」
- `Loop()` 的睡法改成「按固定周期绝对时间睡」：`nextAt += interval; Thread.Sleep(max(0, nextAt - now))`

**预计收益**：推送上限从 13.56fps → 跟随采集（12~15fps 或更高，取决于抓帧）；**去掉空转写出**（实测每 25 秒多写 320 块）。
**依据**：§1.2 实测「块数 320 但实际新帧更少」；§1.3 的睡法分析。
**成本**：**0.5 人日**。
**风险**：**低**。若不加「无新帧不推」的判断，静止画面会持续占用带宽（但现在是 0.03Mbps，影响可忽略）——所以这条要与建议 2 配套。

### 建议 2：加 frameSeq + 变化检测，「没变就不抓不编不推」

**做什么**：`SessionRecorder` 每帧带 `frameSeq` 与内容哈希（或全分辨率采样比对）；内容相同则跳过编码与推送；`/stream` 只在有新 `frameSeq` 时写字节。
**预计收益**：静止画面 CPU 从「持续满转」降到接近 0。**这是用户挂机场景的核心收益**——挂机时画面 99% 时间不动，现在却 100% 在抓+编+推。
**依据**：微软官方「Only changed parts... no updates are sent」；`STREAM-PERF-AUDIT` 已定性指出「整条链路没有任何帧间复用」。
**成本**：**1~1.5 人日**（要处理哈希开销，纯哈希 1734×927×4 ≈ 6.4MB/帧，可能比抓屏还贵 → 建议**降采样哈希 + 全分辨率抽样**）。
**风险**：**中**。降采样会漏掉小光标移动 → 必须保留「周期性全帧校验」兜底。

### 建议 3：改用硬件编码器（软编 → 异步 NVENC）

**做什么**：改 `MfFrameEncoder.TryInitialize()`，把 `hwColl` 提到 `swColl` 之前，并实现 `MF_TRANSFORM_ASYNC_UNLOCK` + `GetEvent` 事件驱动（交接文档已有跑通的实现记录，在 `tools/stream-probe/`）。
**预计收益**：**消除软编流水线累积**。交接文档实测：软编 30 帧入只出 13 帧（端到端 1384ms）→ 硬编异步 1:1（636~742ms）。**这是被实测验证过的、收益最大的一次改动**。
**依据**：`STREAM-LATENCY-TEST-20261122.md` §2 实测表。
**成本**：**1~2 人日**（事件驱动要处理超时与重入）。
**风险**：**中**。硬编在某些驱动/虚拟机上不可用 → 必须保留软编回退（现在的代码已有回退结构，改成 `hw` 优先、`sw` 兜底即可）。

### 建议 4：手写 ICodecAPI 设低延迟参数（关 B 帧 / 无限 GOP / 实时模式）

**做什么**：手写 `ICodecAPI`（约 50 行 COM 接口），在 `TryInitialize()` 后设：
- `CODECAPI_AVLowLatencyMode = true` —— 砍编码器内部缓冲
- `CODECAPI_AVEncMPVGOPSize` 调大（或 0 = 无限）—— 避免周期性 IDR 尖峰
- `CODECAPI_AVEncCommonRealTime = true` —— 实时模式，允许丢质量保延迟
**预计收益**：编码端约省 **1~2 帧缓冲**（按 15fps 即 66~132ms；按 30fps 即 33~66ms）。**依据**：交接文档 §4 列为第 1 优先优化项，但**我自己未实测**——这条的数字来自编码器通用行为，不是本机测量，标 **【未实测】**。
**成本**：**1 人日**（COM 接口易错，本项目手写 COM 翻车过 3 次，见交接文档 §3.2 教训）。
**风险**：**中高**。`SetValue` 失败通常是静默返回错误码，必须逐项校验并在失败时降级。

### 建议 5：把「延迟」变成可回归的数字（测量先行）

**做什么**：在页面里埋点，记录 `capturedAt`（服务端帧时间戳，随帧下发）与 `requestVideoFrameCallback`/`decoder output` 时刻，算 P50/P95 帧龄并在页面上小字显示。
**预计收益**：不直接降延迟，但**让后面每一条优化都可证伪**。没有这个，我们只能靠「感觉好点了」。
**依据**：本次调研的最大障碍就是「用户说卡，但我们没有一个能对齐用户体感的数字」。
**成本**：**0.5 人日**。
**风险**：**低**。

## 5. 三个指定技术点的专项评估

### 5.1 WebCodecs 的 `optimizeForLatency`

**事实**：`VideoDecoderConfig.optimizeForLatency` 是 W3C WebCodecs 规范的配置项，含义是「提示解码器优先低延迟而非吞吐」。**【引用】**规范定义。

**它能省多少**：
- **确定性部分**：它影响的是**解码器内部是否攒帧**。现代浏览器在 `optimizeForLatency: true` 下通常**不额外攒帧**（输出即用），关闭时可能攒 2~4 帧以提升吞吐。
- **量级估算**：按 15fps 计，省 2~4 帧 = **133~266ms**；按 30fps 计 = **66~133ms**。
- ⚠ 但这是**通用行为推断，我没有在本机实测**。标 **【未实测】**。

**关键提醒（比这个参数重要得多）**：
> **当前 `optimizeForLatency` 不是我们的瓶颈。** 因为我们的推流上限只有 13.56fps，而帧在服务端就已经排队了 157ms。**在服务端节拍问题修好之前，调这个参数最多让「已经晚到的帧」早 30~60ms 上屏，用户感知不到。**

**建议**：这个参数**已经在代码里设了**（`docs/web-index.html` 的 `decoder.configure({... optimizeForLatency: true})`）——**不用再投入**。真正该做的是建议 1/2。

### 5.2 MF 的 `CODECAPI_AVLowLatencyMode`（需手写约 50 行 COM）

**现状【代码事实】**：`Services/MfFrameEncoder.cs` 里 **grep `ICodecAPI` / `AVLowLatency` / `GOP` / `BFrame` 全部零命中**。也就是说：
- 没有设低延迟模式
- 没有设 GOP 大小（实测 IDR 约 0.8/s，是 MFT 默认行为）
- 没有禁用 B 帧

**为什么值得做**：这是**唯一能让编码器「不再自己攒帧」**的手段。软编同步 MFT 的「30 入只出 13」正是这个问题的症状。

**收益（分层陈述，避免夸大）**：
| 收益来源 | 量级 | 证据 |
|---|---|---|
| 消除编码器内部帧缓冲 | 1~2 帧（66~132ms @15fps） | **【未实测】** 通用行为 |
| 减少周期性 IDR 尖峰 | 偶发卡顿消失（每次 IDR 都是大帧） | **【代码事实】** 实测 20 个 IDR/25 秒 |
| 实时模式允许丢质量 | 高负载时不再雪崩 | **【未实测】** |

**成本与风险**：
- 手写 COM 在本项目**翻车过 3 次**（槽位错位、`[local]` 标记、IID 写错）。
- `SetValue` 失败是静默的 → 必须**逐项校验返回值**，不能假设成功。
- **风险缓解**：先只做 `AVLowLatencyMode` **一项**，验证有效再加其余两项。不要一次上三个。

**重要顺序建议**：**先做建议 3（换硬编），再考虑建议 4。** 理由是：硬编异步本身就把「攒帧」问题解决了（实测 1:1 产出），而 `AVLowLatencyMode` 手写 COM 风险更高、收益更不确定。**先做低风险高收益的。**

### 5.3 「不攒帧、直接推」的可行性

**我们的实现现在有没有在攒帧？—— 有，而且是三层都在攒：**

| 层 | 有没有攒 | 证据 |
|---|---|---|
| ① 采集层 Ring | **攒，但只保最新** | `GetLatestJpeg()` 取尾帧，语义上是「丢旧保新」，这层**做得对** |
| ② 编码器 MFT 内部 | **攒**（软编同步） | 交接文档实测「30 帧入只出 13 帧」**【代码事实+外部实测】** |
| ③ 推流节拍 | **攒**（`Task.Delay(66)` 串行等待） | 【实测】推流 13.56fps，帧在两次推流之间干等 |

**所以「不攒帧直接推」的可行性判断**：

- **③ 最容易**：把「定时推」改成「有帧就推」。技术上是**去掉 `Task.Delay`，改成事件/信号量**。**可行性高、风险低**，就是建议 1。
- **② 中等**：换硬编后天然 1:1（建议 3）。若坚持软编，只能靠 `AVLowLatencyMode`（建议 4，风险高）。
- **① 已经是好的**：不需要动。

> **一句话**：**「不攒帧直接推」不是要做一件新事，而是把现在三处「故意攒着」的地方逐个解开。③ 是 5 行代码，② 是换编码器，① 不用动。**

## 6. 给用户的「到底怎么才能跟手」结论

按用户能理解的话说：

1. **现在的「卡」主要是我们把帧率钉死在 15fps，而且每一帧还额外多等了一轮。**
   实测：采集 12.14fps、推流 13.56fps，两段串起来每帧先等 157ms 才出发。改掉两个硬编码的 66ms，这是**半天的事**。
2. **编码器用的是软件版本，而交接文档里实测过：换成硬件能把延迟砍一半（1384ms → 636~742ms）。**
   这是已经验证过收益的改动，**1~2 天**。
3. **挂机时画面几乎不动，但我们仍然每秒抓 15 次、编码 15 次、推送 15 次。**
   微软官方文档明确说「没变化就不该发」。加上「没变就不干活」，挂机时 CPU 能降到接近零，**1~1.5 天**。
4. **换传输协议（WebRTC/QUIC）现在不该做。**
   实测局域网传输只占 0.8ms。那是给公网 60fps 高码率准备的方案，现在做等于**给一个还没发生的病吃药**。
5. **对标要用「端到端」比，不要拿自己的端到端去比人家宣传的「传输环节」。**
   华为 HDP 敢说「端到端 <100ms」，那是这个行业里比较诚实且可对标的目标。我们现在的合理目标不是 3ms，是**先做到 100ms 以内**。
