## 0. 一句话结论

**在本地控制台会话上，桌面复制可用且极快（0.13ms/帧），现有 BitBlt 却是 17~20ms/帧 —— 单是抓屏就吃掉 60fps 预算的全部。但本次运行的是「本地控制台」而不是 RDP 会话（`SM_REMOTESESSION=0`），所以这个结论对目标场景（代理跑在 RDP 会话里）**不成立**，必须按 §4 的命令在 RDP 会话内复测一次才算数。**

已确证的部分（与 RDP 无关，可直接用）：

| 事项 | 结论 |
|---|---|
| 硬件 H.264 编码器 | **存在**：`NVIDIA H.264 Encoder MFT`（NVENC） |
| 软件 H.264 编码器 | 存在：`H264 Encoder MFT` |
| BitBlt 抓屏成本（2560x1440） | **17.2 ~ 19.8 ms/帧** ← 这就是 60fps 的真正拦路虎 |
| GDI+ JPEG q75 编码（1080p） | 4.5 ~ 4.9 ms/帧，单帧 197KB，**折算 5.78 MB/s @30fps** |
| 脏矩形平均占比 | **50.7%**（脏矩形方案能省的编码量上限） |

★ 顺带把交接文档里一个长期混淆的数字拆开了：`WebServer.cs:136-137` 注释写的
「BitBlt + JPEG 一次 13~16ms」是**合并值**。实测拆开后是
**BitBlt 17~20ms + JPEG 4.5~4.9ms** —— 也就是说抓屏才是大头，不是编码。
这与 `STREAM-PERF-AUDIT` §1.2 的猜测（编码是大头）**方向相反**。

## 1. ⚠ 本次会话性质：**不是 RDP**

```
[LOCAL   ] SM_REMOTESESSION     运行在本地控制台会话内，**不是 RDP**

[INFO    ] 进程 SessionId        session 1（活动控制台 = 1）
```

同一台机器上有 RDP 会话在跑，但**本探测进程在 session 1（物理控制台）**：


本次实测的恰是它说**不能代表**的那一侧。

所以本报告分成两部分：

- **§5 表 A：与会话无关的事实**（硬件存在性、编码成本、编码器枚举）→ 可直接采信

### 2.6 Media Foundation H.264 编码器枚举

| 类别 | 数量 | 名称 | 硬件 URL | D3D11-aware | 错误码 |
|---|---|---|---|---|---|
| 硬件 | **1** | `NVIDIA H.264 Encoder MFT` | `NVIDIA H.264 Encoder MFT` | 否 | `0x00000000` |
| 软件 | 1 | `H264 Encoder MFT` | — | 否 | `0x00000000` |

> ★ 这里踩过一个会直接导致**错误结论**的坑：
> 第一版用 `MFT_ENUM_FLAG_SYNCMFT | MFT_ENUM_FLAG_ASYNCMFT` 枚举，
> 得到「**0 个硬件编码器**」，而本机明明有 RTX 4060。
> **硬件 MFT 必须用 `MFT_ENUM_FLAG_HARDWARE` 单独枚举**，否则永远看不到 NVENC。
> 如果没发现这个，报告会写出「本机没有硬件编码器，只能软编」的假结论。

### 2.7 编码实测

| 路径 | 均值 | p95 | 单帧体积 | 折算 @30fps | 可信度 |
|---|---|---|---|---|---|
| **GDI+ JPEG q75（1920x1080）** | **4.931 ms** | 7.034 ms | 197 KB | **5.78 MB/s** | ✅ 可信 |
| MF H.264（40 帧 MP4） | 0.284 ms | — | 23 KB | 0.69 MB/s | ⚠ 仅 CPU 侧下界 |

**H.264 那一行的口径必须看清楚**：

```
H.264 诊断: 40帧MP4=920KB  WriteSample累计=0.7ms  Finalize=9.2ms
```

`WriteSample` 累计只有 0.7ms，`Finalize` 9.2ms。NVIDIA 的 MFT 是**异步**的：
`WriteSample` 只把样本排进队列就返回，真正编码在 GPU 上完成。
所以 0.284ms 是**「CPU 侧提交成本」的下界**，不是完整的编码成本。

> ★ 这个数字第一版跑出来是 **0.020ms、单帧 3KB**，看起来「比 JPEG 快 236 倍」。
> 那是**假数据**：NV12 填充过于平坦（纯渐变），编码器把整帧压成极少字节。
> 程序现在内置体积自校验：40 帧 1080p H.264 合理下限 **300KB**，低于就打
> `UNRELIABLE` 并**拒绝输出排名数字**。修正填充内容后升到 920KB，才允许报数。

### 2.8 汇总

```
OK=12  FAIL=0  其它=19  共 31 项
```

**0 个 FAIL** —— 在本地控制台会话上，DXGI 桌面复制与硬件 H.264 编码**都可用**。

## 3. 60fps 路径结论

### 3.1 三条路径的单帧预算（16.7ms = 60fps）

| 路径 | 抓屏 | 编码 | **合计** | 60fps 判定 |
|---|---|---|---|---|
| **现有：BitBlt + GDI+ JPEG** | 17.2~19.8 ms | 4.5~4.9 ms | **≈ 22~25 ms** | ❌ **只能约 41~45 fps** |
| **桌面复制 + GDI+ JPEG** | 0.13 ms | 4.5~4.9 ms | **≈ 5.0 ms** | ✅ **够 60fps（有余量）** |
| **桌面复制 + MF H.264** | 0.13 ms | 0.28 ms（CPU 下界） | **≈ 0.4 ms**（下界） | ✅ CPU 侧够 60fps |

### 3.2 结论与限定条件

**结论 1：60fps 的瓶颈是抓屏，不是编码。**
BitBlt 单帧 17~20ms 已经吃掉全部 16.7ms 预算。所以：
- 不换抓屏方式，任何编码优化都到不了 60fps；
- 反过来说，**只要抓屏换成桌面复制，哪怕继续用 GDI+ JPEG 也够 60fps**（5.0ms）。

**结论 2：桌面复制相对 BitBlt 是 130~155 倍差距**，不是优化而是数量级替换。

**结论 3：「桌面复制 + H.264」的 0.4ms 是下界，不能当预算用。**
真实的 60fps 还取决于：
- GPU 编码吞吐（本程序只测了 CPU 侧提交）
- **NVENC 并发会话数限制**（消费级驱动历史上 2~3 路，新版 5~8 路）
- GDI→GPU 上传带宽（当前采集是 GDI 位图，要先上传）

### 3.3 对 `STREAM-PERF-AUDIT` 的修订建议

| 原文 | 本次实测 | 建议 |
|---|---|---|
| §2.2「JPEG 编码是最大头，估算 20~60% 单核」 | 编码 4.9ms，**抓屏 17~20ms** | **方向要反过来**：抓屏才是最大头。`§4.5(e)` 的收益排序要重写 |
| §1.2 ③④ 注「13~16ms 是 BitBlt+JPEG 合并值」 | 拆开 = **BitBlt 17~20 + JPEG 4.5~4.9** | 合并值本身偏小，且大头被归错了 |
| §4.1(a) 脏矩形「编码 CPU 降 90%+」 | 脏矩形占比 **50.7%** | 收益方向成立，但基线编码只占 4.9ms，**脏矩形的绝对收益有限**；
    真正该做的是先换抓屏（省 17~20ms） |
| §4.5(e)「P2，先在 RDP 内做可行性 spike」 | 本地可行、RDP **未测** | spike 做了一半，**剩下一半必须在 RDP 会话内跑**（§4） |

### 3.4 一个被这次数据改变的建议

原审计把 `(a) 脏矩形` 排在 `P1`、把 `(e) DXGI` 排在 `P2`。按本次实测：

> **换抓屏（BitBlt → 桌面复制）的收益是 17~20ms/帧，而脏矩形最多省 4.9ms 的一半。**

如果 §4 的 RDP 复测确认桌面复制可用，那么 **`(e)` 的可用性验证应该提到 `(a)` 之前** ——
不是先做脏矩形，而是先确认能不能换掉抓屏。反之如果 RDP 下桌面复制不可用，
那 60fps 这条路在现有架构里基本关闭，应重新评估目标帧率。

## 5. 三路径 CPU 估算

> ★ 口径说明：下表的「ms/帧」都是**实测**；「% 单核 @30fps / @60fps」是由实测换算的**估算**，
> 换算公式：`CPU%单核 = ms/帧 × fps ÷ 10`（100ms/s ÷ 1000 = 0.1%/ms，即 ms×fps/10）。
> 这个换算是「该环节独占一个核跑满」的理想值，实际会受调度/并行影响。

### 5.1 单账号，单帧成本

| 路径 | 抓屏 | 编码 | 单帧合计 | 数据来源 |
|---|---|---|---|---|
| **① 现状** BitBlt + FromHbitmap + JPEG | 17.2~19.8 ms | 4.5~4.9 ms | **≈ 22~25 ms** | 实测 |
| **② 桌面复制 + JPEG** | 0.13 ms | 4.5~4.9 ms | **≈ 5.0 ms** | 实测 |
| **③ 桌面复制 + H.264 硬编** | 0.13 ms | 0.28 ms（下界） | **≈ 0.4 ms**（下界） | 实测（下界） |

> 路径①漏了 `Image.FromHbitmap`（GDI→GDI+ 又一次 ~7.9MB 拷贝）。
> `STREAM-PERF-AUDIT` §1.2 ⑥ 提到过这段，但本程序没单独测，
> 所以①的 22~25ms 是**低估**，真实值更高。

### 5.2 折算成单核占用（单账号）

| 路径 | @30fps | @60fps | 备注 |
|---|---|---|---|
| ① 现状 | **≈ 66~75 % 单核** | ≈ 132~150 % 单核（不可能） | 与 `STREAM-PERF-AUDIT` 估的 0.3~0.7 核上界吻合 |
| ② 桌面复制 + JPEG | ≈ 15 % 单核 | ≈ 30 % 单核 | |
| ③ 桌面复制 + H.264 | ≈ 1.3 % 单核（下界） | ≈ 2.5 % 单核（下界） | 下界，不含 GPU 侧 |

> ★ 「@30fps 现状 ≈ 66~75% 单核」与 `STREAM-PERF-AUDIT` §2.2 的
> 「估算 0.3~0.7 核/账号」**上界吻合**。那条估算不是瞎猜的 —— 本次实测给了它一个硬支撑。
> 同时也说明：**这个数如果属实，8 账号全录就是 5~6 核常驻**，比文档假设的 2~3 核严重。

### 5.3 8 账号全录的量级

| 路径 | @30fps 单核合计 | 对比 32 逻辑核 |
|---|---|---|
| ① 现状 | **≈ 528 %**（5.3 核） | 约整机 **16.5%** |
| ② 桌面复制 + JPEG | ≈ 120 %（1.2 核） | 约整机 3.8% |
| ③ 桌面复制 + H.264 | ≈ 10 %（0.10 核，下界） | 约整机 **0.3%** |

> ★ 这里有三个**未测项**必须声明，否则上表会被过度信任：
> 1. **NVENC 并发会话数限制**：8 路同时硬编可能直接撞上限（消费者驱动 2~8 路），
>    撞上之后会静默回退到软编，届时 ③ 退化到接近 ① 的编码部分。
> 2. **GDI→GPU 上传**：路径 ②③ 假设帧已经在 GPU 上，实际从 BitBlt 迁移要加上传成本。
> 3. **多账号时 8 个桌面复制的并发开销**：本程序只测了 1 个 duplication 会话。

### 6.3 多次运行的稳定性

BitBlt 是唯一波动明显的一项，多轮实测：

| 轮次 | BitBlt 均值 | 桌面复制均值 | JPEG 均值 |
|---|---|---|---|
| 1 | 15.99 ms | 0.121 ms | 4.71 ms |
| 2 | 18.50 ms | 0.129 ms | 4.55 ms |
| 3 | 19.42 ms | 0.112 ms | 4.72 ms |
| 4 | 19.83 ms | 0.119 ms | 4.64 ms |
| 5 | 17.23 ms | 0.132 ms | 4.93 ms |

- **桌面复制**：0.11~0.13ms，极稳定（±15% 以内）
- **JPEG**：4.5~4.9ms，稳定
- **BitBlt**：**16~20ms，波动 ±25%** —— 受当时桌面内容/合成负载影响明显。
  这个波动本身就说明 BitBlt 在真实负载下没有确定性，不适合作为 60fps 的基础。

### 6.4 自测中修掉的 7 个真 bug

这些都是**只有真跑才会暴露**的，全部已修并复测：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 枚举到「0 个硬件编码器」 | 用 `SYNCMFT\|ASYNCMFT` 枚举看不到 NVENC | 改用 `MFT_ENUM_FLAG_HARDWARE` 单独枚举 |
| 2 | `0xC0000005` 崩溃在 `SetSampleTime` | `IMFSample` vtable 前 33 槽是 `IMFAttributes`，漏声明导致偏移错位 | 显式重复声明全部 33 个方法 |
| 3 | 仍崩（第二次） | `interface X : Y` 在这个 QI 场景下不等于手写完整 vtable | 同上，改为完全展开 |
| 4 | 「H.264 0.020ms，比 JPEG 快 236 倍」 | 异步 MFT：`WriteSample` 只入队，耗时不是编码耗时 | 改端到端口径 + 标注「CPU 下界」 |
| 5 | 「单帧 3KB」 | NV12 填充过于平坦，编码器压成极少字节 | 填拟真内容 + **300KB 体积自校验**，不达标拒绝报数 |
| 6 | 脏矩形恒 100% | `GetFrameDirtyRects` 的 size 参数是**缓冲区字节数**，不是元数据大小 | 传 `rects.Length * 16` |
| 7 | BitBlt 少拷一半像素 | `SM_CXSCREEN` 在 DPI 150% 下返回逻辑尺寸 1707x960 | 改用 `EnumDisplaySettings` 取 2560x1440 |

> 第 2/3/4/5 条都指向同一类失败：**「跑通了、有数字、但数字是假的」**。
> 这比崩溃更危险 —— 崩溃会逼你修，假数字会直接进报告。
> 所以程序里加了两道自校验：**体积自校验**（H.264）和**物理上限自校验**（CPU%）。

## 7. 已知限制（如实列出）

| 限制 | 影响 | 规避 |
|---|---|---|
| **本次非 RDP 会话** | 桌面复制可用性/耗时结论对目标场景**无效** | 必须按 §4 在 RDP 内复测 |
| H.264 数字是 CPU 侧下界 | 不能当完整编码成本 | 见 §2.7 口径说明 |
| 硬编走的是「系统内存 NV12 → MFT」 | 不是 GPU 零拷贝直通 | GPU 直通会更快，但需采集侧产 D3D11 纹理 |
| NVENC 并发会话数未测 | 8 路同时硬编可能撞限制 | 需单独做并发 spike |
| GDI→GPU 上传未测 | 路径②③ 的 0.13ms 假设帧已在 GPU | 实际迁移要加上传成本 |
| 只测 1 路 duplication | 8 账号并发的调度开销未知 | 需多路并发测试 |
| `FromHbitmap` 未单测 | 路径① 的 22~25ms 是**低估** | 真实值更高，不影响「抓屏是大头」的结论 |
| 32 逻辑核的高端机器 | 折算整机占用时要注意分母 | 报告里单核% 与整机% 分开列 |

## 8. 下一步建议（给 Lead 决策）

1. **必须做**：按 §4 在 RDP 会话内跑一次 `media-probe.exe`。
   在那之前，`(e) DXGI` 方案**不能**被标成「已验证可用」。
2. **如果 RDP 下可用**：把「换抓屏」的优先级提到脏矩形之前 ——
   实测差距是 17~20ms vs 最多省 2.5ms，投入产出比差一个数量级。
3. **如果 RDP 下不可用**：60fps 在现架构里基本关闭，建议目标帧率定回 30fps，
   精力放在「脏矩形 + 采集/观看解耦」（这两条不依赖抓屏方式）。
4. **无论哪种**：本次实测的「BitBlt 17~20ms」是一条**独立于 RDP**的硬结论，
   它意味着 `STREAM-PERF-AUDIT` §2.2 把「JPEG 编码」当最大头是错的方向，
   那张表需要按本次数据修订。
5. **可以顺带做的**：把 `PERF-MEASURE` 那个只读脚本和本程序配合用 ——
   前者量进程 CPU，后者量单帧成本，两者相乘可以互相验证。
