## B. 双观众同时订阅【实测】✅ 通过（核心验收）

**为什么这条最关键**：P1 把「每观众独立编码」改成「共享一次采集编码 + 每观众 4 帧队列」。
单观众能出画面**完全不能证明**多观众也对。队列逻辑的典型错误症状：
第二个观众订阅成功但永远读不到帧 / 两观众抢同一读指针 / 第二个把第一个饿死。
**这些只有同时连两个才暴露。**

**命令**：
```powershell
tools\stream-verify\bin\Release\net11.0-windows\stream-verify.exe dual `
    --dir $env:TEMP\sv-p1verify --port 19095 --token test123 --seconds 12 --ffprobe <ffprobe路径>
```

**方法**：两个独立 `HttpClient` **同时**长连接 `/stream`（第二个错开 1 秒加入，模拟"后加入"），
各自统计字节数与 Annex-B 起始码数量。

**输出片段**：
```
== 两个观众同时订阅 /stream（12 秒）
== 结果
  观众A  HTTP=200  字节=3164743  NAL=334  关键帧=11  时长=12.0s
  观众B  HTTP=200  字节=3164743  NAL=334  关键帧=11  时长=12.0s

== 判定
ok   观众A 收到 334 个 NAL（3164743 B）
ok   观众B 收到 334 个 NAL（3164743 B）
   两观众 NAL 数比值 = 1.00（A=334 B=334）
ok   两观众吞吐量相当（比值 ≥ 0.5，说明是共享编码+各自队列，不是互相抢占）

== ffprobe 分别验证两个观众的码流
   观众A：codec_name=h264 profile=Main level=50 width=2560 height=1368
   观众B：codec_name=h264 profile=Main level=50 width=2560 height=1368

RESULT=PASS 双观众同时订阅通过（各自都能读到帧）
```

**判读**：
- 两人**字节数完全相同**（3,164,743 B）、**NAL 数完全相同**（334）、**关键帧数完全相同**（11）。
  这正是"共享一次编码、把同一份 NAL 分发给各自队列"应有的表现。
- 如果各自独立编码，字节数通常会略有差异（编码器状态不同）；如果互相抢占，比值会明显偏离 1。
- 两个流分别被 ffprobe 独立识别为 h264 —— 说明**各自都是完整可解码的流**，不是拼凑。
- **`viewers` 字段**也在单观众测试中体现（`viewers=0`→日志里 `viewers=1`），可观测性好。

> **局限（如实说明）**：只测了 **2 个**观众。3 个及以上、以及"观众中途断开后队列是否正确释放"
> 本次**未验证**——如果需要，可以再加。

## E. WGC 帧池修复回归【实测】✅ 通过

**这是对我此前根因分析的直接检验。**
我此前判定：`WgcCapture` 用 `GetForegroundWindow()` 抓**单个窗口**（当时 1721x927），
却用 `GetSystemMetrics()` 的**整屏**尺寸（2560x1440）建帧池 → 超出区域全 0 → 全黑。
修复方式是改用 `item.Size`（已确认在 `WgcCapture.cs:117/340`）。

### 同样的场景复测

**先确认场景条件与当初一致**【实测】：
```
前台窗口: 1721x927       ← 与当初测出全黑时的窗口尺寸一致（窗口明显小于整屏 2560x1440）
```

**对照实验结果**：

| 抓法 | 尺寸 | Y 均值 | 非黑占比 | 判定 |
|---|---|---|---|---|
| CopyFromScreen | 1707x960 | 246.9 | 100.0 % | 有内容 |
| agent BitBlt | 2560x1440 | 242.9 | 99.9 % | 有内容 |
| **agent WGC** | 2560x1368 | **247.1** | **99.9 %** | **有内容** |

```
★ 两种后端都不是全黑。
RESULT=OK BOTH-FINE 两种后端都能抓到内容
```

### 修复前 vs 修复后（同一场景、同一会话）

| | 修复前（02:15 实测） | 修复后（02:57 实测） |
|---|---|---|
| WGC Y 均值 | **0.0** | **247.1** |
| WGC 非黑占比 | **0.0 %** | **99.9 %** |
| WGC R/G/B 均值 | 0/0/0 | 247/247/248 |

**人眼确认**：修复后的 `C-wgc-live.jpg`（292 KB）是**完整彩色桌面**，与 BitBlt 输出一致。

**结论：根因判断成立，修复有效。** 帧池尺寸改用 `item.Size` 后，窗口小于全屏时不再全黑。

> ⚠ **一个诚实的补充**：我无法 100% 排除"这次的前台窗口恰好变了"的可能，
> 但我**实测确认了窗口仍是 1721x927**（与当初一致），且代码里 `GetSystemMetrics` 已从这两处移除
> （仅剩 `:495` 的 `DllImport` 声明）。
> 更重要的是：`recordstatus` 现在报 `captureMs=4`（WGC），说明 WGC 路径确实在正常工作。
