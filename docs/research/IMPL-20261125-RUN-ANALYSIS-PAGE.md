### 1.1 为什么必须加 `/api/bgi/picks`（唯一新增的后端接口）

t9 把三类拾取事实（`picked` / `no_target` / `skipped`）落进了 `pick_event` 表，
存储层也有 `QueryPickFactsAsync` / `QueryPickCountsAsync`，
**但没有任何 HTTP 入口** —— 界面上「这条路线漏捡了什么」根本查不到，
只能看 run 上的汇总数字。这是任务要求 B-5 项，属于**确实缺**的最小必要接口。

接口设计（全部只读、账号维度必带、分页硬上限 500）：

    GET /api/bgi/picks?user=账号&days=7[&run=ID][&route=ID]
                      [&kind=picked|no_target|skipped][&offset=0][&limit=100]
    → { ok, user, days, offset, limit, kind,
        count,
        counts: { picked, noTarget, skipped },     ← 便于界面对账
        items: [{ runId, routeId, kind, item, ts, tsMs, lineNo, srcFile }] }

## 2. 页面结构

    运行分析（#/ledger/:id）
    ├─ 工具条：时间范围(后端) · 配置组 · 状态 · 时长≥ · 排序 · 搜索 · 重置
    ├─ 指标卡 ×6：运行次数 / 成功率 / 失败次数 / 总时长 / 总拾取 / 总摩拉
    ├─ ① 运行记录（默认展开）     ← 核心：时间 / 时长 / 状态（此前完全看不到）
    │    └─ 点行展开 → 路线明细 + 报错完整栈（按需拉 /runs/detail）
    ├─ ② 按配置组汇总（默认展开）
    ├─ ③ 拾取明细（三类计数 + kind 过滤 + 分页）
    ├─ ④ 问题组（沿用老台账视图，用户熟悉）
    └─ ⑤ 米游社摩拉（分区，展开时才加载，标注口径）

### 2.1 筛选分层（★ 最容易做错的地方）

    days（时间范围）  → **后端参数**：查库时按 cutoff 过滤 → 改了必须重新请求
    配置组/状态/排序/关键字/时长阈值/kind
                      → **前端内存过滤**：数据已在内存，改了只重渲染、不发请求

### 2.2 分页

三项列表各自独立分页，每页 50 条（`RA.pageSize`），服务端 `/api/bgi/picks` 另有
`limit≤500` 硬上限 —— 双层保护，确保单次响应远低于 §17.5 的 1 MB。

### 2.3 筛选条件写入 URL hash

    #/ledger/acc_a2?days=30&state=Finished&sort=dur-desc&kw=罐子

刷新 / 分享 / 前进后退都不丢筛选。时间范围变化时通过 `RA.days` 触发重新请求。
