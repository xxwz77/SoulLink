## 0. 结论先行（≤300 字）

**233ms 不是链路延迟，也不是浏览器/代码 bug——它是在「静止桌面」上测到的「保活节拍采样等待」。**

1. **Q1**：RDP 自身传画面有延迟，LAN 同机 **20~60ms**（物理下限 ~20~38ms）。这是差分测量的"零点基准"，要从 233ms 里**加回去**：SoulLink 绝对端到端 ≈ **253~293ms**，比 233 更大。
2. **Q2**：233ms 的主项是**静止桌面保活节拍**。代码常量 `KeepaliveIntervalMs=500`（2fps）【代码事实 SessionRecorder.cs:89】，实测静止 /stream 只推 **2.10fps、帧间隔 531.6ms**，随机采样的期望等待 **233~261ms**，与用户读数**数值直接重合**【实测 12 §5.3】。服务端单帧工作仅 **13ms(p50)**、队列 **0ms**、传输 **~5ms**、浏览器段 **1~5ms（最坏 25ms）**——这些加总 ~20~40ms，**解释不了 233ms**。所谓"~140ms 账外缺口"= **帧龄（抓屏节拍里的等待）**，服务端日志从不记这一项。**输入/鼠标链路已排除**（秒表法是纯视频差分）。
3. **Q3**：**第一优先不是改代码，是让用户"让画面动起来"复测一次**（成本≈0，预判 233→20~40ms）。真代码动作按 P0 埋点（帧级 capturedAt）、P1 静止保活 500ms→100~200ms（产品决策）、P2 2D 回退兜底。**换 UDP 收益 ≈0，不要做。**

## 2. Q1 —— RDP 本身传送画面也有延迟吗？大概多少？

**有。LAN 同机 **20~60ms**，物理下限约 **20~38ms**。** 但它是这条测量的"零点基准"，方向要反过来读。

### 2.1 RDP 侧延迟构成（标来源）

| 段 | 量级 | 证据等级 |
|---|---|---|
| DWM 合成等待 | 0~16.7ms（p50=15.2ms，60fps 节拍） | 【已有实测】RDP-DDA-CEILING：DWMFRAMEINTERVAL=15 已设，帧间隔 p50=15.2ms |
| RDP 编码（bitmap delta / AVC444） | ~2~10ms（官方预算 33ms/帧，硬编实际个位数） | 【官方文档+推断】KB2885213 / RemoteFX 计数器 |
| 传输（LAN/回环） | 0.8~5ms | 【已有实测】AUDIT-00：/live 0.8ms p95 4.6ms |
| 客户端解码 + 直绘上屏 | 解码 2~5ms + 0~16.7ms vsync | 【推断】 |
| **RDP 端到端合计** | **物理下限 ~20~38ms，现实典型 ~20~60ms** | 【推断】与 HANDOFF-20261124 §3.4「20~38ms」口径一致 |

### 2.2 为什么 RDP 低（机制差异，决定它"低"不是"黑科技"）

| 环节 | RDP | SoulLink Relay | 证据 |
|---|---|---|---|
| 抓屏 | DWM 重定向面直通图形管线，**无 CPU 读回** | DDA Acquire + staging + Map + Marshal.Copy 读回 8.3MB BGRA | 【代码事实】DxgiDdaCapture.cs:428-472 |
| 色彩 | 保持 GPU 原生格式 | 跨 GPU 零拷贝禁用 → CPU BgraToNv12 1~2ms | 【代码事实】SessionRecorder.cs:1332-1414 |
| 编码 | bitmap delta（静态/UI）+ AVC444 满屏 | 全帧 H.264 NVENC，无 delta | 【官方文档+推断】 |
| 队列 | 无多帧 viewer 队列 | Pending 深度 2 | 【代码事实】SessionRecorder.cs:97 |
| 客户端 | 解码直绘 | WebCodecs + WebGL2 直绘 | 【代码事实】web-index.html:1204 |

### 2.3 关键结论

**RDP 那 20~60ms 不是"233 里能扣掉的部分"，而是"要加回绝对延迟的部分"**：
- SoulLink 绝对端到端 = 233 + RDP自身(20~60) ≈ **253~293ms**。
- 233ms 差分里，"物理/会话层下限"占 **0ms**（差分把共有段和 RDP 下限都抵消了）——233ms 全部是 SoulLink 相对 RDP 多出来的可优化部分。

## 3. Q2 —— 233ms 归因排序（每项 ms 区间 + 证据等级 + 最大可控项）

> 口径：233ms = SoulLink(浏览器) E2E − RDP E2E（同一桌面、秒表、多次截图平均）。测量方法本身**已由 12 §3 标定验证可靠**（注入 0/50/120/300ms → 读出 0/52/122/300ms，误差 ≤2ms）——**233ms 是真实测到的量，不是噪声**。

### 3.1 归因表（按对 233ms 差分的贡献排序）

| 归属段 | 对 233ms 的贡献（ms） | 证据等级 | 说明 |
|---|---|---|---|
| **静止保活节拍（帧龄）** | **~200~233ms**（静止 2.10fps，帧间隔 531.6ms，采样期望 233~261ms） | 【实测】12 §5.3 + 【代码事实】SessionRecorder.cs:89 | **主项，数值直接重合。** 静止桌面保活 2fps，画面任何变化最多等 ~500ms 才被采到编码 |
| **服务端管线（capture+convert+encode）** | ~13ms(p50) / 27ms(均值)；差分里净 ~5~15ms | 【实测】12 §5.2（70 行日志：capture 7 + convert 2 + encode 4） | 已被日志记账，不是账外项 |
| **服务端 viewer 队列** | ~0ms（queueAge p50=0，max 18ms） | 【实测】10 §5.1 / 12 §5.2 | 事件驱动已消除轮询税 |
| **传输层（HTTP chunked/TCP）** | 2~20ms（典型 ~5ms） | 【实测】10 §3/§5（回环 RTT 1.1ms）+ 12 §12.1（Nagle 分写 <1ms） | 换 UDP 收益 ≈0，见 §4 |
| **浏览器段（收包→解码→上屏）** | 1~5ms（p95 ≤8ms，最坏 1 vsync ≤25ms） | 【实测】09 §4 + 12 §5.4 | WebGL2 主路径 texImage2D 0.1~0.2ms；2D 回退 22ms/帧**仅当 WebGL2 不可用** |
| **输入/鼠标链路** | **0ms（已排除）** | 用户澄清 + 口径定义 | 秒表法是纯视频差分，不含鼠标事件 |
| **物理/会话层下限（RDP 自身）** | 差分中 0ms（已抵消）；绝对口径需 +20~60ms | 08 §1.3 | 这是要"加回"的，不是"扣掉"的 |

### 3.2 核心矛盾的解法："~140ms 账外缺口"去哪了

服务端日志自报 ~90ms 与真机差分 233ms 之间的缺口，**不是"某一段慢"，而是"日志只记单帧工作耗时，从不记帧龄"**：

| 项 | 日志是否记录 | 量级 |
|---|---|---|
| captureMs + convertMs + encodeMs | ✅ 记录 | 13ms(p50) |
| queueAge（入队→出队） | ✅ 记录 | 0ms |
| **帧龄（采集→入队的抓屏节拍等待）** | ❌ **从不记录** | 静止 **233~261ms** / 动态 0~118ms(p90) |
| 浏览器收包→上屏 | ❌ 不记录（协议无 capturedAt） | 1~5ms（实测） |

**结论**：所谓 140ms 缺口 ≈ 静止场景下的"帧龄"。旧"~90ms"是在**动态（鼠标移动 43fps）**场景测的（帧龄仅 ~11ms）；用户 233ms 是在**静止（秒表桌面 2fps）**场景测的（帧龄 ~233ms）。**两者场景不同，不是"哪里漏了 140ms 的 bug"。**

### 3.3 最大可控项

**最大可控项 = 静止保活节拍（帧龄）**。把 `KeepaliveIntervalMs=500` 提到 100~200ms（5~10fps），静止场景采样等待从 ~233ms 降到 ~50~100ms，**可回收 ~130~180ms**——这是所有候选里唯一"量级级"的收益，且改动一行、无风险。其余（管线 13ms、传输 5ms、浏览器 5ms）都已接近各自物理/工程下限，继续压的空间都在个位数 ms。

### 3.4 一处必须诚实标注的条件性

12 §5.3 同时测到「静止（另一时段）17.25fps / 17.30fps」——说明"静止"不总等于 2fps：只要桌面上有**任何在变的东西**（正在跑的毫秒钟、闪烁光标），DDA 就产出 ~17fps，采样等待降到 ~28ms，233ms 就不成立。因此 **233ms=保活节拍 这个结论，成立前提是用户测量时段桌面处于真静止（秒表未在跑/变化极慢）**。这正是 Q3 把"复测一次（画面动起来）"列为 P0 的原因：一次复测同时关闭这最后的 10% 不确定性，也顺带验证管线真实延迟。

## 4. Q3 —— 下一步做什么（P0 / P1 / P2）

> 每项：改哪个文件 / 预期省多少 ms / 风险 / 用户可自测步骤。
> 先分「测量/环境问题」与「真延迟优化」两类——**前者优先级更高**，因为当前最大嫌疑是"静止场景把保活节拍测成了延迟"，必须先复测定性，再决定要不要改代码。

### A. 测量/环境问题（先做，成本≈0，决定要不要改代码）

#### A1（P0）让画面"动起来"复测一次 —— 定性 233ms 是节拍还是链路
- **改哪个文件**：无（零代码）。
- **预期**：动态场景读数 233 → **20~40ms**（移动 26fps 帧间隔 18ms + 单帧 13ms + 解码 <1ms）。
- **风险**：无。
- **用户自测**（12 §2.3）：被测桌面放一个**持续变化**的动画窗口（或用 12 的条码时钟）→ Windows 分屏，左边 RDP、右边 SoulLink 浏览器同显 → **单张同框截图**（Win+Shift+S 一次截全屏）→ 读两通道差值 → 重复 ≥15 次报 p50/p90。**判读：读数掉到几十 ms = 之前 233 是静止保活节拍，不是链路慢；仍 >200ms = 才进入 B2 埋点追查。**

#### A2（P0）确认自己有没有落到 2D 回退（唯一还活着的浏览器段风险）
- **改哪个文件**：无。
- **预期**：确认后要么排除浏览器段，要么发现 22ms/帧的 2D 回退。
- **风险**：无。
- **用户自测**（09 §8 步骤 1，一条命令）：F12 → Console 粘贴：
  `const c=document.getElementById('vframe'),gl=c.getContext('webgl2'); console.log('路径:',(gl&&!gl.isContextLost())?'WebGL2(正常)':'2D回退(慢22ms/帧)')`
  → 输出 `2D回退` 才需要 B3。

### B. 真延迟优化（A1/A2 之后，按优先级）

#### B1（P0）帧级时间戳埋点 —— 把"账外"变"账内"（终结 140ms 争议的唯一手段）
- **改哪个文件**：`Relay/SessionRecorder.cs`（VideoFrame 加 `CaptureAtTicks`，:~795/~1012 构造、:1020-1027 日志、:1211-1231 出队）+ `Relay/AgentWebServer.cs:516-525`（v=2 帧头 4B→12B 带 capturedAtUnixMs）+ `docs/web-index.html:1496-1505`（解帧头算 `now − capturedAt` 单程延迟）。
- **预期省多少 ms**：本身 0ms；价值是把端到端从"差分猜"变成"单程实测"，永久终结"账外缺口在哪"的争论。
- **风险**：低（只加字段、不改行为）；需同步改 3 处 + 客户端/服务端版本对齐（streamVersion 协议）。
- **用户自测**：改后连流看顶栏/控制台新增 `frameAgeMs / E2E ms`，与秒表差分对账。

#### B2（P1）静止保活节拍 500ms → 100~200ms（产品决策，非 bug 修复）
- **改哪个文件**：`Relay/SessionRecorder.cs:89`（`KeepaliveIntervalMs`）。
- **预期省多少 ms**：静止场景采样等待 **~233ms → ~50~100ms（省 ~130~180ms）**——全链路唯一"量级级"收益。
- **风险**：静止带宽从 ~80KB/15s 等比例上升（5fps 约 4~5 倍）；**属产品决策**——若用户高频场景是游戏/视频（持续动态），此改动收益趋零，反而白增带宽；若含"盯数字/进度条/静止桌面"，则是体验质变。
- **用户自测**：静止桌面下通过浏览器看一个跳秒表，改动前后对比"数字跳变到画面更新"的间隔；同时观察带宽（任务管理器 / agent 日志流量）。

#### B3（P1）2D 回退兜底（仅当 A2 确认落到 2D 才需要）
- **改哪个文件**：`docs/web-index.html:1248` 后 + `:1315-1319`（WebGL2 不可用时把 canvas backing 降到 `min(显示尺寸, 视频尺寸)`）。
- **预期省多少 ms**：2D 强制同步 **22ms → 3.7ms/帧**（09 实测 backing 900×506）；60fps 下从"稳态积压 100ms 丢帧"回到"0 积压"。
- **风险**：低（只动回退分支）；画质略微下降（降采样到显示尺寸）。
- **用户自测**：A2 那条命令若报 `2D回退`，改后重跑，看 `drawImage` 耗时从 22ms 掉到 <5ms。

#### B4（P2，建议不做）换 UDP / WebTransport
- **结论**：**局域网/回环场景收益 ≈0 甚至为负**（TCP 现状传输段 0.8~5ms，丢包≈0；UDP 省 <2ms，但要付 HTTPS+证书+QUIC 服务端栈成本）。触发条件 = 未来公网/穿透（RTT>20ms 且丢包>0.5%）才启用（10 §6 决策树已就绪）。

## 5. 一句话给用户/Lead

**233ms 大概率不是"哪里慢"，而是"静止桌面下 2fps 保活节拍让画面变化最多晚 500ms 才被推出来"。先让画面动起来复测一次（A1，零成本），读数若掉到几十 ms 就实锤；之后唯一值得做的代码动作是 B1 埋点（把帧龄变可测）+ B2 静止保活提速（产品决策）。浏览器段（1~5ms）、传输段（~5ms）、服务端单帧（13ms）都已接近下限，不是本问题的主战场。**
