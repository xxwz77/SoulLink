## 一、★ 「图标列在黑边区不挡画面」有没有标准做法

### 1.1 这在技术上叫什么

**这是「letterbox 区域（黑边）利用」** —— 当视频比例 ≠ 屏幕比例时，必然产生黑边；
**成熟做法是把 UI 放到黑边里**，而不是浮在视频上。

### 1.2 三个产品的实际做法（对比）

| 产品 | UI 放在哪 | 是否压画面 | 出处 |
|---|---|---|---|
| **向日葵**（本次录屏） | **黑边/留白区** | **不压** | v0032 / v0142 像素观察 |
| **Moonlight** | **完全不放常驻 UI**（屏幕全给游戏），操作用三指手势/键组合 | 不压 | `Game.java` 无常驻工具栏；`THREE_FINGER_TAP_THRESHOLD=300` |
| **RustDesk** | **底部常驻工具栏**（`_showBar`） | **会压**，但可折叠 | `remote_page.dart:92, 690-698` |

### 1.3 「把 UI 放进黑边」的技术前提

**必须先知道黑边有多大** —— 而这依赖两个值：
1. **视频宽高比**（服务端分辨率，我们 `prefConfig.width/height` 等价物）；
2. **屏幕宽高比**（`DisplayMetrics`）。

**Moonlight 的 `StreamView.onMeasure()` 就是在算这个**（`StreamView.java:38-60`）：
```java
if (widthSize > heightSize * desiredAspectRatio) {
    measuredHeight = heightSize;
    measuredWidth  = (int)(measuredHeight * desiredAspectRatio);   // 左右黑边
} else {
    measuredWidth  = widthSize;
    measuredHeight = (int)(measuredWidth / desiredAspectRatio);   // 上下黑边
}
setMeasuredDimension(measuredWidth, measuredHeight);
```
**⇒ 这段代码算出的 `measuredWidth/Height` 就是「画面实际占的矩形」，
屏幕减掉它，剩下就是黑边区 —— 也就是「可以安全放 UI 的地方」。**

### 1.4 结论：**有标准做法，而且我们已经有现成的数学**

**标准做法 = 「letterbox 内摆 UI」**：
```
1. 算出画面矩形（等比缩放后）
2. 屏幕 - 画面矩形 = 安全 UI 区（黑边）
3. 若安全区够大（如上下各 > 48dp）→ UI 放里面（不压画面）
4. 若安全区太小（如全面屏几乎无黑边）→ 退回「半透明浮层 + 可折叠」
```

**为什么这是最优解**：
· **不遮挡内容**（用户看得到完整远端画面）；
· **不依赖手势**（按钮可见、可发现）；
· **同时解决了「工具栏挡住自己要点的东西」** —— 这是远控最烦的体验问题。

**⇒ 我们该怎么做**：
**这正是我上一份报告（`INTERACTION-STANDARDS §5.2`）说的「常驻折叠按钮」的最佳落点** ——
**按钮不放画面内，放黑边区。** 两者结合：
· **黑边够大** → 工具栏直接常驻在黑边里（学向日葵）；
· **黑边不够** → 折叠按钮放黑边、展开时浮层（学 RustDesk）。

## 二、「官方推荐布局」有没有开源实现

### 2.1 有：Moonlight V+ 的 4 套预设（源码确认）

**文件**：`app/src/main/java/com/limelight/binding/input/virtual_controller/VirtualControllerConfigurationLoader.kt`（12,440B / 192 行）

**预设枚举**（`VirtualControllerLayout.kt`，395B 全文）：
```kotlin
enum class VirtualControllerLayout(val preferenceValue: String) {
    XBOX("xbox"), DS("ds"), NS("ns"), CLASSIC("classic");
}
```

**坐标体系**：沿用官方 **128×72 逻辑网格**，按 `scale = height / 72f` 缩放（`L36` 附近）。

**各预设的差异点（源码确认，`VirtualControllerConfigurationLoader.kt`）**：

| 差异 | XBOX | DS | NS | CLASSIC |
|---|---|---|---|---|
| 强调色 | `0xFF8ED269`（绿）`L42` | `0xFF83B7FF`（蓝）`L43` | `0xFF56CEE5`（青）`L44`，**右侧另用 `0xFFFF7C83` 红** `L49` | `0xF00000FF` |
| 面键布局 | 标准 XBOX 排布 | **`symmetric` 对称排布** `L69` | **`swapped` 面键互换** `L85`（还与 `config.flipFaceButtons` 异或） | 沿用官方原始 |
| 肩键标签 | `L1/R1` | `L1/R1` | **`L/ZL/R/ZR`** `L108` | 同官方 |
| Back/Start | `BACK`/`START` `L119-120` | `⋯`/`≡` | `−`/`+` | `BACK`/`START` |
| Guide | `⌂` | `⌂` | `⌂` | `GUIDE` `L129` |
| 坐标单位 | 非 classic 用 `(x*scale)+rightOffset`，`L52-58` | | | classic 用 `x*scale`（原始） |

**关键实现细节**（`L52-58`）：
```kotlin
controller.addElement(element,
    (x * scale).roundToInt() + if (right) layoutWidth - (128 * scale).roundToInt() else 0,
    (y * scale).roundToInt() + controller.profileOffsetY,
    // Round shared boundaries once so adjacent hit targets never overlap by a pixel.
    if (classic) (w * scale).roundToInt()
    else ((x + w) * scale).roundToInt() - (x * scale).roundToInt(),
    ...)
```

**⇒ 三条可直接借鉴的工程做法**：
1. **逻辑网格 128×72 + 按高度缩放** —— 跨设备一致；
2. **`right` 标志让右侧键簇「从右往左排」**，不用为每种屏幕重算坐标；
3. **相邻控件边界只取整一次**（`(x+w)*scale - x*scale` 而不是 `w*scale`）—— **防像素重叠导致点击区互相吃**。

### 2.2 我们的可行性

**V+ 是 GPL-3.0** ⇒ **不能抄代码**，但**坐标体系与工程做法可借**（这是设计思想，不是代码）。

**我建议我们的预设直接用这 4 类**（XBOX/DS/NS/自定义），因为：
· 用户熟悉（对应三种手柄）；
· **中文场景下「NS 布局」最像手游**（面键位置与任天堂一致），**对原神/永劫这类跨平台游戏最自然**。

## 三、「游戏键盘」的布局生态

### 3.1 ★ 向日葵的完整生态（v0134 + v0139 证据）

**四个标签页**（v0134）：
| 标签 | 含义 |
|---|---|
| 最近使用 | 用过的布局 |
| **官方推荐** | 官方维护的布局库 |
| **网友分享** | **UGC（用户生成内容）** |
| 我的键盘 | 自己创建的 |

**布局详情页**（v0139，我找的这一帧）：
```
┌────────────────────────────────┐
│ 键盘预览 · 原神手机端按钮     ✕ │
├────────────────────────────────┤
│  [布局缩略图：左摇杆 + 右侧键簇] │
│                                │
│  👍 30    ⭐ 85    ↗            │   ← 点赞数 / 收藏数 / 分享
│  ┌──────────────────────────┐  │
│  │      使用 · 835          │  │   ← 835 人使用过
│  └──────────────────────────┘  │
└────────────────────────────────┘
```

**⇒ 这是一个完整的「布局分享生态」**：
1. **官方维护一批**（官方推荐）；
2. **用户上传/分享**（网友分享）；
3. **有社交指标**（点赞 30、收藏 85、使用 835）；
4. **一键套用**（「使用」按钮）；
5. **预览**（缩略图 + 名称）。

### 3.2 其他产品的类似机制（对比）

| 产品 | 有没有布局分享生态 | 出处 |
|---|---|---|
| **向日葵** | ✅ **完整**（官方+网友+点赞+收藏+使用数） | v0134 / v0139 录屏 |
| **Moonlight V+** | ✅ **部分**：4 套预设 **+ `crown-profiles` 社区配置仓库**（「Community Crown profile store for Moonlight V+」，`qiin2333/crown-profiles` 6★，通过 `index/v1.json` 静态商店分发） | T30 报告已记录；`crown-profiles` README |
| **Moonlight 官方** | ❌ 只有 1 套内置布局，**不能改键位**（只能移动/缩放） | `VIRTUAL-CONTROLS-RESEARCH` §4.4（552 行已详） |
| **RustDesk** | ❌ **未发现**（它是远程桌面，不是游戏按键场景） | 本轮查 `remote_page.dart` 无相关 |

**⚠️ 注意**：V+ 的 `crown-profiles` 是**「王冠配置」（Crown）**，
[推测] 从命名看它是**整套串流参数预设**（分辨率/码率/HDR 等），**不一定是虚拟按键布局**。
**我没有找到 V+ 有「虚拟按键布局」的社区分享** —— 它的 4 套预设是**硬编码在代码里的**。

### 3.3 对我们的启示（按投入产出排序）

| 阶段 | 做什么 | 依据 |
|---|---|---|
| **P0** | **内置 2~3 套预设**（桌面操作 / FPS / 3D 游戏），**本地保存自定义** | V+ 的做法（代码内置） |
| **P1** | **导入/导出**（JSON 文件，用户之间手动分享） | 成本最低的「分享」 |
| **P2** | **官方推荐库**（我们维护，随版本更新） | 向日葵「官方推荐」 |
| **P3** | **网友分享 + 点赞/收藏/使用数** | 向日葵「网友分享」，**但这需要服务端 + 审核 + 运营，成本最高** |

**我的建议：P0+P1 先做，P2/P3 明确不做。**
理由：我们是**工具**不是**社区产品**；
用户量不足以形成 UGC 生态，**做了没人上传就是空页面**（比没有更糟）。
**⇒ 这与 ATM-GI 的 `docs-对比报告.md` 教训一致：要敢写「不建议做的」。**

## 四、v0142 布局的实测结构（供设计参考）

**从左到右、从上到下（像素观察）**：

| 位置 | 内容 |
|---|---|
| **左侧**（画面左边缘外） | `Esc`、`F1`、`Q`/`W`/`A`/`S`/`D` 十字、`Enter`、`Alt` —— **约 9 个** |
| **右侧**（画面右边缘外） | `F`、`R`、`C`、`Shift`、`空格` + **顶部一排圆形键** —— **约 12 个** |
| **形态** | **半透明圆形**（能看见底下的黑边/桌面边缘） |
| **是否压画面** | **不压**（全部在画面矩形外） |

**⇒ 这个布局对我们的直接价值**：
· **左侧 = 移动键簇**（WASD 十字 + 修饰键）；
· **右侧 = 动作键簇**（技能/交互/跳跃）；
· **这正是「FPS/3D 游戏」的经典分配**，可以直接作为我们的第 2 套预设。

## 七、给我们的一句话

**向日葵这 211 帧最有价值的一条，不是「它有虚拟键盘」，而是：**

> **它把 UI 放在黑边区，一点画面都不挡。**

**我们现在的「单击呼出菜单」+「UI 压画面」是两个错误叠加。**
正确做法是：**算出画面矩形 → 把工具栏放进剩余黑边 → 单击还给远端左键。**
