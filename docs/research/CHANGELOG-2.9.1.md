# SoulLink 2.9.1 变更

日期：2026-11-19
主线：三种通道模式的互斥保护（手动优先）

## 背景

系统里有三条并存的通道：

| 通道 | 代理进程 | 命令行 |
|------|----------|--------|
| SYSTEM 计划任务 | SoulLink.proxy.exe | --relay <管道> |
| Broker 服务 | SoulLink.Agent.exe | --relay <管道> |
| 手动代理 | SoulLink.Agent.exe | （无参数） |

它们会在同一会话里争用同一桌面的输入，表现为「操作异常 / 视角乱跳」。

## 三条互斥

### 1. 手动优先（会话监控）

`ScanAndDeployAsync` 每轮扫描先判断该会话是否有手动代理，
有则完全跳过自动投送，不创建任何新代理。

理由：用户手动跑代理的场景就是「自动不好用、我要自己控制」，
自动再去建通道只会和它抢输入。

### 2. 手动代理单例

第二个手动代理在启动最开始抢占标记，失败则退出码 4。

### 3. 管道天然单例

同一管道名无法建两个服务器，内核保证。这是最后一道兜底。

## 关键设计取舍：为什么用互斥体而不是命令行

最初实现是解析 `--relay` 来区分手动/自动代理。**这条路走不通**：

- 跨进程读命令行要解析 PEB，布局在各 Windows 版本 / 位数下不同
- 写死偏移会读到别处的值。实测读到过 `Length = 36312` 这种明显异常，
  更糟的是有时会读到「看起来合理」的假值，导致命令行被**悄悄截断**
  （`C:\Program Files\SoulLinkDev\SoulLink.exe "C:\Progra` 只读到一半），
  于是 `--broker` 检测失败，Broker 服务被误判成手动代理
- 这类静默错误比直接失败更难排查，为此消耗了多轮

最终改用**命名互斥体**：

```
Global\<身份>.ManualAgent.<会话号>.v1
```

- 存在性判断是内核原子操作，跨会话可见
- 进程退出自动释放，不会残留导致自动投送被永久卡住
- 不依赖任何 PEB / WMI / 命令行解析

副作用：删除了 `Services/ProcessCommandLine.cs`（PEB 解析实现）。

## 验证

`AgentMutexCheck`（新）：

```
ok   没有手动代理时不误报（宿主进程不会被当成代理）
ok   手动代理启动后能被识别（手动优先依据）
ok   重复启动的手动代理会退出
ok   重复启动返回专用退出码 4
ok   手动代理退出后标记自动释放（不会永久卡住自动投送）
ok   同一管道名不能有两个服务器（天然互斥）
```

其余回归全部通过：LogFilterCheck / ManualAgentCheck / ManualAgentLiveCheck /
BrokerCheck / BrokerAuthCheck / ProxyRaceCheck。

## 未解决

- **A3 会话侧键未命中**仍未修复。手动代理可用于在该会话复验，
  以区分「投送路径问题」还是「注入本身问题」。
- 手动优先不主动杀掉已存在的自动代理，只影响后续调度。
- UAC 开启的 linked token 分支、冷启动时间窗口、锁屏与会话切换未回归。
