## 0. 结论速览（先看这里）

1. **国内云电脑/云游戏没有一个用 RDP。** 它们全部是「自研串流协议 + GPU 虚拟化/直通 + 边缘节点调度」三层。RDP 是「桌面会话远程投影」协议，云游戏是「GPU 渲染 → 编码 → 推流」的媒体管线，两者在采集层、编码层、注入层的思路完全不同。这就是它们能在 60fps 跑、SoulLink 在 RDP 会话内 BitBlt 只能 22~31ms 的**结构性根因**：云游戏在**真实 GPU 桌面/离屏表面**上抓帧（DXGI/WGC/API hook 全可用），SoulLink 在 **RDP 会话（无真实桌面复制通道）**里抓帧（DXGI DDAPI 失败、只剩 BitBlt/WGC 待测）。
2. **「一台机器多开」有两条截然不同的技术路线**：
   - **真云厂商（顺网/达龙/腾讯 START/米哈游/阿里/华为）＝ 数据中心 GPU 服务器 + 虚拟化（vGPU/直通/容器）**，每用户一个「GPU 实例 + 独立 Windows/游戏会话」，串流出去。这是「重资产、重架构」，SoulLink **抄不动**（也不该抄——SoulLink 是单机工具，不是云服务商）。
   - **远程控制厂商（UU/ToDesk/向日葵/RayLink）＝ 现有 Windows 桌面 + 自研串流 + 键位映射**，一台 PC 一个桌面被远程看/控，**不做虚拟化多开**。这一路才和 SoulLink「本机多账号 + 远程控制」**同构**，是唯一值得抄的对象。
3. **值得抄的三样东西**（详见 §6/§7）：
   - **抓屏/编码**：抄 Sunshine/云游戏共识的「WGC + 硬件编码（NVENC/AMF/QSV）+ 无 B 帧 + 无限 GOP/按需 IDR + 丢旧帧」——SoulLink 已识别的方向，本文从国内产品侧再次证实这是唯一正确的路。
   - **手机操作**：UU 远程的「官方键位方案库（400+ 游戏，分享码导入）+ 滑动转视角（按住左/右/中键滑动）+ 触屏/鼠标指针双模式 + 显示鼠标自动隐藏按键 + 锁定鼠标禁用点击 + 宏/一键多键」。这与 SoulLink 已有 `VIRTUAL-CONTROLS-RESEARCH` 的定案**完全一致**，本文补齐「产品级设计清单」。
   - **延迟目标**：云游戏端到端 RTT 预算「边缘节点 30~50ms、超 80ms 拖滞」；桌面云（华为 HDP/阿里 ASP）官方口径「端到端 <100ms 无感知」。SoulLink 局域网场景应能做到更好，外网应把目标定在 <100ms。
4. **SoulLink 与它们的本质区别**（一句话）：云厂商是「**我把 GPU 搬到云端，你远程玩**」；SoulLink 是「**你的游戏已经跑在你本机 RDP 会话里，我只做画面+输入的中继**」。所以 SoulLink 不需要也不应该重做虚拟化多开，只需要**把「RDP 会话内的抓屏/编码/输入注入」这条链路做到云游戏同等的低延迟标准**。

## 2. 官方宣传 vs 用户实测反馈（延迟/帧率可信度）

> 官方数字是**营销口径**，不能直接当工程基准；本节把「宣传值」与「第三方/实测」分开，标注可信度。

| 产品 | 官方宣传 | 第三方/实测线索 | 可信度判断 |
|---|---|---|---|
| UU 远程 | 4K 144 帧、500 Mbps 码率、毫秒级延迟 | 官网玩家评价反复强调「局域网下延迟低、画面跟手、像本地」；无第三方精确 ms 实测 | 局域网体验好（自证）；4K 144 是**上行能力上限**，实际受被控端 GPU 与网络约束，非承诺常态 |
| 顺网云电脑 | 3A 15~25ms、330+ 边缘节点 | 第三方实测报告称「3A 游戏延迟低至 15-25ms」；「通宵包 3.98 元」 | 15~25ms 是**边缘节点就近**下的网络 RTT 口径，不含渲染/编码；可信但需拆解 |
| 腾讯 START | 60 帧超清 | 会员资费报道明确「15 小时/月、60 帧」 | 60 帧是会员档承诺；画质分档 |
| 云·原神 | 60 帧、超高清 | 攻略站：需等级≥10、高帧率资格、最低码率 ≥15 Mbps、帧率优先模式 | 60 帧有准入门槛（资格+码率），体验标杆但门槛真实 |
| ToDesk | 8K 360 帧、<3ms | 「<3ms」是**内网/专线**口径（官网小字语境）；高清场景 <0.04s（40ms）更接近真实端到端 | <3ms 不现实作为端到端（仅传输环节）；40ms 量级更可信 |
| RayLink | 144 帧、10ms | 未找到第三方精确实测 | 10ms 同为传输口径 |
| 华为 Workspace | HDP、<100ms | 掘金/墨天轮/白皮书多次提到「端到端时延 <100ms、YUV444 真彩」 | <100ms 是**桌面办公**口径，可参考；游戏未承诺 |
| 阿里 无影 | ASP 自适应流化 | 官方文档「低时延、自适应编码、替代 HDX」 | 未公开游戏级帧率/延迟 |

**共性结论**：
- 云游戏/云桌面的「延迟」宣传几乎都指**网络传输/协议环节**，不叠加渲染与编码；真实的「手感延迟」要再加渲染帧时间 + 编码 2~8ms + 解码 + 显示。**SoulLink 对标时，应把目标定为「端到端 <100ms」，而不是拿厂商的 <3ms/<10ms 宣传值当基准。**
- 「帧率」宣传（144/360）是**被控端/上行渲染能力上限**，远端显示实际受码率、解码、屏幕刷新率约束。

## 3. 国内云电脑的「多开」与串流架构分析（核心）

### 3.1 两条截然不同的「多开」路线

```
路线 A：数据中心云厂商（顺网 / 达龙 / 腾讯 START / 米哈游 / 阿里 / 华为）
┌──────────────────────────────────────────────────────────────┐
│  GPU 服务器（如 NVIDIA A10/A16/L40，支持 vGPU/直通）           │
│   ├─ 虚拟机 1 ── Windows + 游戏进程 1 ── 编码器 ─┐            │
│   ├─ 虚拟机 2 ── Windows + 游戏进程 2 ── 编码器 ─┼─ 边缘节点   │
│   └─ 虚拟机 N ── Windows + 游戏进程 N ── 编码器 ─┘  ── 用户端  │
│   虚拟化技术：GPU 直通（1 GPU = 1 VM）/ vGPU（1 GPU = 多 VM）  │
│              / 容器（LXC/Docker，云游戏常见「一卡多路」）       │
└──────────────────────────────────────────────────────────────┘

路线 B：远程控制厂商（UU / ToDesk / 向日葵 / RayLink）
┌──────────────────────────────────────────────────────────────┐
│  用户自己的 1 台 PC（物理机，跑 1 个 Windows 桌面）            │
│    └─ 被控端 Agent ── 抓屏(GPU) ── 编码 ── 专网/P2P ── 手机    │
│    └─ 输入回传（触屏/键鼠/手柄）→ 注入本机                     │
│  无虚拟化，无多开；一台 PC 就是一个可被远程看的桌面            │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 云厂商的 GPU 多开三技术（业界共识，非单一产品内部文档）

来自多篇公开技术文章（CSDN《云游戏 GPU 虚拟化技术分析》《云游戏时延预算》《云游戏架构》等）交叉印证：

| 技术 | 做法 | GPU 利用 | 隔离 | 成本 | 适用 |
|---|---|---|---|---|---|
| **GPU 直通（passthrough）** | 物理 GPU 整卡直通给 1 个 VM | 1 卡 = 1 用户 | 强（硬件隔离） | 最高 | 高规格单用户 |
| **vGPU（虚拟化）** | NVIDIA vGPU（MIG/GRID）把 1 张 GPU 切成多份虚拟 GPU | 1 卡 = 4~16 用户 | 中（显存/算力隔离） | 中 | **云游戏主流**（一卡多路） |
| **API 转发/容器** | 容器共享宿主机 GPU，应用层 API 转发（如 CloudXR、自研 hook） | 最高 | 弱（共享） | 最低 | 手游/轻量多开 |

**对 SoulLink 的含义**：这三条都是**数据中心重资产**（要买 vGPU 授权、要装虚拟化平台、要机房+边缘节点），SoulLink 是「单机多账号 RDP 挂机工具」，**不是、也不该变成云厂商**。SoulLink 的「多账号」是靠 **RDP 多会话（Windows 多用户会话/RDP 环回）** 实现的，本质是「操作系统级的桌面会话隔离」，而非「GPU 级虚拟化」——这条差异在 §5 展开。

### 3.3 云厂商/远程控制的串流管线（共性）

无论路线 A 还是 B，串流内核都长这样（SoulLink 可对照）：

```
[抓屏] DXGI Desktop Duplication / WGC / 游戏引擎 API hook / 离屏表面
   → 真 GPU 帧（不是 GDI BitBlt 的 CPU 拷贝）
[编码] 硬件编码器 NVENC / AMF / QSV（或云厂商自研低延迟编码）
   → 无 B 帧、低延迟 tune、无限 GOP/按需 IDR、CBR
[传输] 自研 UDP 协议 / WebRTC(DataChannel+RTP) / HDP / ASP
   → 丢旧帧 + NACK/FEC + 拥塞控制 + 边缘节点就近
[解码+显示] 客户端硬解 → 超分 → 上屏（低延迟渲染）
[输入回传] 触屏/键鼠/手柄 → 独立低延迟通道（UDP/WebSocket），与视频流分离
```

关键设计共识（对 SoulLink 直接有用）：
1. **视频流与输入指令通道分离**（CSDN 原文：「触控指令走 UDP 私有协议回传，信令走 WebSocket，二者分离，避免音视频流卡顿阻塞指令通道」）。SoulLink 现在 HTTP 串行「取帧 + 发指令」共用一条轮询，是延迟抖动的来源之一。
2. **编码标准选择**：H.264（兼容性最好、首屏秒开）→ H.265（省 30~40% 码率，有授权/兼容问题）→ AV1（码率最低但编码开销大、移动端硬解有限）。动态策略：服务端用 NVENC 同时出 H.264+AV1 两路，端侧按能力选；网络差先调码率档、不轻易切编码标准（切标准会触发解码器重建）。SoulLink 用 MF/NVENC MFT，对标 H.264 起步即可。
3. **低延迟编码是硬门槛**：CSDN 原文「缺省状态下的 NVENC 延迟可能超过 100ms，对云游戏完全不可用，必须显式开启低延迟配置」——与 SoulLink 已有 `OSS-REMOTE-RESEARCH §4.2` 的 Sunshine 低延迟参数结论完全一致。

### 3.4 云桌面协议（华为 HDP / 阿里 ASP）——「不是 RDP」的明确证据

- **华为 HDP（HUAWEI Delivery Protocol）**：官方公开「智能检测内容类型（普通文本/自然图像/视频/3D 图形）采用不同编码，端到端时延 <100ms、YUV444 真彩」。这是**按内容分区域自适应编码**的桌面流化协议，与 RDP 的「GDI 指令 + 位图缓存」思路不同。
- **阿里 ASP（Adaptive Streaming Protocol）**：官方文档「阿里云自研、面向应用流、端云协同、自适应流化、逐步替代老旧 HDX（Citrix）协议」。分层架构「算力层 / 传输协议层 / 终端接入层」。
- **结论**：连最「传统」的企业云桌面都不用 RDP（或用 RDP 也只是兼容层），而是自研协议。**RDP 在「低延迟游戏画面」这个场景下不是行业选择**——这反证了 SoulLink 在 RDP 会话内做 60fps 画面是逆势而行，应尽快验证 WGC 抓屏 + 硬件编码替代 BitBlt。

## 4. 收费模式 → 成本结构反推

| 产品 | 收费 | 反推的成本信号 |
|---|---|---|
| UU 远程 | 基础免费不限次 | 远程串流（路线 B）**无 GPU 采购成本**，只有带宽+研发摊销；免费可持续 → 说明「串流+键位映射」本身技术成本不高，主要成本在专网带宽 |
| 顺网云电脑 | 通宵包 3.98 元、按时计费 | 云电脑（路线 A）有 GPU 硬件成本，但**边缘节点多、单卡多路摊薄**，低价仍可盈利 → 说明「一卡多路 + 就近边缘」能把单用户成本压到极低 |
| 腾讯 START | VIP 29 元/月仅 15h（约 1.9 元/小时） | 云游戏 GPU 成本刚性，「限时」是为了控成本；小时单价高 → 说明「3A 云游戏单小时 GPU 成本」明显高于挂机场景 |
| 云·原神 | 600 米云币/小时 | 官方云游戏小时单价，反映「单用户 GPU 渲染 + 编码 + 带宽」的真实成本线 |
| 华为/阿里云桌面 | 按月（如 90 元/月 4U8G 起） | DaaS 桌面是「算力租售」逻辑，与挂机工具无关 |

**对 SoulLink 的关键结论**：**路线 B（远程串流）的收费极低甚至免费，恰恰证明「本机已有 GPU 的前提下，串流+键位映射」的边际成本几乎为零**——这给 SoulLink 一个强信号：**不要重造 GPU 云（成本高），把现有本机 GPU + RDP 会话内的抓屏编码链路做顺，就能以近乎零边际成本提供「远程控制」体验**。SoulLink 与 UU 的技术形态同属路线 B，UU 免费可持续，SoulLink 更不该在这条路上有大额技术投入。

## 5. 与 SoulLink 现有 RDP 架构的差异

| 维度 | 国内云厂商（路线 A） | 国内远控（路线 B） | SoulLink 现状 |
|---|---|---|---|
| 游戏跑在哪 | 云端 GPU 虚拟机/容器 | 用户自己的物理 PC | 本机 RDP 会话（多账号） |
| 多开本质 | GPU 虚拟化（vGPU/直通/容器） | 无多开（1 PC = 1 桌面） | **RDP 多会话（Windows 多用户/环回），OS 级桌面隔离** |
| 抓屏 | 真 GPU 桌面（DXGI/WGC/hook 全可用） | 真 GPU 桌面（DXGI/WGC 全可用） | **RDP 会话内：DXGI DDAPI 失败（E_OUTOFMEMORY）、BitBlt 22~31ms、WGC 待测** |
| 编码 | 硬件 NVENC/AMF/QSV/自研 | 硬件编码 | GDI+ JPEG 软编（`SessionRecorder.cs:343`） |
| 输入注入 | 虚拟机内注入（无 RDP 边界） | 本机驱动级/合成注入（console session，可用虚拟 HID） | **RDP 会话内 `mouse_event`/`SendInput`（带 INJECTED 标志；驱动级虚拟 HID 不可用）** |
| 传输 | 自研 UDP/WebRTC/边缘节点 | 自研 UDP/P2P/专网 | 局域网 HTTP（每帧请求 + `Task.Run`） |
| 延迟目标 | 30~80ms（边缘就近） | <100ms | 当前 100~600ms（估算） |

**三点硬差异（架构边界，需如实告知用户）**：
1. **抓屏边界**：云游戏/远控都在「真实 GPU 桌面」抓帧，所以 DXGI/WGC/硬件编码全通；SoulLink 在 RDP 会话内，没有真实桌面复制通道，DXGI DDAPI 已实测失败，**只能走 WGC（基于 DWM 合成层，待实测）或 BitBlt（已通但慢）**。这是 RDP 架构的固有边界，不是代码没写好。
2. **输入边界**：云游戏/远控可以挂虚拟 HID 驱动（console session），相对位移「无 INJECTED 标志、反作弊友好」；SoulLink 在 RDP 会话内 HID 设备不可见，**只能用 `mouse_event` 相对位移（带 INJECTED 标志）**，严格反注入的游戏会忽略（见 `OSS-REMOTE-RESEARCH §2.4`，已定案）。
3. **多开边界**：SoulLink 的「多账号」是 RDP 多会话，**不需要也不应该**做 GPU 虚拟化。多账号各自在 RDP 会话内跑游戏，SoulLink 只需对每个会话做「抓屏+编码+输入中继」，而不是把 GPU 切成多份——这比云厂商简单得多，但也被 RDP 会话的抓屏/输入边界卡住。

## 6. 能借鉴的具体做法（按优先级）

### 6.1 抓屏与编码（对齐 Sunshine 结论，国内产品再次印证）

| 做法 | 来源 | SoulLink 落点 |
|---|---|---|
| **WGC 抓屏优先于 BitBlt** | 全行业（含 Sunshine，见 `OSS-REMOTE-RESEARCH §3`） | RDP 会话内 `CreateForWindow`/`CreateForMonitor` 形态实测 `IsSupported()` + 抓 1 帧；成功则替换 BitBlt |
| **硬件编码替代 GDI+ JPEG 软编** | 云游戏全用 NVENC/AMF/QSV；「NVENC 缺省 >100ms，必须开低延迟」 | MF/NVENC MFT（`Mp4Writer` 已有 MF 经验），开低延迟 profile、关 B 帧、GOP 调大 |
| **无 B 帧 + 无限 GOP/按需 IDR + CBR + 丢旧帧** | Sunshine 参数 + 云游戏低延迟共识 | 已在 `OSS-REMOTE-RESEARCH §4.2` 定案，照做 |
| **视频流与输入指令通道分离** | CSDN「触控走 UDP、信令走 WebSocket，与视频分离」 | SoulLink 现有 HTTP 串行，中期改 WebSocket/DataChannel（已在 `STREAM-PERF-AUDIT §4.4/4.7` 列） |
| **动态编码：H.264 起步，端侧按能力降级，网络差先调码率不切标准** | CSDN 云游戏编码选型 | SoulLink MF 先 H.264；预留码率自适应 |

### 6.2 手机操作（UU 为重点的产品级设计清单）

> UU 远程 `/features/keyboard/` 官网公开功能清单（2026-11-22 抓取核对），与 SoulLink 已有 `VIRTUAL-CONTROLS-RESEARCH` 定案逐条对照。

| UU 公开功能 | 原文 | 对 SoulLink 的产品级要求 |
|---|---|---|
| **官方键位方案库** | 「超 300 款按键方案」「官方为各新老游戏提供专属键位方案，点击即用」；游戏页更新为「400 多款」 | **预设方案库是产品化核心**：SoulLink 至少内置主流游戏（原神/永劫/魔兽等）预设，且**官方持续维护**。仅靠用户自建布局，产品力差一截 |
| **分享码导入/导出** | 「复制分享码 / 输入分享码导入」 | 分享码 = `版本前缀 + gzip + base64url`（`VIRTUAL-CONTROLS-RESEARCH §5.3` 已定案），P0 无服务器可做 |
| **3D 视角控制** | 「支持左键、右键、中键按住滑动视角」「鼠标移动灵敏度、按住移动灵敏度、滚轮灵敏度可调」 | **滑动转视角 = 按住某键 + 相对位移**，与 SoulLink `moverel` 定案一致；**必须支持「按住右键/中键滑动」可选**（部分游戏相机拖拽需要） |
| **触屏 vs 鼠标指针双模式** | 「屏幕触控下点击直接调动鼠标至点击位置；鼠标指针下控制端始终显示鼠标，点击/移动作用在鼠标所在位置」 | **两种鼠标语义都要有**：触屏模式（点哪指哪=绝对定位+点击）与指针模式（相对移动）。SoulLink `move`/`moverel` 已覆盖两端，需在前端做模式切换 |
| **智能鼠标/防漂移** | 「可关闭智能游戏鼠标」「鼠标漂移、乱动可关闭智能游戏鼠标」 | 游戏锁鼠标时的「回中/防漂移」要可开关（SoulLink `RelayAgent` L711-714 已处理相对位移不回中，对应 UU 的「智能游戏鼠标」） |
| **显示鼠标自动隐藏按键** | 「显示鼠标时自动隐藏虚拟按键」 | 虚拟按键与鼠标指针的显示互斥策略（`VIRTUAL-CONTROLS-RESEARCH §5.2 global.hideWhenMouseVisible` 已列） |
| **锁定鼠标禁用点击** | 「锁定鼠标时禁用鼠标点击（防误触）」 | 射击类游戏锁鼠标时禁用画面点击（`global.disableClickWhenMouseLocked` 已列） |
| **一键多键/宏** | 「多个按键组合，一键顶多键」「编辑操作脚本，一键释放连招」「宏按键在功能键中选取」 | 数据模型支持组合键 + 宏 steps（`VIRTUAL-CONTROLS-RESEARCH §5.2 mode:macro` 已列） |
| **映射全键鼠** | 「支持映射全键鼠按键，包括小键盘、鼠标侧键」 | 键名表覆盖 NumPad + XButton1/2（已列） |
| **手柄直连 + 震动 + 虚拟手柄** | 「支持 XBOX、PS、小鸡、北通…」「手柄震动」「最多 4 个手柄」 | 手柄是**另一条输入线**（可选中期项），震动反馈是沉浸感加分项 |
| **编辑能力** | 「增减按键、调整大小/透明度/命名」 | 布局编辑 = 移动/缩放/命名/透明度（SoulLink `MOBILE-CONTROLS-DESIGN §4` 已设计） |

**UU 手机操作设计的三条「产品级」结论**：
1. **官方方案库 > 自建布局**。用户点名「UU 虚拟按键很好」，核心是「打开即用」——400+ 游戏官方键位，套用后微调即可。SoulLink 的 P0 若只有「用户自己拖按键」，上手门槛远高于 UU；**必须内置一批预设方案**（哪怕先 5~10 款热门游戏）。
2. **「屏幕触控 / 鼠标指针」双模式是转视角能否顺手的开关**。触屏模式 = 点哪指哪（绝对定位），适合点按；指针模式 = 相对移动，适合转视角。两者都要，且切换要一键。
3. **「滑动转视角 + 按住键滑动」是键鼠游戏在手机上的正解**，UU 明确做了「左/右/中键按住滑动」，证明这不是 SoulLink 的独创判断，而是被千万级用户验证过的行业标准。SoulLink 的 `moverel` 方向正确。

### 6.3 延迟目标与网络

| 做法 | 来源 | SoulLink 落点 |
|---|---|---|
| 端到端 RTT 预算：边缘节点 30~50ms，>80ms 明显拖滞 | CSDN 云游戏时延预算 | SoulLink 局域网应 <50ms；外网目标 <100ms（对齐桌面云 <100ms 口径） |
| 边缘节点/专网就近 | UU 300+ 节点、顺网 330+ 节点 | SoulLink 单机无边缘节点，**局域网 P2P 直连**即可，外网穿透靠用户现有方案（`MOBILE-REMOTE-PLAN` 已列） |
| 网络质量看抖动+丢包，不看平均 RTT | CSDN「平均 40ms 但抖动 >20ms 不如稳定 60ms」 | SoulLink 的 WebSocket/自适应码率应把「抖动」纳入降码率判据 |

## 7. 给 SoulLink 的 5 条具体建议（收口）

1. **不要做 GPU 虚拟化/云化（路线 A 不抄）。** SoulLink 是单机多账号工具，多账号靠 RDP 多会话即可，无需也不该投入数据中心 GPU 虚拟化。这条线成本高、与产品定位不符。
2. **抄路线 B 的「抓屏+编码+输入」内核，但正视 RDP 边界。** 唯一值得投的是「RDP 会话内 WGC 抓屏（替代 BitBlt）+ MF 硬件编码（替代 GDI+ JPEG 软编）」。这是把 22~31ms 提到 60fps 的唯一结构性机会，先花 1 小时写最小 WGC 探测（`OSS-REMOTE-RESEARCH §7 建议 2`）。
3. **输入注入没有捷径。** 云游戏/远控的驱动级虚拟 HID 在 RDP 会话内不可用，SoulLink 只能用 `mouse_event` 相对位移（已实现，接 HTTP 即用）。如实告知用户：严格反注入的游戏在 RDP 内无完美解。
4. **手机操作照 UU 抄，重点是「官方预设方案库 + 分享码 + 双鼠标模式 + 滑动转视角」。** 数据模型 `VIRTUAL-CONTROLS-RESEARCH §5.2` 已齐，P0 补「内置 5~10 款热门游戏预设 + 分享码导入导出」即可拉开与「自建布局」的体验差距。
5. **延迟目标定「端到端 <100ms」，别被厂商 <3ms/<10ms 宣传带偏。** 局域网场景应做到 <50ms；外网 <100ms。串流参数照 Sunshine/云游戏共识（无 B 帧、低延迟 tune、丢旧帧、视频与输入通道分离）。

## 8. 「查不到」的诚实声明

- **各产品服务端抓屏/编码/协议的具体实现**：顺网/达龙/腾讯 START/米哈游均**闭源，无公开技术白皮书细节**。只拿到「GPU 渲染 GPU + 串流 + 算力调度」「边缘节点数量」等营销口径。真正的协议细节（用 DXGI 还是 WGC、编解码参数、注入方式）查不到，也未做逆向。
- **UU 远程的编解码协议与延迟实现**：官网只有「4K 144 帧、500 Mbps、毫秒级」营销口径，无技术博客/API 文档。键位映射的**功能面**公开充分（§6.2 全部来自官网），但**布局文件格式、摇杆/滑动阈值、协议字段**查不到。
- **达龙云电脑**：官网极简（信息量少），技术细节、帧率/延迟/多开方式均未公开。百度百科/第三方评测在本次网络环境下检索被安全验证/泛化阻断，未拿到可靠实测。
- **顺网云电脑精确帧率/码率**：官方只给「高帧原生画质」「光追」定性，精确值未公开；「15~25ms」来自第三方实测转述，非官方承诺。
- **云·原神服务端架构**：官网仅「实时云端技术」；其网页版确用 WebRTC 播放（前端可观察），但服务端 GPU 虚拟化/编码细节未公开。
- **各远程控制（ToDesk/向日葵/RayLink）的虚拟摇杆/游戏键位映射**：普遍弱于 UU/Moonlight，公开资料只有「游戏键盘/手柄支持」一句，无键位映射的详细功能清单（这正说明 UU 在游戏键位映射上是差异化强项）。
- **知乎/CSDN 的原创技术深文**：知乎 403、CSDN 搜索页 JS 渲染，未能批量抓取；360/搜狗返回的 CSDN 云游戏架构文为「AI 创作分发」内容，**含错误风险，仅作行业共识交叉印证，不作单一事实源**。GPU 虚拟化三分类（直通/vGPU/API 转发）来自多篇公开文章一致表述，可信度高，但非任何产品官方文档。
