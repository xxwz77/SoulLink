# 三方案对抗性评审与唯一落地顺序

> 日期：2026-11-22；评审：kimi-reviewer；基线：SoulLink 3.3.19 当前源码。  
> 对象：STREAM-PERF-AUDIT v1.1、MOBILE-REMOTE-PLAN v1.2、WEB-EXTENSION-PLAN 当前版；交叉参考 CITATION-AUDIT-20261122.md。  
> 裁决口径：**通过**＝可按方案直接立项；**有条件通过**＝方向可取，但必须先满足本文条件；**驳回**＝核心路线或关键事实不成立。本文不改业务代码。

## 0. 一句话总评与唯一顺序

**三份方案都找到了真问题，但都不能原文照做：链路稿把推导当收益、手机稿一度漏掉协议接线、网页稿把完整安全产品塞进前置；最终只走“现有 HTTP 链路的可测量小改 → 手机与 BGI 只读 → 受控流程编辑”，WebRTC 不是必经路线。**

人日是有既有代码上下文的一名开发者的**粗估**，含验证，不是承诺；远端输入只保证已提交到代理，不能冒充游戏已接受。

### P0：先修并测量现有链路，不引入新媒体栈（合计 5~7 人日）

1. **安全门槛**：开启非 loopback 网页控制必须强制非空口令；校验主站写请求 Origin/CSRF，代理 CORS 改为主站精确 Origin；不开放公网端口映射。保留旧局域网只读体验的兼容开关，但不要默认匿名写入。
2. **测量与正确性**：给帧加 `frameSeq/capturedAt`，同序号返回 304 或跳过传输；用 `visibilitychange/pageshow` 恢复拉帧。按代理进程（`SoulLink.Agent.exe` 或对应 `--relay` 进程）与浏览器进程分别采 CPU，记录帧字节、实际新帧率、输入至新画面的 P50/P95，区分录制与观看开销。不要把代理内部静态类名当进程名。
3. **低成本体验**：保留 JPEG 和现有直连；网页自绘**预测光标**并在代理开关中关闭直播帧内光标，用固定光标图/热点；录制回放保留原光标。先不改采集线程结构。
4. **真正的按需**：`/api/list` 改为指定账号、限制条目/元数据；不得打开一个账号仍扫全部用户的录像目录。

**验收**：后台/回前台连续 20 次均自动恢复；同 `frameSeq` 不重复解码；30fps 动态操作与 10fps 背景均能正确点击、拖动、滚轮；无人请求时零新增网页网络请求；强制口令与 Origin 负例通过；每个观看者带宽 ≤ 同内容 30fps 全帧基线的 1/3（仅在内容、质量、分辨率一致时比较）；录制前后 N 秒内容无缺失。**没有同机测量数据，不宣称 CPU 降了多少。**

### P1：手机可用 + BGI 只读 + 经验证的变化区域实验（合计 9~15 人日）

1. **移动网页（4~6 人日）**：单指点/拖、双指滚轮、长按右键；触控板 `moverel`；IME 的 `text` 用 Unicode 成对发送并处理代理键/断线释放；横竖屏坐标；WiFi 切换后重取会话。manifest/图标可选，不做 Service Worker 缓存实时画面。
2. **BGI/流程只读（2~3 人日）**：`BgiLogCenter` 新增一致读取点，产出稳定白名单 DTO；summary/today 与有限日志/catalog 均用户触发；流程只读图用轻量 DOM/SVG，不重刻 WPF 画布。
3. **预览节流实验（1~2 人日）**：不改现有 Ring 回放采样，仅在代理保留最新预览帧，由观看请求限速到 5~10fps；验证它能减多少浏览器解码，而不是宣称省录制 CPU。
4. **脏矩形技术 spike（2~4 人日）**：比较同一抓帧的固定块，先做关键全帧 + 变化块 + 序号 + 丢块重同步，HTTP 实现即可；WebP 仅在现有 JPEG 基线上另测，依赖增量 >5MB 先停下询问。

**验收**：iOS Safari 与 Android Chrome 真机通过点击、中文、右键、双指滚轮、后台恢复；BGI 未绑定账号零新增 IO，无定时 BGI 请求，旧快照不被后续写入改变；脏矩形在真实 BGI 画面的带宽/代理 CPU 优于同内容全帧，且断线后能完整重同步。达不到就撤掉实验，不上 WebSocket 掩盖问题。

### P2：受控流程 JSON 编辑；其余重工程全部有门槛（合计 6~10 人日）

- 先做 WPF 草稿隔离，再做统一 `FlowEditService`：定义字段白名单、`editRevision`/If-Match、保留运行态、暂停后提交、备份与严格原子保存、审计。编辑默认关，危险动作需本机授权/二次确认；先 JSON/结构化表单，不做拖拽画布。
- **验收**：WPF/Web 同版本只有一个保存成功；412 不丢草稿；运行中编辑不改变当前扫描；保存/备份/审计失败均不假成功；恢复定义不回滚 RunComplete/游标；非法/未知字段、环、ReDoS、超长请求均被拒。
- **不在默认 P2**：Capacitor 原生壳、上架/后台保活、音频、剪贴板、多显示器、多人观看、TURN/WebRTC。仅在 P0/P1 的 P95 反馈延迟 >300ms、移动带宽或电池实测不达标，且小改无法达到目标时，单独立项。多显示器/原生壳等需求也可独立提前，但不得借“远程手感”混入性能项目。

## 3. 量化复算表

以下算术可复核；**算术正确不等于场景已实测**。统一用 1MiB=1,048,576 bytes、1KiB=1024 bytes。

| 断言 | 来源与独立复算 | 判定 |
|---|---|---|
| 30fps/q75＝4.8MB/s | 交接给的条件值 ⇒ 4.8MiB/s÷30＝**163.84KiB/帧**。若静止降频 1fps，同帧大小＝**0.16MiB/s**；10fps＝**1.60MiB/s** | **有条件可用，非固定基准**。必须以真实内容/分辨率/质量采样；不能拿 30fps 基线证明静止优化收益 |
| 每帧 7.9MB 位图 | 1920×1080×4÷2²⁰＝**7.910MiB** | **算术通过（估算）**；1920×1080 假设下成立，不等于每帧分配都等价于物理内存新增 |
| 30fps 采集 0.3~0.7 核 | 注释合并值 13~16ms×30÷1000＝**0.39~0.48 核**，只覆盖注释中一次 BitBlt+JPEG，不含全部步骤 | **待测**；实测每个代理进程、抓屏/转换/编码分项，不能用注释拼区间 |
| 浏览器 30fps 解码≈1 核；每观看者 +1 核 | 当前只有交接的定性/注释，无浏览器 Performance 采样；解码可能硬件/线程调度不同 | **待测**；按浏览器进程记录 CPU、掉帧、实际新帧率，禁止作为容量规划值 |
| 脏矩形带宽 4.8→0.5MiB/s、CPU -90% | 设变化面积 r、单位面积压缩率 k：动态带宽≈4.8×r×k + 协议开销。静止若已降至 1fps，则应从 0.16MiB/s 起比；编码省的是变化块，不是全屏 BitBlt/比较 | **存疑**；需真实挂机/游戏样本。完全静止可趋近零传输，但不是零采集 CPU |
| 本地预测光标间接省 3~6 倍 CPU/带宽 | 仅当预览从 30 降 10/5fps，**传输和浏览器解码理想比**为 3/6 倍；录制线程不变则代理 CPU 不随比例下降 | **有条件成立**；改为预览节流的算术上界，不称光标本身节省采集 |
| WS 带宽省 5~10% | 160KiB 帧的 5%＝**8192 bytes/帧**，10%＝16384 bytes/帧；普通 HTTP 请求+响应头通常远低于该数，且 keep-alive 已存在 | **驳回该收益数字**。WS 只在服务端主动推送、实测延迟/背压明显更好时选；当前无证据 |
| WebP -30%、动态自适应 -30~50%、WebRTC -50~80% | 无同图同主观质量/同网络测量；系数不可连乘。WebP 要额外编码器与依赖体积；WebRTC 还含编码、拥塞、丢包成本 | **待测，不能进入承诺**；产物 >5MB 必须询问，先测 JPEG 基线 |
| 1080p H.264 <1Mbps、端到端 <100ms、观看 10+ | 都是目标，不是从当前代码推出；RDP 会话 DXGI/硬编可用性未知 | **待 spike**；先验证采集，失败即终止，不做 WebRTC 全栈 |
| 当前“3 账号 10fps＝388GB/天” | 3×10fps×3600×24＝**864,000 帧/天**。388GB/天⇒约 **449KB/帧**；而 SessionRecorder 注释 126KB/帧⇒约 **106GB/天** | **历史数字场景不一致**，不能用作当前基线；不是本方案的新增优化收益 |
| BGI 尾窗数百 KB、CPU 近零 | 行数/字符预算可核，但实际 UTF-8 大小、物品/组数量未知；网页无请求时可做到零新增网页扫描，但不能把已有日志中心 CPU 算成零 | **部分可用**；用脱敏生产样本校准 DTO 字节、创建耗时与序列化稳定性 |

## 4. 风险 TOP3

| 排名 / 触发条件 | 后果 | 缓解与退出标准 |
|---|---|---|
| **1. 为“无人观看节能”停掉或降频录制采集** | 前 N 秒环形回放缺帧，事故取证失效；用户看到“性能提升”却丢核心功能 | Ring 录制与实时预览分离；任何降频只作用于预览。若用户要求无人也保留 30fps 回放，就承认采集 CPU 不能归零，不硬造“双分支近零” |
| **2. 空口令/CORS/共享 WebPassword 叠加流程或手机写控制** | 同链路或恶意网页可注入键鼠；流程能启动程序/结束进程，等同远程操作面，泄露后不可逆 | 非 loopback 写控制强制非空、精确 Origin/CSRF；流程编辑默认关，危险动作本机授权/step-up，审计后才开；公网不裸开。401/403/跨 Origin/重放全部有负例 |
| **3. 流程共享对象与快照共享引用被“只读/编辑”直接序列化或覆盖** | 调度读到半成品、运行游标/今日状态回滚、快照并发枚举异常；编辑门与 Scanned 预览还可能死锁 | WPF 草稿克隆 + 统一 revision/定义白名单事务；暂停流程再提交；数据中心在内部一致读取点构造稳定 DTO；压力测试含日志写入、调度、WPF/Web 同时读写 |

## 5. 遗漏项与需求边界

| 遗漏项 | 当前覆盖缺口 | 裁决 |
|---|---|---|
| **真正的输入反馈测量** | 三份都以帧率/带宽代替输入→远端可见反馈；无远端真实光标位置回传 | P0 必补 P50/P95；本地 CSS 光标只是预测，不能验收“远端已响应” |
| **无人观看与回放保真的产品选择** | “录制一直 30fps”与“无人采集近零”逻辑互斥 | 让用户选：保真持续 Ring / 节能低保真 Ring / 仅观看采集；默认不牺牲现有回放 |
| **多显示器、DPI、分辨率/旋转** | 当前抓屏是 `SM_CXSCREEN/SM_CYSCREEN`，输入按同一宽高；不是虚拟屏全坐标 | 明确 P0/P1 仅主屏；多显示器另立项，先采集 `SM_XVIRTUALSCREEN` 等实际边界再设计 |
| **音频与双向剪贴板** | 手机稿只列“以后/壳可提供”，网页稿未覆盖；远程控制没有这两项不等于完整 ToDesk | 不作为本期性能前置；需要时分别做音频采集/播放和受控文本剪贴板安全设计，不能用 WebRTC 一笔带过 |
| **断线后的输入安全** | 移动稿谈恢复取帧，但没把按下态、网络乱序、pointercancel、锁屏列成完整协议 | `session/generation + releaseall`、断线拒绝迟到输入、重连不补发旧点击；真机必须测 |
| **多人观看与控制权** | 链路稿的 1~2/5~10/10+ 无测量；未定义多人同时输入、观看者权限和背压 | 默认单控制者、只读观察者；有界帧队列和观看数上限实测后定，不承诺人数 |
| **移动端后台保活与耗电** | Capacitor 不能绕过 iOS 后台冻结；“可申请”不等于可长期直播 | 明确后台即暂停画面，回前台恢复；不承诺持续后台远程桌面，电池实测后才决定 APP 壳 |
| **录像回放列表仍然全量扫描** | 现有 `WebServer.cs:544-597` 对全部账号/条目扫目录和 meta，虽然按需触发但范围过大 | 纳入 P0：按 accountId + limit 查询，避免账号/历史增长后卡顿 |
| **Unicode 文本与高危节点的资源上限** | text 长度、请求体、代理键组合、正则 ReDoS、路径/进程操作未形成统一预算 | 移动端 text 设长度/速率上限；流程写设白名单、正则超时、危险动作确认与审计 |
| **部署与凭据轮换的可用性** | LAN HTTPS 证书、Tailscale 多地址 Origin、凭据轮换 UI 都需产品选择 | 在这些问题决策前，仅 loopback 或受控 LAN/Tailscale 验证；不把“用户自己配 TLS”当零成本 |

## 6. 评审后的硬约束

- 任何性能百分比都必须附：同机、同画面、同分辨率/质量、观看者数、是否录制、采样窗口、P50/P95。**缺一项就只叫目标/估算。**
- 新周期任务仍走 `TickHub`；网页按刷新/展开取数优先，不用新定时器解决同步。WPF 页面只切 Visibility，新增可见性逻辑必须走 `OnPageActivated/OnPageDeactivated`。
- 脏矩形/WebP/WS 均先保持旧 JPEG 回退；流媒体协议不得在代理任意增加端点而不同时更新 `WebDirect.IsAllowedPath`、鉴权与限流。
- 流程备份/审计写用户数据目录，不进 dist、不进包；任何新增依赖或产物 >5MB 先解释。以上均为设计与验收建议，本轮没有改业务代码、没有发版。
