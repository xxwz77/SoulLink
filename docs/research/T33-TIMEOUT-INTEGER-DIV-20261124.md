# T33 紧急：整数除法导致抓屏超时小于帧间隔，每帧必超时

> **这是我 T31 引入的 bug。** 你的判断完全正确。

---

## 0. 我错在哪

T31 我写了 `int ms = Math.Clamp(1000 / _fps, 8, 20)`。
三个问题叠在一起：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `1000 / _fps` 是**整数除法**：fps=60 → 16，而真实间隔 16.67ms | 超时比间隔小 0.67ms → **每帧都差一步** |
| 2 | 上限 clamp 到 20，fps=30 时间隔 33.33ms | 超时 20ms 远小于间隔 → 也必超时 |
| 3 | urgent 再减半（19/2≈9ms） | 更小于间隔 → urgent 补帧也拿不到新帧 |

**最讽刺的是**：T31 的注释里我自己写了「若超时远小于帧间隔…帧率实际减半」，
却在实现里用整数除法 + 过低上限，**正好造出了注释警告的那个场景**。

你给的日志证据是决定性的：
```
captureMs=16  acqMs=16   ← 恒等于 acqMs = 每帧都等满超时，从未拿到新帧
captureMs=7   acqMs=16   ← 偶尔拿到（DDA 恰好提前一点点）
```
**`captureMs` 恒等于 `acqMs` 就是「每帧必超时」的指纹。**

---

## 1. 修复

```csharp
// 旧（错）：整数除法 + 上限 20 + urgent 减半
int frameIntervalMs = 1000 / Math.Max(1, _fps);
int ms = Math.Clamp(frameIntervalMs, 8, 20);
if (InputTriggeredFrame) ms = Math.Max(4, ms / 2);

// 新（对）：浮点向上取整 + 余量，不因 urgent 缩短
int frameIntervalCeil = (int)Math.Ceiling(1000.0 / Math.Max(1, _fps));
int ms = Math.Clamp(frameIntervalCeil + 2, 8, 120);
```

**为什么 +2ms**：吸收调度抖动与 Windows 计时器精度（即使已 `timeBeginPeriod(1)`，仍非精确）。

### ★ urgent 不再减半 —— 你的提醒是对的

减半后 19/2≈9ms **小于 60fps 的帧间隔 16.67ms** → urgent 补帧同样拿不到新帧，
**等于把我刚修好的 bug 又引回来一次**。

urgent 的真正收益本来就不在缩短超时，而在另外两处（均未改变）：
1. **跳过 `WaitUntilNextSlot` 节拍**（`inputTrigger=true` 时短路求值）；
2. **`if (urgent) RequestKeyFrame()`** —— 让这一帧是 IDR，客户端 firstKey=false 时才收得下。

## 2. clamp 边界（三档都算清）

| fps | 真实间隔 | `Ceiling` | +2 后 | 超时 | 余量 | 判定 |
|---|---|---|---|---|---|---|
| **30** | 33.33ms | 34 | 36 | **36ms** | +2.67ms | ✓ |
| **60** | 16.67ms | 17 | 19 | **19ms** | +2.33ms | ✓ |
| **120** | 8.33ms | 9 | 11 | **11ms** | +2.67ms | ✓ |

**上限必须放宽**：
· 你建议放宽到 40（容纳 fps=30 的 36ms）—— 但 fps=15 需要 69ms，仍会被截断；
· 我取 **120**：fps=10 → 102ms ✓、fps=15 → 69ms ✓、fps=20 → 52ms ✓，全部通过；
· 正常 30~120fps 时实际取值只有 **11~36ms**，与原固定 100ms 相比已大幅缩短。

**唯一不覆盖的档位**：fps ≤ 9（间隔 ≥111ms 时 120ms 上限可能不够）。
但 `StreamFps`/`RecordFps` 现实中不会配到个位数，且低 fps 本身对延迟不敏感 —— **记录为已知边界，不再放宽**。
（无限放宽等于回到「静止时白等」的老问题，那是 T31 要解决的。）

## 3. 延迟推演

| | 修前（T31 的 bug） | 修后 |
|---|---|---|
| 单拍抓屏 | **恒定 16ms 等满 → 复用旧帧** | ~0.1~2ms 拿到新帧；静止时最多 19ms |
| 是否拿到新帧 | **否（每帧必超时）** | **是** |
| 延迟 | 逐帧累积 → 用户实测 **91ms / 136ms（5.5 / 8.2 帧）** | 回到 1~3 帧（**30~60ms**） |

**关键机理**：修前每一拍都「复用上一帧」，但 `_frameSequence` 不增长 → `desktopChanged=false`；
而 `inputTrigger` 让它仍然编码并**入队一帧重复画面** → 队列里堆的是**旧内容**，
客户端按序播放 → **延迟 = 队列长度 × 帧间隔**，逐帧累积。这与你观察到的「3 帧 → 9 帧」完全吻合。

## 4. 你要求评估的：T26 的 `if (urgent) RequestKeyFrame()` 是否也在拖慢？

### 结论：**不是本次延迟恶化的原因，但确实值得收紧。**

**先排除嫌疑**：

| 论证 | 依据 |
|---|---|
| `captureMs` 恒等于 `acqMs` 是**确定性**现象 | 整数除法是编译期常量计算，与 IDR 毫无关系 |
| IDR 只影响**单帧体积与编码耗时**，不改变「拿不到新帧」这件事 | 超时判断发生在抓屏层，早于编码 |
| 若 IDR 是主因，`captureMs` 应偏高但**不恒定等于 `acqMs`** | 实测是恒定相等 |

**所以真凶是整数除法，不是 IDR。** 先修那个。

### 但 IDR 的频率确实值得讨论

现状：`RequestKeyFrame()` 内部有 **200ms 进程内节流**（我 T26 时加的 `KeyFrameMinIntervalMs`），
即**最坏 5 次 IDR/秒**。

**实际频率**：人手快速拖动松手，每次间隔约 300~800ms → **每次都会触发 IDR**（都 > 200ms）。
连拖 5 次 ≈ 5 个 IDR / 3 秒 ≈ 1.7 次/秒。

| 代价 | 程度 |
|---|---|
| 带宽 | IDR 体积是 P 帧 5~10 倍 → 短时带宽尖峰 |
| 编码 | NVENC 重建 GOP，单帧耗时上升 |
| 浏览器 | 正常处理 IDR 是常规操作，**不会重建解码器** |
| 关键 | **IDR 不会拖慢后续帧** —— 编完即结束 |

### 我的建议：**加一个「距上次 IDR < 1s 则不重复」的启发式**（但我没改）

理由：
· **服务端确实不知道客户端的 `firstKey` 状态**，所以只能启发式；
· 但「1 秒内已经发过 IDR」时，客户端**几乎必然已经拿到**（除非它在这 1s 内刚连上）；
· 而 `RequestKeyFrame` 已有的 200ms 节流**太短** —— 它防的是「同一瞬间的风暴」，
  防不住「连续松手每次都来一个」；
· 改成 1s 可把最坏 IDR 频率从 5 次/秒 降到 1 次/秒，代价是：极少数情况下
  「用户在 1s 内连松两次，第二次不升级 IDR」—— 但此时客户端 firstKey 早已为 true，
  **P 帧完全够用**，没有实际损失。

**我没有改这一处**，因为你要求「至少给出分析，不一定要改」，且改动会在 200ms 语义上叠加一层，
**建议单独一个任务验证**（比如先把整数除法修复部署、确认延迟回到 1~3 帧，再决定要不要收紧 IDR）。
避免同时改两处，万一延迟仍有问题无法归因。**这也是我这次该学的教训**（见 §6）。

## 5. 顺带加的「安全网」：让这类 bug 不再静默复发

**为什么加**：这个 bug 在日志里的唯一特征是「`captureMs` 恒等于 `acqMs`」，
**极难一眼看出**，只能靠用户感知到「延迟变大」才被发现 —— 这种检测方式太晚、代价太大。

新增 `IsAcquireTimeoutSane()` + 每拍断言：
```csharp
if (!ddaForTrigger.IsAcquireTimeoutSane() && _lastSaneWarnAt != fps)
{
    _lastSaneWarnAt = fps;
    RelayAgent.LogQuiet("[video] 警告：抓屏超时 <= 帧间隔（fps=" + fps
        + ", acqMs=" + ddaForTrigger.LastAcquireTimeoutMs
        + "）→ 会每帧必超时、只能复用旧帧，画面延迟会逐帧累积");
}
```
判据就是 `CurrentAcquireTimeoutMs() > 1000.0/fps`。**成本是几次浮点比较**，可忽略；
一旦配置不自洽，日志立刻可见，不必等用户报「卡」。

## 6. 我该吸取的教训（说清楚，不只是修完就算）

T31 那次改动我犯了三个错：
1. **整数除法未审查** —— `1000 / 60` 这种写法在「必须大于某值」的语义里天然危险；
2. **注释与实现自相矛盾** —— 注释警告「超时远小于帧间隔会丢帧」，实现却造出了这个场景；
3. **clamp 上限拍脑袋定 20** —— 没有逐档验证 fps=30 是否够用。

**共同根因**：我没有把「超时 vs 帧间隔」这个**关键不等式**写成可执行的断言，
只写在了注释里。注释不会报错，断言会。所以这次补了 `IsAcquireTimeoutSane()`。
