## 1. 四类定义与用户原话依据

### 1.1 四类体系（category 枚举，取值即落库值）

| category（落库值） | 中文名 | 定义 |
|---|---|---|
| `legendary_elite` | 传奇精英 | 高价值精英怪：摩拉值 ∈ {800, 1200, 3000}，或 600 且路线名含「传奇」 |
| `elite` | 普通精英 | 精英怪：摩拉值 ∈ {200, 400, 600}（600 须先排除传奇） |
| `legendary_minion` | 传奇小怪 | 除传奇精英/普通精英以外的击杀获取，且摩拉值 > 150 |
| `minion` | 小怪 | 其余（摩拉值 ≤ 150） |

### 1.2 用户原话依据（2026-11-25 定稿，逐字保留）

- 四类体系：「传奇精英（legendary_elite）/ 普通精英（elite）/ 传奇小怪（legendary_minion）/ 小怪（minion）」
- 小怪定义：「小怪 = 除传奇精英与普通精英以外的击杀获取；其中 >150 者为传奇小怪。」
- 击杀数：「击杀数不算，按1来，小怪算法太麻烦。」→ **kill_count 恒为 1**，不做倍率换算。
- 汇总口径：「传奇精英 3 次 = 3 条记录，不是 3 只怪」→ 字段用 `record_count`；若保留 `kill_count` 必须注释「恒 1、等同记录条数」。

### 1.3 数据来源模型（重要：两个来源，不是同一个）

归类需要两个原始字段，它们**来自两个不同的系统**：

| 字段 | 来源 | 精度 | 说明 |
|---|---|---|---|
| `mora_value`（摩拉数值） | **米游社「旅行者札记」摩拉获取记录**（monthDetail 逐条） | 数值（整数） | 一条 = 一次获取，含时间 / 获取途径 / 获取数量 |
| `route_name`（路线名） | **BGI 日志**（进入路线循环 / 脚本执行结束） | 时间到秒 | 用于 600 歧义消解 + 归属到具体路线 |

**为什么是两个来源**：BGI 日志里**没有**「击杀怪物奖励 600」这种逐条摩拉值（只读核实：20261124.log 全文 grep 无「击杀怪物奖励」锚点，只有「精英0，小怪0」计数头 L2425/L5449）；逐条摩拉值在米游社札记里。所以：

- **摩拉值 + 获取途径 + 时间（分钟）** ← 米游社札记 monthDetail（截图实证字段：`时间`/`获取途径`/`获取数量`，获取途径 = 「击杀怪物奖励」）。
- **路线名 + 路线起止时间（秒）** ← BGI 日志（进入路线循环 route=… / 脚本执行结束）。
- **两者靠「时间窗口」做分钟级 join**：把米游社札记某分钟的击杀记录，归属到「覆盖该分钟的 BGI 路线」上（见 §7.3）。

由此确定的硬事实（写入本规则，不再是「假设」）：

1. **逐条摩拉记录确实存在**（一条 = 一次获取，三字段：时间/获取途径/获取数量）。
2. **时间精度到分钟**（13:40 / 13:38），**没有秒**。
3. **同一分钟可以有多条记录**（13:37 两条、13:38 三条）→ 不能用时间去重、不能假设「一分钟一条」。
4. **真实数值分布**：既有 600 这种大值，也有 38 / 40 / 45 这种远低于 150 的小值（印证「枚举值 + 小怪」假设，小值落规则 6 → minion）。
5. **获取途径字段 = 「击杀怪物奖励」**（摩拉 Tab 下基本都是击杀来源，原样落库，未来可用于排除非击杀来源）。
6. **数据延迟约 1 小时** → 拉取与「和 BGI 日志对账」都要考虑滞后，当天最新时段可能拉不全。
7. **札记只统计非充值获取** → 不会混入氪金流水。

### 1.4 参考实现佐证与「单次数值」关键洞察（来自 Lead 拆包核对）

一个已落地的同类参考项目（Morale 页 + MysAccounts 页）提供了三点直接佐证：

1. **档位表与用户规则完全一致**：参考实现原文字段 `amount_label: "200 / 400 / 600 / 800 / 1200 / 3000"`，描述「单次击杀奖励精确命中固定档位时，统一纳入精英怪收益」；小怪 = 「除固定精英档位外的其他**正数**击杀奖励」。→ 印证用户 v4 的枚举表，且确认「其他正数」归小怪（对应本规则 §2 规则 5/6）。
2. **数据模型含 `single_morale`（单次摩拉）+ `count`（次数）+ `morale`（该类总额）**。→ 与本规则「一条记录 = 一次击杀、kill_count 恒 1」吻合；`count` 语义 = 记录条数，与 §5 汇总口径可直接对齐。
3. **精英怪内部再分「普通/中级/高级」三档**是参考项目的额外细分，用户没要求，**本规则不做**。

**★ 必须用真实数据回答的关键问题（决定 600 消解是否还需要路线名）**：

- 若米游社 monthDetail 真实返回里**有 `single_morale` 字段**（单次击杀的摩拉值），那么「600 到底是 600×1 还是 200×3」在**数据层就消解了**——`single_morale` 就是单次数值，`count` 就是次数，600 就真的是「单次 600」（走 §2 规则 2/3/4 消解歧义），**路线名判别的必要性大幅下降**。
- 若真实返回里**只有 `action + num`（总额或单条），没有 single_morale/count 拆分**，则「600」仍可能是多只怪合并值，**必须靠路线名**（§2 规则 2/3）。

→ 这条已列入 §7.1 校准项 4，**t18 的第一优先级是确认 monthDetail 返回里有没有 `single_morale`/`count` 字段**。

## 2. 判定表与优先级

判定**自上而下，命中即止**（第一条命中的规则决定类别，不继续往下）。

| 优先级 | 条件 | 结果 category | 说明 |
|---|---|---|---|
| 1 | `mora_value ∈ {800, 1200, 3000}` | `legendary_elite` | 传奇精英的固定值，**不看路线名** |
| 2 | `mora_value == 600` 且 `route_name` 含「传奇」 | `legendary_elite` | 600 是歧义值，靠路线名里的「传奇」判传奇精英 |
| 3 | `mora_value == 600` 且 `route_name` 含「精英」且**不含**「传奇」 | `elite` | 600 + 路线名只标精英 |
| 4 | `mora_value ∈ {200, 400, 600}`（其余情况） | `elite` | 普通精英固定值；600 若路线名既不含传奇也不含精英也落这里 |
| 5 | `mora_value ∉ {200,400,600,800,1200,3000}` 且 `mora_value > 150` | `legendary_minion` | 大于 150 的「非精英标准值」都是传奇小怪 |
| 6 | 其余（`mora_value ≤ 150`） | `minion` | 兜底：小怪 |

### 2.1 优先级关键点（易错处）

1. **规则 2 先于规则 3**：路线名同时含「传奇」和「精英」时（如「传奇精英」），先命中规则 2 → `legendary_elite`。
2. **规则 1 不看路线名**：800/1200/3000 无论路线名是什么都判传奇精英。
3. **规则 4 是 200/400/600 的兜底**：600 只有在规则 2、3 都没命中（路线名既不含「传奇」也不含「精英」）时才由规则 4 判 `elite`。
4. **规则 5 的「其余情况」= 不在这六个值里且 >150**：例如 250、900、1500、5000 都 → `legendary_minion`。
5. **规则 6 兜底 ≤150**：真实截图已出现 38/40/45 这类小值，落此规则。

## 3. 伪代码（实现者可直接照抄）

### 3.1 分类函数（C# 风格，可直接照抄逻辑）

```csharp
// category 枚举：LegendaryElite / Elite / LegendaryMinion / Minion
// 常量：当前规则版本
public const int RuleVersion = 4;

// 精英标准值集合（legendary_elite 与 elite 共用的固定摩拉值）
private static readonly HashSet<long> EliteValues = new() { 200, 400, 600, 800, 1200, 3000 };
private static readonly HashSet<long> LegendaryEliteValues = new() { 800, 1200, 3000 };
private static readonly HashSet<long> NormalEliteValues = new() { 200, 400, 600 };

public static MoraCategory Classify(long moraValue, string routeName)
{
    string route = routeName ?? "";

    // 规则 1：传奇精英固定值（不看路线名）
    if (LegendaryEliteValues.Contains(moraValue))
        return MoraCategory.LegendaryElite;

    // 规则 2：600 + 路线名含「传奇」
    if (moraValue == 600 && route.Contains("传奇", StringComparison.Ordinal))
        return MoraCategory.LegendaryElite;

    // 规则 3：600 + 路线名含「精英」且不含「传奇」
    if (moraValue == 600 && route.Contains("精英", StringComparison.Ordinal)
        && !route.Contains("传奇", StringComparison.Ordinal))
        return MoraCategory.Elite;

    // 规则 4：普通精英固定值（200/400/600 兜底）
    if (NormalEliteValues.Contains(moraValue))
        return MoraCategory.Elite;

    // 规则 5：>150 且不在精英标准值集合 → 传奇小怪
    if (!EliteValues.Contains(moraValue) && moraValue > 150)
        return MoraCategory.LegendaryMinion;

    // 规则 6：兜底 ≤150 → 小怪
    return MoraCategory.Minion;
}
```

### 3.2 等价的逐条 if 写法（不含集合，便于阅读/移植到 SQL）

```
if value in (800, 1200, 3000):            return LegendaryElite   # 规则1
if value == 600 and '传奇' in route:     return LegendaryElite   # 规则2
if value == 600 and '精英' in route and '传奇' not in route:
                                          return Elite           # 规则3
if value in (200, 400, 600):             return Elite           # 规则4
if value not in (200,400,600,800,1200,3000) and value > 150:
                                          return LegendaryMinion # 规则5
return Minion                                                     # 规则6（≤150）
```

### 3.3 备注：字符串匹配口径（待 t18 确认，见 §7）

- 「传奇」「精英」匹配目前按**全角中文字面量**、`StringComparison.Ordinal`（区分大小写但中文无大小写）做子串包含。
- 是否要处理「繁体/异体」、半角/全角差异，属 t18 校准点，**本规则暂不额外处理**，实现者先按直译匹配，留好扩展点。

## 4. rule_version 机制与重算策略

### 4.1 为什么要有 rule_version

归类规则会迭代（当前 v4；未来可能 v5/v6）。若只存「结果 category」不存「判定用的原始输入 + 当时版本」，规则升级后历史数据就变成「按旧规则算的、无法追溯、无法重算」的死数据。

### 4.2 落库字段（每条摩拉记录）

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `mora_value` | INTEGER | 米游社札记「获取数量」 | 原始摩拉数值（**必须保留原始值**，是重算的唯一依据之一） |
| `single_morale` | INTEGER | 米游社札记（**若返回**） | 单次击杀摩拉值；**若 monthDetail 返回此字段，优先用它做 §2 判定**（600 消解不用路线名）；缺省则回退用 `mora_value` + `route_name` |
| `count` | INTEGER | 米游社札记（**若返回**） | 该条记录对应的次数；语义 = 记录条数（与 §5 一致，kill_count 恒 1 的同一口径） |
| `route_name` | TEXT | BGI 日志（join 所得） | 归属路线名（**必须保留原始值**，600 歧义消解依据） |
| `acquire_way` | TEXT | 米游社札记「获取途径」 | 原样落库（如「击杀怪物奖励」），未来可用于排除非击杀来源 |
| `acquire_minute` | TEXT | 米游社札记「时间」 | 分钟精度，如 `2026-11-25 13:40`（**无秒**） |
| `category` | TEXT | 派生 | legendary_elite / elite / legendary_minion / minion |
| `rule_version` | INTEGER | 派生 | 判定时使用的规则版本（当前 = 4） |
| `kill_count` | INTEGER | 常量 | 恒 1（若保留此字段，**必须注释「恒 1、等同记录条数」**；见 §5） |

### 4.3 重算策略（规则升级时）

1. `classify(mora_value, route_name)` 必须是**纯函数**且版本化（当前实现返回 v4 结果）。
2. 规则升级 = 只改 `Classify` 函数体 + 把 `RuleVersion` 常量 +1。
3. 重算 = 一条 SQL 单遍扫描，把「`rule_version < 当前版本`」的记录**重新调 `Classify(mora_value, route_name)` 更新 `category` 和 `rule_version`**。
4. **不需要重新解析日志、也不需要重新拉米游社**（因为 `mora_value` + `route_name` 已落库），也不删除旧结果（更新覆盖即可）。
5. 若历史记录缺 `mora_value` 或 `route_name`，则**无法重算**，只能标记 `category='unknown'` 或保持旧值 + `rule_version` 不变——这是为什么 §4.2 强调原始输入必须落库。

### 4.4 版本记录建议

- 文档头部 `rule_version = 4`；代码里一个 `RuleVersion` 常量；落库字段同名。
- 每次改规则，在本文档末尾 changelog 追加（版本号、改了什么、谁确认）。

## 5. 汇总口径（记录条数，非击杀数）

### 5.1 用户裁定

「击杀数不算，按1来，小怪算法太麻烦。」→ **`kill_count` 恒为 1**，不做任何倍率换算（不管一条记录背后实际打了几只怪）。

### 5.2 字段命名

- 汇总字段用 **`record_count`**（= 记录条数）。
- 若实现保留 `kill_count` 字段，**必须加注释「恒 1、等同记录条数」**，否则后续读者会误以为在做击杀倍率。

### 5.3 汇总 SQL 口径

```sql
-- 按类别汇总：直接数记录条数，kill_count 恒 1，不参与倍率
SELECT category, COUNT(*) AS record_count
FROM mora_kill_record
WHERE account = $account AND route_id = $route_id   -- 或按任意聚合维度
GROUP BY category;
```

- 「传奇精英 3 次」= 该类别 3 条记录，**不是** 3 只怪。
- 任何展示/报表都只显示 `record_count`，不展示 `kill_count` 的累加（它恒等于记录数，无信息量）。

## 7. 待 t18 校准的假设（真实数据验证清单）

> 已由截图实证的硬事实已写进 §1.3，**不再列为「待验证」**。以下仅列「仍需用全量真实数据校准」的点。

### 7.1 关于「数值」字段

1. `mora_value` 的来源已确认 = 米游社札记 monthDetail 的「获取数量」列（截图实证）。仍需校准：**全量数据的数值频次表**——标准值集合 {200,400,600,800,1200,3000} 是否真是「全部」精英/传奇精英取值，还是只是高频子集（若发现 700 之类，规则 5 会把它错判成 legendary_minion）。
2. 数值是否恒为整数，是否会出现小数、负值、缺失；若出现，占比多少（截图未覆盖，需全量）。
3. 38/40/45 之外，小怪值是否还有 50/60/70/80… 等其它取值（真实频次表由 t18 用全量数据给出）。
4. **★ 第一优先级：monthDetail 真实返回里有没有 `single_morale`（单次摩拉）+ `count`（次数）字段**（参见 §1.4）。有 → 600 消解走数据层、路线名判别降级为可选；无（只有 action+num）→ 必须靠路线名（§2 规则 2/3）。这一条直接决定「路线名字段是否必须」和「归属算法的复杂度」。

### 7.2 关于 600 的歧义消解

4. 路线名是否**稳定**含「传奇」「精英」字面量（全角中文）；有没有写成「传说」「精英怪」「菁英」等变体导致规则 2/3 漏匹配。
5. 「传奇精英」这类同时含两词的路线名实际占比，验证规则 2 先于规则 3 是否符合真实语义。
6. 600 且路线名既不含传奇也不含精英（落规则 4 → elite）的真实占比，判断是否需要更多歧义信号。

### 7.3 关于归属算法（分钟窗口 join）—— 本节的硬约束

截图已确认「米游社札记时间精度到分钟、同一分钟可多条」。因此归属算法**必须按分钟窗口设计**，并接受以下约束：

7. **join 键 = 分钟**：米游社札记 `acquire_minute`（如 `13:40`）→ 匹配 BGI 路线时间窗口（进入路线循环 route=… 到 脚本执行结束，秒级）覆盖到 `13:40:00 ~ 13:40:59` 的那条路线。
8. **同一分钟内多条记录无法再细分先后**：13:38 有 600/38/45 三条，它们都落在同一分钟，米游社没给秒 → 若该分钟内只有一条 BGI 路线，则三条都归它；**若该分钟内有多条路线切换，则无法确定每条属于哪条路线**（只能：a) 全部归该分钟「占时长最长」的路线，b) 或全部标 `route_name='(分钟重叠)'` 待人工，二选一由 t18 定，并作为已知误差写进实现）。
9. **时区/时钟偏差**：米游社札记时间（服务端，UTC+8）与 BGI 本地日志时间（本地，UTC+8）可能有分钟级偏差；且札记「数据延迟约 1 小时」。join 前需确认两边时区一致，且**当天最新 ~1 小时的记录可能拉不到**，归属时不能用「BGI 有路线但米游社没记录」判为无击杀。
10. **归属失败的兜底**：米游社有摩拉记录、但对应分钟在 BGI 里没有打开的路线窗口（BGI 没跑 / 日志缺失 / 时间对不上）→ `route_name` 置空、`category` 仍按 `Classify(mora_value, "")` 算（600 会落 elite），并额外标记 `unattributed` 供排查。
11. **「精英0，小怪0」预标注旁证**：BGI 日志 `当前组 路径组1 共 5 条路线，精英0，小怪0`（20261124.log L2425/L5449）可作路线级精英/小怪预标注的旁证，但**逐条摩拉值的归属仍须走米游社札记 × BGI 分钟 join**，二者口径不同，不能互相替代。

### 7.4 关于匹配率与规则有效性

12. 用全量真实数据跑一遍 `Classify`，统计四类分布是否合理、`minion` 是否兜底吞了过多本应判为精英/传奇的记录（匹配率）。
13. 规则 5 的 >150 阈值是否与真实「传奇小怪」摩拉下限吻合（真实数据里传奇小怪的摩拉区间）。
14. `kill_count` 恒 1 的口径下，是否需要额外保留「某分钟某路线击杀了几只」的原始计数供未来规则升级（若规则文档外的展示需要，另议，不属于本任务）。

### 7.5 结论

在 t18 校准完成前，**本规则 v4 按 §3 伪代码原样实现即可**；归属算法先按 §7.3 的分钟窗口 join + 重叠兜底实现。校准若发现假设不成立，按 §4 走 rule_version 升级重算，不动已落库的 `mora_value`/`route_name`/`acquire_way`/`acquire_minute` 原始输入。
