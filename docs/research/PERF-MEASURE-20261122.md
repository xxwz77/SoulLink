## 0. 一句话总结

之前所有性能文档里的量化数字，除了 `PERF-3.3.4` 那次的「空闲约 16% 单核」和几处代码注释，
**其余全是估算，没人真的量过**。本文配一个**纯只读**的采样脚本，让用户自己在生产挂机态下量出：

| 要量的东西 | 脚本给什么 | 用来验证哪条结论 |
|---|---|---|
| 瞬时 + 平均 CPU% | 每个进程的中位/均值/P95/峰值 + 寿命平均基线 | 「0.3~0.7 核/账号」「空闲 16%」 |
| TCP 逐连接收发字节 | 按进程归集的 MB/s | 「30fps/质量75 ≈ 4.8 MB/s」 |
| 工作集、句柄数 | WorkingSet64 + `GetProcessHandleCount` | 句柄是否泄漏 |
| 有人看 / 没人看 | 按发送速率自动分组对照 | 「采集侧不看有没有人看」 |

**测量方法上的铁律**（交接文档 §6.4 记过一次 279% 假数据事故）：
差分采样必须**成对 `$p.Refresh()`**，并且必须用「进程总 CPU ÷ 存活时长」交叉验证。
脚本把这两条都做成了硬性自检 —— 不满足就明确报错，而不是给你一个好看的假数字。

## 1. 怎么跑

### 1.1 最常用：量当前正在挂机的实例

```powershell
# 在主程序 + 代理都在跑的时候，采样 60 秒（默认值）
pwsh -File scripts\measure-soullink-perf.ps1
```

它会自动找到**主程序**（`SoulLink`）和**所有代理**（同进程名的 `--relay`、
或独立文件名 `SoulLink.Agent.exe`），不需要你手动填 PID。

### 1.2 完整参数

```powershell
pwsh -File scripts\measure-soullink-perf.ps1 `
     -Seconds 60 `          # 采样时长（秒），默认 60
     -IntervalMs 1000 `     # 采样间隔（毫秒），默认 1000
     -ProcessName SoulLink` # 进程名，不含 .exe
     -Csv out\perf.csv `    # 可选，导出逐采样点明细
     -Label "30fps-有人看"  # 可选，写进 CSV 的标签
```

另有三个给排障用的参数：`-ProcessId`（只量指定 PID）、`-ConfigPath`（显式指定 config.json）、
`-WatchingThresholdMBps`（判定「有人在推帧」的阈值，默认 0.05）。

### 1.3 三组对照实验（**这才是把估算钉死的关键**）

单次采样只能得到一个状态下的数字。要验证「有人看 vs 没人看」的差异，必须**成对**跑：

```powershell
# ① 无人观看态（关掉所有网页，账号照常挂机/录制）
pwsh -File scripts\measure-soullink-perf.ps1 -Seconds 180 -Label idle -Csv out\idle.csv

# ② 有人观看态（打开网页实时画面，让它持续刷新；最好拖动窗口制造画面变化）
pwsh -File scripts\measure-soullink-perf.ps1 -Seconds 180 -Label watching -Csv out\watching.csv
```

两次的 `-Seconds` 建议 ≥120 秒：太短会被启动期开销和一次 GC 带偏。

## 2. 这个脚本量什么（以及为什么这么量）

### 2.1 五项指标

| 指标 | 来源 | 口径 |
|---|---|---|
| 瞬时 CPU% | `Process.TotalProcessorTime` 差分 | **单核百分比**，可 >100 |
| 寿命平均 CPU% | 同上累计值 ÷ `StartTime` 至今 | 交叉验证基线 |
| 工作集 | `Process.WorkingSet64` | 瞬时物理内存 |
| 句柄数 | `GetProcessHandleCount`（kernel32） | 单次系统调用 |
| 网络收发 | TCP eStats `DataBytesOut/DataBytesIn` | **TCP 载荷字节**，不含 IP/TCP 头 |

### 2.2 为什么句柄数必须走 `GetProcessHandleCount`

`AGENTS.md` 性能约束第 3 条：`Process.HandleCount` **每次 3~5ms**，挂在 1Hz 循环里
**它自己就吃掉 20% CPU** —— 也就是说，用错 API 的测量工具会污染被测对象，
量出来的 CPU 里有五分之一是测量者自己。

脚本用 `Add-Type` 声明 `kernel32!GetProcessHandleCount` + `kernel32!OpenProcess`，
用最小只读权限 `PROCESS_QUERY_LIMITED_INFORMATION (0x1000)` 打开、读完立刻 `CloseHandle`。
**声明失败就跳过该项并明确标注「不可用」，不退化成正则解析 `netstat` 或反射慢路径**
（那只会得到又慢又错的数据）。

### 2.3 ★ 为什么网络字节不能从 `GetProcessIoCounters` 取（这是个真坑）

直觉上「进程发送了多少字节」应该看 `GetProcessIoCounters`。**实测证明不行。**

本次自测做了一次对照（见 §5.1）：让一个子进程经 loopback 发送 **12.8 MB**，
同时读它的 IO 计数器：

```
SOCKET: drained=12844800 bytes
SOCKET: child WriteTransfer=1334  OtherTransfer=576002
        WriteOps=4  OtherOps=3052
```

`WriteTransferCount` 只有 **1334 字节**，与真实的 12.8MB 差了四个数量级。
原因：Windows 的 IO 计数器统计的是**文件/设备 I/O 管理器**路径，socket 走的是
`afd.sys` + TDI/WSK，**不经过 IoCounters**。

所以脚本改用 TCP 层：`GetExtendedTcpTable`（拿到「每条连接属于哪个 PID」）
+ `GetPerTcpConnectionEStats`（拿每条连接的**累计**收发字节），
按 PID 归集后做差分 → 得到真正的 MB/s。

同一轮的验证：发送端发 8,388,608 字节，接收端实收 8,388,608 字节，
eStats 读到 `DataBytesOut=8,388,648`（差 40 字节 = 40 个 TCP 段头的统计口径差，误差 ≈ 5ppm）。

**代价与限制**（要如实告诉你）：

- 只覆盖 **IPv4**。IPv6 的 `GetPerTcp6ConnectionEStats` 在本机对 TCPv6 连接
  稳定返回 `1214 (ERROR_INVALID_PARAMETER)`，实测换 8~200 字节各种 ROD 尺寸、
  以及地址字节序两种变体都失败。所以走 IPv6 的连接**不计入速率**。
  SoulLink 的网页/代理都是 IPv4 `127.0.0.1` / 局域网 IPv4，不受影响。
- 只能读到**已 ESTABLISHED** 的连接。已关闭的连接不保留统计，
  所以「刚才那一阵突发流量」不会在事后被补算进来 —— 必须在流量发生**当时**采样。
- 连接重建（换端口重连）会让累计值回退，脚本按 0 处理并记录，不会算出负速率。

### 2.4 工作集与句柄：只做参考，不做定性

`AGENTS.md` 性能约束第 4 条说得很清楚：**句柄增长要观察 >15 分钟才能定性**。
所以脚本的默认 60 秒采样只能告诉你「现在有多少句柄」，**不能**据此判断泄漏。
要查泄漏就用 `-Seconds 1000` 跑十几分钟看趋势，或者对比两次运行的均值。

## 3. 「有人观看 / 无人观看」怎么区分（这是被问到的重点）

**`/live` 有没有被请求，是代理进程的内部状态，只读手段观测不到。**
不能去 attach 调试器、不能读目标进程内存（既违反只读约束，也不现实）。

脚本采用**可观测的等价判据**：

> 有人在看 → 代理必然在持续向外发送 JPEG 帧 → 代理的 TCP 发送速率显著 > 0。
> 没人看 → 采集循环照跑，但没有 socket 写出 → 发送速率 ≈ 0。

判据落在 CSV 的 `State` 列（`watching` / `idle`），阈值默认 **0.05 MB/s**
（可用 `-WatchingThresholdMBps` 调整）。汇总里按这个分组给出两行对照。

### 3.1 这个判据的边界（务必知道）

| 情形 | 判据表现 | 结论 |
|---|---|---|
| 网页开着、画面在动 | 发送速率高 → `watching` | 正确 |
| 网页开着、画面长期静止（前端「静止降频」降到 1fps） | 发送速率很低，可能 < 阈值 → 误判成 `idle` | **会低估「有人看」的占比** |
| 网页关掉，但浏览器还挂着 keep-alive 连接 | 连接在、不推帧 → 速率 0 → `idle` | 正确 |
| 代理在推帧但走的是 IPv6 | 不计入 → 误判成 `idle` | 本项目场景不会发生 |

**所以第 ② 组实验建议拖动窗口 / 播放视频制造画面变化**，
让发送速率明显高于阈值，这样分组才干净。

另一个更硬的替代办法：直接看**发送速率的绝对值**，而不是二分类。
脚本输出的「代理发送均值/峰值 MB/s」本身就是连续量，
「达到 4.8MB/s 的多不多」比「watching 占几成」更有信息量。

## 4. 输出怎么读

### 4.1 汇总表列义

```
角色    PID  会话  端口  CPU中位%  CPU均值%  CPU峰值%  寿命均CPU%  工作集MB  句柄均值
代理   12345    3   18081   41.20     43.55     78.10       40.12    182.4       912
```

| 列 | 含义 | 怎么用 |
|---|---|---|
| `CPU中位%` | 逐采样点差分的中位数 | **主判据**。中位比均值抗突发 |
| `CPU均值%` | 平均值 | 与中位差距大 = 有突发 |
| `CPU峰值%` | 最大值 | 看瞬时尖峰 |
| `寿命均CPU%` | 累计 CPU ÷ 存活时长 | **交叉验证**。与中位差 3× 以上要警惕 |
| `句柄均值/峰值` | `GetProcessHandleCount` | >15 分钟窗口才可定性 |
| `发送/接收MB/s` | TCP 载荷速率 | 验证带宽结论 |
| `连接数均` | ESTABLISHED 连接数 | 判断有没有人在连 |

### 4.2 三个必须记住的口径

1. **CPU% 是「单核百分比」**，100 = 吃满 1 个逻辑核，可 >100。
   **÷逻辑核数**才是「占整机」（本机 32 核，16% 单核 ≈ 整机 0.5%）。
   文档里所有「X% 单核」都是这个口径。
2. **分母是 Stopwatch 实测间隔**，不是标称 `-IntervalMs`。
   `Start-Sleep -Milliseconds 1000` 实际会睡 1010~1020ms，
   用标称值会把 CPU% 系统性算低 1~3%。
3. **发送/接收是 TCP 载荷**，不含 IP/TCP 头（每帧 HTTP 头数百字节，可忽略）。

### 4.3 「数据可信度自检」段

每次运行都会打印这一段，**先看它再看数字**：

| 输出 | 含义 | 动作 |
|---|---|---|
| `Refresh 自检：通过` | 脚本先自己忙等 ~120ms，确认 CPU 计数如实增长 | 说明差分机制是好的 |
| `Refresh 自检：✗ 失败` + 退出码 4 | 本机计数器异常，继续测只会得到假数据 | 换机器/重启后再测 |
| `超过物理上限` 报警 | CPU% > 核数×100，物理上不可能 | 该采样点作废，延长重跑 |
| `交叉验证：一致` | 瞬时均值 ≈ 寿命平均 | 可以采信 |
| `交叉验证：偏差 3×+`（黄色） | 窗口内正忙 / 进程刚启动 | 延长 `-Seconds` 重测 |

★ **差分为 0 不是错误。** 真的空闲的进程，CPU 累计时间就是不长。
脚本只在「差分为 0」**但**「寿命平均显示它明显在干活」时才提示可疑，
不会把正常空闲误报成假数据。

## 5. 自测记录（可复现）

### 5.1 底层机制验证（本次开发中实测，不是估算）

**① 句柄数 + 进程外读取**

```
PSVersion : 7.6.9      Cores : 32     Add-Type : OK
OpenProcess(LIMITED, self) : True
GetProcessHandleCount(self) : 556
```
对 `services / wininit / System / explorer / csrss` 都能用 `PROCESS_QUERY_LIMITED_INFORMATION`
读到句柄数与 IO 计数（读不到时返回 -1，脚本按「不可用」处理，不编造）。

**② socket 字节不在 IO 计数器里**（决定用 TCP eStats 的那次对照）

```
SOCKET: drained=12844800 bytes
SOCKET: child WriteTransfer=1334  OtherTransfer=576002  WriteOps=4  OtherOps=3052
```

**③ TCP eStats 的字节数与真实收发逐字节吻合**

```
发送端发 8,388,608 字节 → 接收端实收 8,388,608
eStats: pid=184804 rodSize=96 OK DataBytesOut=8388648 DataBytesIn=0
```
`rodSize` 是扫出来的（8→200 每次 +4，第一个成功的是 96），
不是抄来的常量；读数与真实字节吻合才反过来证明这个尺寸是对的。

**④ 跨进程 + 速率差分**

```
before: v4[out=0        in=0 conns=1 fail=0]
after : v4[out=6553640  in=0 conns=1 fail=0]     ← 实际 drained 6,553,600
```
`GetExtendedTcpTable` 的「先问需要多大」那次调用返回 **122（ERROR_INSUFFICIENT_BUFFER）**，
这是正常返回值而不是错误 —— 一开始就是在这里写错了判断，导致整个网络功能静默失效。

### 5.4 已知答案验证：网络速率 1.0 MB/s

构造一个「每 100ms 发 100KB」的发送端（理论 **1.0 MB/s**），用持续消费的接收端接住：

```
发送端 pid=131364，理论 1.0 MB/s（每 100ms 发 100KB）
实际被消费的字节: 7680000 → 7.32 MB
  [  6/6]   代理 1 个·发送合计 0.94 MB/s ← 有人观看
  代理发送合计       : 0.895 MB/s   （折算 3.15 GB/小时）
状态     采样点 约合秒 主程序CPU% 代理均值CPU% 代理发送MB/s 发送峰值MB/s
有人观看      6   6.00                    8.56         0.90         0.94
```

实测 **0.895 MB/s** vs 理论 1.0 MB/s（差 10%，来自建连前的空档 + 采样边界），
并且 `← 有人观看` 自动置位 → **状态判据也是好的**。

> ★ 这里踩到一个真实坑：第一次验证只读了一次就停，接收端不消费 →
> TCP 背压把发送端卡住 → 量到 0.027 MB/s。
> **测带宽必须保证接收端在持续消费**，否则量的是背压不是带宽。
> 在真实场景里浏览器就是那个消费者，所以正常采样没问题。

### 5.5 开发中发现并修掉的三个真 bug

自测不只是「跑一遍不报错」，下面三个只有真跑才会暴露：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 脚本崩 `Argument types do not match` | PowerShell 7.6.9 上对泛型 `List[object]` 施加 `@()` 会抛异常 | 改 `$Rows.ToArray()` |
| 2 | 「占整机 **306.854%**」 | CPU% 已经是百分数，换算整机又乘了 100 | 改成 `CPU% ÷ 逻辑核数` |
| 3 | 空闲进程被标红「Refresh 失效」 | 把「差分为 0」当故障 | 差分为 0 只在「寿命平均显示在干活」时才算可疑 |

顺带加了 **Refresh 自检**（先自己忙等 120ms 证明计数会涨），
把「机制本身是否可信」变成开跑前的硬门禁 —— 失败就退出码 4，不给假数据。

## 6. ★ 怎么用这个脚本验证或推翻那三个数

### 6.1 「30fps / 质量75 ≈ 4.8 MB/s」

**出处**：`HANDOFF-3.3.19` §4.1、`STREAM-PERF-AUDIT` §2.2 / §5.2。

**怎么测**：

```powershell
# 1) 确认 config 是 30fps / 质量75（脚本会自己打印出来，只读）
# 2) 打开网页实时画面，拖动窗口让画面持续变化（否则会因「静止降频」掉到 1fps）
pwsh -File scripts\measure-soullink-perf.ps1 -Seconds 60 -Label 30fps-有人看 -Csv out\watching.csv
```

看汇总里的 **`状态对比 → 有人观看 → 代理发送MB/s`**，以及脚本直接给出的 `比值 = 实测 / 4.8`。

| 实测（单代理发送均值） | 结论 |
|---|---|
| **2.9 ~ 6.7 MB/s**（0.6~1.4×） | **成立**，交接文档这个数可以继续引用 |
| **1.7 ~ 2.9 MB/s**（0.35~0.6×） | 偏低。先排除：画面是否静止（静止降频到 1fps 会让它掉一个数量级）、浏览器是否真的在取帧 |
| **> 6.7 MB/s** | 偏高。分辨率或画质高于基线（1080p/75 是基线）。**该结论要按实测修订，不能再用 4.8** |
| **< 1.7 MB/s** | 先怀疑「根本没在推帧」，其次才是编码参数 |

**关键提醒**：脚本也会打印当前 `RecordFps / RecordQuality`。
如果配置不是 30/75，它会**明确拒绝**直接对照（只给一个按帧率线性折算的粗估），
因为「5fps 下的 MB/s」和「30fps 下的 MB/s」不是一回事。

### 6.2 「录制中代理 ≈ 0.3~0.7 核/账号」

**出处**：`STREAM-PERF-AUDIT` §2.2 / §2.3 / §4.3 / §5.2。

**怎么测**：默认跑法就够（代理在录制中时采集循环恒跑，与有没有人看无关）：

```powershell
pwsh -File scripts\measure-soullink-perf.ps1 -Seconds 180 -Csv out\agents.csv
```

看**每个代理的 `CPU中位%`**（口径：100 = 1 核）。

| 实测（每代理中位） | 结论 |
|---|---|
| **30 ~ 70%** | **成立**，0.3~0.7 核/账号是准的 |
| **< 30%** | 偏低。**先确认该账号在不在 `RecordAccountIds` 里**（脚本会打印）—— 没开录制当然不烧。开着录制仍这么低 → 采集比估算便宜，把结论往下修，`STREAM-PERF-AUDIT` 里「脏矩形收益」的绝对量也要同比下调 |
| **> 70%** | 偏高。说明 GDI+ 软编确实是大头，**脏矩形 / 降帧的收益比文档估的更大**，优先级应上调 |

**这条结论最重要的用法**：
分别在「有人看」和「没人看」两种状态下量同一个代理。
如果两次的 `CPU中位%` **差不多**（差距 < 20%），就**证实**了
`STREAM-PERF-AUDIT` §2.1 的核心论断：

> 采集侧不看有没有人观看 —— `SessionRecorder.Loop()` 是 `while(!_stopRequested)` 死循环，
> `IsLiveActive()` 定义了却没人消费。

如果「没人看」时明显更低，那这个论断就**被推翻**了，
说明有某种我没读出来的降频机制在起作用 —— 那就该回去重新读代码。

### 6.3 「空闲挂机态 ≈ 16% 单核」

**出处**：`PERF-3.3.4` §0（三次采样 14.1% / 17.5% / 15.9%）、`HANDOFF-3.3.19` §1.5。
注意这条**本来是实测值**，但那是 **3.3.4 基线**，而 3.3.19 自称修掉了几处开销
（`Kick()` 移出 UI 线程、日志增量追加、`Discover` TTL 1s→3s），
**所以现在应该比 16% 更低 —— 本次实测正是验证「修复有没有效」**。

**怎么测**（必须干净的空闲态）：

```powershell
# 1) 关闭所有网页标签（消除浏览器侧干扰）
# 2) 主程序保持挂机，不要操作它，让它稳定跑满 10 分钟以上（避开启动爬坡）
pwsh -File scripts\measure-soullink-perf.ps1 -Seconds 300 -Label idle -Csv out\idle.csv
```

看 **主程序的 `CPU中位%`**：

| 实测（主程序中位） | 结论 |
|---|---|
| **11 ~ 21%**（±30%） | 与基线一致，16% 成立 |
| **< 11%** | **修复有效** —— 说明 §1.5 那批改动真的把开销压下去了。**以本次实测为准修订基线**，并把这个数写回文档（这是好消息） |
| **> 21%** | 比基线高。先排除外来因素：`dist\stable\` 的挂机测试版是否也在同机运行、是否有页面在跑动画/日志满速滚动、`-Seconds 180` 复测是否稳定复现 |

**必须做交叉验证**：脚本会同时打印主程序的 `寿命均CPU%`。
如果中位和寿命平均差 3× 以上，说明进程刚启动（启动开销把平均值拉高了），
**这次的空闲基线不作数**，要么等 10 分钟，要么用 `-Seconds 1000` 长采样。

### 6.4 顺带能验证的第四、第五件事

| 结论 | 怎么验证 |
|---|---|
| 8 个账号全录的**总** CPU | 看汇总的「所有代理合计」—— 每个代理的中位之和，直接对上 §2.2「3 个账号全录 ≈ 2~3 核常驻」 |
| 句柄有没有泄漏 | `-Seconds 1000` 跑 15+ 分钟，看 `句柄峰值 - 句柄均值` 是否单调上升（`AGENTS.md` 要求 >15 分钟才能定性） |
| 工作集是否异常 | 代理 `工作集MB` 应远小于「7.9MB 位图 × 帧数」—— 因为 `Ring` 只存压缩后的 JPEG（§1.2 第 ⑧ 跳） |

## 7. 如果量出来和估算差很多，说明什么

这一节是给「拿到数字之后」用的。**差得多不等于测错了，也不等于代码坏了** —— 先按下面顺序排除。

### 7.1 先排除「测法问题」（占九成）

| 症状 | 最可能的原因 |
|---|---|
| 发送速率极低（<0.5 MB/s） | 画面静止 → 前端「静止降频」已降到 1fps。**制造画面变化再测** |
| 发送速率是 0 | 网页没在取帧 / 浏览器标签被隐藏（`document.hidden` 会停拉）/ 走的是 IPv6（不计入） |
| CPU 全是 0 | 目标进程真的空闲（如采样时它在等 I/O）。看 `寿命均CPU%` 是否有量 |
| CPU 高得离谱（>核数×100） | 采样点重合 —— 但脚本已用 Refresh 自检 + 上限检查拦住，真出现就退出码 4 |
| 两次跑差一倍 | 采样窗口太短 / 期间有投送、连接、GC 突发。**加长到 180s 并取中位数** |
| 句柄数一直涨 | 短窗口内的启动爬坡。**必须 >15 分钟**才能定性 |

### 7.2 再考虑「文档的估算错了」

如果**测法确认无误**、**多次复现一致**，而数字和文档差得远，那结论是：

| 情况 | 说明什么 |
|---|---|
| 实测 CPU **明显低于** 0.3~0.7 核 | 「JPEG 软编是大头」这个估算偏悲观。收益排序要重算：脏矩形的绝对收益变小，可能不如先做「采集/观看解耦」 |
| 实测 CPU **明显高于** 0.7 核 | 估算偏乐观 → **脏矩形 + 降帧的优先级应上调**，因为省得比文档说的更多 |
| 实测带宽 **远低于** 4.8MB/s | 「吃满一个核」的主因可能不在带宽，而在**每帧全图解码**（浏览器侧）。那么 `createImageBitmap` / 帧差 的收益比 WebP 更大 |
| 实测带宽 **远高于** 4.8MB/s | 用户「太卡」的根因更可能是带宽/编码，`STREAM-PERF-AUDIT` 里「P0 降帧」的收益应上调 |
| 空闲 **低于** 16% | **这是好消息**：3.3.19 的性能修复有效。把基线往下修订，并把「16%」从文档里退役 |
| 空闲 **高于** 16% 且稳定复现 | 有回归。要么 3.3.19 的修复没生效，要么另有新增周期任务（对照 `AGENTS.md` 性能约束第 1 条：**新增周期任务必须走 `TickHub`**） |

### 7.3 一条元规则

> **一个数字只有在「两次独立运行 + 交叉验证吻合」之后才配写进文档。**
>
> 这正是交接文档 §6.4 那次 279% 假数据事故的教训：
> 当时的数字看起来完全合理（279% 不像 0% 那么刺眼），
> 只有拿「总 CPU ÷ 存活时长」一对，才暴露出它是假的。
> 本脚本把这条交叉验证做成了**每次必打印**，就是想让它无法被忽略。

## 8. 安全性：为什么可以放心在挂机时跑

脚本头部有完整声明，这里再列一次它**只**做了什么：

| 允许 | 为什么安全 |
|---|---|
| `Get-Process` + `Refresh()` | 只读操作系统计数器 |
| `GetProcessHandleCount` / `GetProcessIoCounters` | 最小只读权限（`0x1000`）打开，读完立刻关闭 |
| `GetExtendedTcpTable` / `GetPerTcpConnectionEStats` | 读内核连接统计表，不产生任何收发包 |
| 只读打开 `config.json` | `ConvertFrom-Json` 解析后显示，绝不写回 |

它**明确不做**：

- 不写任何配置/注册表、不结束/暂停/重启任何进程、不启停服务
- 不碰 `dist/`（`-Csv` 指向 `dist\` 会被直接拒绝并报错退出）
- **不调用 `SetPerTcpConnectionEStats`** —— 那会改网络栈状态，属写操作。
  所以它也只能读数，不能「打开统计开关」（这也是 IPv6 拿不到数的原因之一）
- 不注入、不挂钩、不 attach 调试器、不读目标进程内存

对正在挂机的账号的唯一影响：每 `IntervalMs` 毫秒读一次计数器，
单次微秒级、无锁、不打断目标进程。**挂机时可以放心跑。**

## 10. 已知限制（如实列出）

| 限制 | 影响 | 规避 |
|---|---|---|
| IPv6 连接不计速率 | 走 IPv6 时发送量被低估为 0 | 本项目是 IPv4，不受影响；若将来改 IPv6，此处必须重做 |
| 只能看 ESTABLISHED | 已关闭连接的历史流量不可回溯 | 必须在流量发生时采样 |
| 状态判据是「发送速率」的代理指标 | 画面长期静止时会把 `watching` 误判为 `idle` | 测时制造画面变化；或直接看速率绝对值 |
| 跨会话读命令行可能被拒 | 代理/主程序分类可能标成「未确认」 | 脚本会显式标注，不假装知道 |
| 句柄数需 >15 分钟才可定性 | 60 秒默认值只能看「当前值」 | 用 `-Seconds 1000` 看趋势 |
| 依赖 .NET/PowerShell 原生声明 | 声明失败则跳过句柄与网络两项 | 会明确标注「不可用」，不编造数字 |
