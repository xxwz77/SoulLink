## 0. 一句话结论

**在真正跑游戏的 A1 会话（session 18）里，以 A1 本人身份实测：WGC `CreateForWindow` 成功抓到"原神"游戏窗口，帧到达 31.7 fps、帧间隔稳定 ~31ms、125/127 帧画面内容各不相同——WGC 忠实捕获了游戏的真实渲染帧率。这个 ~31ms 帧间隔正好对应原神的 30fps 锁帧，不是 WGC 的瓶颈。BitBlt 基线 34.67ms 则连 30fps 都吃力。结论：WGC 在 RDP+动态游戏场景成立，帧率上限由游戏自身锁帧决定（30fps 游戏就给 30fps，60fps 游戏就给 60fps）；当前唯一障碍仍是显存不足导致硬设备回退 WARP。**

## 3. 关键结论

### 结论 1：WGC 抓到的是游戏的真实渲染帧率，不是抓屏瓶颈

- `CreateForWindow` 帧间隔 **avg=31.01ms、p95=33.37ms、max=34.49ms** —— 这个数字极其稳定地落在 **30fps 锁帧**区间（33.3ms/帧）。
- **125/127 帧内容哈希互不相同** —— 画面确实在实时更新，不是"重复推同一帧"。
- 这直接证明：**WGC 的帧到达率 = 游戏自身的渲染率**。游戏锁 30fps → WGC 给 30fps；游戏跑 60fps → WGC 给 60fps（本地控制台动态画面已实测 58.1~58.5fps，见 `WGC-VERIFY`）。

### 结论 2：CreateForWindow 优于 CreateForMonitor（本场景）

- 抓游戏窗口 31.7fps vs 抓整个显示器 12.0fps —— 差 2.6 倍。
- 原因：RDP 会话的显示器合成是"变化驱动"的，桌面大部分静止；游戏窗口是持续渲染的。**抓窗口能精确锁定高帧率来源，抓显示器则被桌面静止区域稀释。**

### 结论 3：显存仍是唯一硬约束

- 探测启动时显存 8038/8188（剩 150MiB），硬设备 `E_OUTOFMEMORY` 回退 WARP。
- 即便如此，WARP 软件光栅下 WGC 仍达到 31.7fps（游戏锁帧上限），说明 WGC 抓帧本身对设备要求不高；但 WARP 的 CPU 开销远高于 GPU，8 账号并发时会是负担。
- 结束探测后显存回落到 6547/8188（GPU 利用率 38%），说明显存占用随游戏负载波动，不是恒定饱和。

### 结论 4：BitBlt 34.67ms 连 30fps 都吃力

- BitBlt avg=34.67ms、max=134.22ms（有抖动尖峰），30fps 需要 <33.3ms，已经临界；60fps 的 16.67ms 完全无望。
- 这再次坐实：**之前"60fps 不成立"的根因就是 BitBlt，WGC 才是对的路。**

## 4. 最终判定：RDP + 动态游戏的帧率

| 问题 | 答案 |
|---|---|
| WGC 在 RDP 会话能抓游戏窗口吗？ | ✅ 能（A1 身份实测抓到"原神"窗口） |
| 抓到的是实时画面吗？ | ✅ 是（125/127 帧内容不同） |
| 帧率到多少？ | **31.7fps = 游戏自身锁的 30fps**（不是 WGC 上限） |
| 60fps 游戏能到 60fps 吗？ | ✅ 理论成立（本地动态画面 WGC 已实测 58fps；游戏锁 60 就给 60） |
| 全屏独占影响？ | 游戏窗口 1920x1080 全屏渲染，WGC 正常捕获，未见独占排他问题 |
| 当前唯一障碍 | 显存不足 → 硬设备回退 WARP（腾显存即可解锁 GPU 路径） |

| 优先级 | 动作 |

| P0 | 腾显存（降游戏画质/分辨率，或上大显存卡），让 D3D11 硬设备可建 |
