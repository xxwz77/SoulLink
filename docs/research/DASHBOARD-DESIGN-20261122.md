# 主页 / 控制面板信息架构设计 + myorg 模块取舍

> 日期：2026-11-22
> 作者：dashboard（agent-team）
> 前置：`MOBILE-REMOTE-PLAN-20261122.md`（手机远程）、`WEB-EXTENSION-PLAN-20261122.md`（网页 BGI 数据/流程）、`WEB-DIRECT-3.3.5-20261122.md`（直连代理）、`PERF-3.3.4-20261122.md`（性能基线）
> 范围：只读分析 + 设计判断。**未改业务代码、未动 dist/、未提交 git**。
> 用户诉求：① 网页主页还没做完，手机主页也差不多；② 状态监控为主、看画面选择性打开、不默认抓缩略图；③ 按钮不能太多（手机操作）；④ 问过"CPU/内存显示会吃性能吗"。
> 补充硬要求（v1.1 增补）：⑤ 每个号独立隔开，总览与账号区视觉分离；⑥ 界面一定要好看（纯 CSS 变量、两套主题、不引框架）；⑦ 0 收益/报错路线要一眼看出来（健康度三态 + 报警入口）；⑧ 远程画面是独立页面，一个按钮整页跳转进入，退出/后退要能显式停帧。

## 0. 一句话结论

1. **主页的本质是"账号状态总览 + 异常一眼可见 + 一键跳转远程画面"**，不是 myorg 那种"功能入口大杂烩"。myorg 的问题恰恰是用户点名的：**主界面入口太多、显示的信息又少**。SoulLink 反着做——**信息密度拉满、入口收到最少**。主页与远程画面是**两个独立页面**（hash 路由 `#/` 与 `#/remote/:id`），不是同页面板。

2. **SoulLink 已经拿到主页所需的绝大部分数据**：`AccountStateCenter`（会话/BGI 进程/当前配置组/停止时刻/报错计数/今日收益）+ `BgiLogCenter`（当前任务/路线/进度/ETA/拾取）+ `BgiStatusParser`（结构化状态）+ `ScriptGroupTracker`（配置组运行记录）+ `DailyStatsCache`（狗粮经验/摩拉）。**`WebServer.ApiSessions()` 已经把其中 80% 序列化给网页了**，主页缺的不是后端数据，是**前端的信息排布 + 一个"按需看画面"的交互**。

3. **myorg 的 56 个模块里，值得抄进 SoulLink 的只有"运行状态监控 + 配置组运行情况 + 今日收益 + 快捷键 + 定时任务"这一小撮**；剩下的大量"米游社/游戏内"模块（祈愿、背包、摩拉札记、角色养成、料理、矿产看板、钓鱼）SoulLink **根本没有数据源**（它只读 BGI 日志，不读米游社、不读游戏内数据），硬抄 = 维护一个拿不到数据的空壳。

4. **CPU/内存显示：可以做，但必须"按需点击才查"，绝不能周期采集**。`Process.HandleCount` 每次 3~5ms、挂 1Hz 循环自吃 20% CPU（AGENTS.md 的教训）；正确做法是用户点"详情"才 `GetProcessHandleCount` + `WorkingSet64`（后者已在 `SessionSlimmer` 用过，零点零几毫秒级）。全局概览根本不需要进程级数据。

## 1. 模块取舍表（myorg 56 路由 → SoulLink 该不该抄）

### 1.0 判定口径（先声明，避免拍脑袋）

| 分类 | 定义 |
|---|---|
| **该集成** | 真正解决"多账号挂机监控"的痛点，**且 SoulLink 已有对应数据源**（去代码里能指到字段） |
| **该集成·优先级低** | 有用，但数据源缺一半 / 需先过安全门槛 / 形态重叠需先收敛 |
| **不该集成** | 华而不实、数据拿不到、维护成本高于价值，三者占其一 |

数据源核实列，全部来自本文第 4 节的代码索引；"✅"= 数据已存在，"⚠️"= 部分存在/需新建，"❌"= 完全没有。

### 1.1 该集成（真正有用 + 数据拿得到）

| myorg 模块 | 解决什么问题 | SoulLink 数据源（核实） | 判断 |
|---|---|---|---|
| **运行状态监控**（Home 内嵌） | 一眼看到每个账号：在线/在跑/跑到哪/有没有报错 | ✅ `AccountStateCenter.AccountState`（SessionId/BgiRunning/CurrentGroup/StoppedAt/ErrorCount）+ `BgiStatus`（TaskName/RouteFile/RouteProgress/CurrentAction） | **核心，直接做**。这是用户要的"状态监控为主" |
| **配置组运行情况**（ListGroups 的"从未启动/运行中/已结束/失败"） | 今天每个配置组跑了没、成没成 | ✅ `ScriptGroupTracker.ScriptGroupRun`（Never/Running/Finished/Failed/Cancelled/Interrupted + 起止时间 + 失败原因） | **做**。主页账号卡片可折叠展开"今日配置组" |
| **今日收益 / 狗粮收益**（AutoArtifactsPro 的收益总览） | 挂机的成果：经验/摩拉/拾取件数/狗粮路线数 | ✅ `DailyStats`（DogfoodExp/DogfoodMora/PickTotal/DogfoodRoutes）+ `BgiStatus.RoutePicks`（当前配置组拾取） | **做**，但只做"狗粮经验/摩拉/拾取件数"三项，不做折线图 |
| **日志查询**（AutoLog 的"搜索/时间段/错误数"） | 出问题能查到原文 | ✅ `BgiLogCenter` 尾窗（800 行/200k 字符，`BgiLogLine`） | **做**，按需（点账号→日志），不实时跟随（WEB-EXTENSION-PLAN §2.1 已定口径） |
| **快捷键一览**（HotKey 的快捷键配置） | 让手机也能"发一次快捷键" | ✅ `BgiDataCenter.DisplayHotkeys`（已从 config.json 解析出"停止当前脚本/自动拾取/截图"等中文名+按键） | **做**。手机端把它做成"停止当前脚本"一个动作的底层通道 |
| **一键操作**（Home 里的重启/发送截图/注销用户） | 手机远程救急 | ✅ 会话操作 `ProcessService.KillAsync`/注销 `WtsSessionQuery` + 直连代理 `/api/input` 发快捷键截图 | **做**，见 §2.3 按钮清单。但"重启/注销"是控制面，须过安全门槛（§3） |
| **定时任务 / 调度**（TaskCron + 调度圣坛） | 定时启动配置组/一条龙 | ✅ `ScheduleRunner` + `TickHub` + `AutomationFlow`（流程里已有 TrigInterval 定时条件） | **复用已有流程**，不另抄 myorg 的 Cron UI。网页编辑见 WEB-EXTENSION-PLAN（安全前置） |

### 1.2 该集成·优先级低

| myorg 模块 | 解决什么问题 | SoulLink 数据源 | 判断 |
|---|---|---|---|
| **一条龙启动/停止**（HotKey 的"启动停止一条龙" + BgiConfig 流程图） | 手机上触发一条龙 | ⚠️ 控制链 `BgiTaskPreparer`/`FlowRunner` 存在，但**网页暴露写接口必须过 WEB-EXTENSION-PLAN §6 安全门槛**（编辑默认关闭） | **低优先**，且只做"启动/停止"两个动作，不抄 BgiConfig 的自动拾取名单编辑 |
| **宏录制**（MacroRecorder） | 录一段键鼠操作回放 | ⚠️ `NativeInput`/`RawMouseInput`/`InputTrace` 有底层，但"录制-回放"是全新功能，跨会话回放可靠性未验证 | 低优先；挂机场景用 BGI 脚本，宏是补充 |
| **脚本队列 / 凯瑟琳工坊**（ScriptManagement，本机 BAT/VBS/EXE 队列） | 把本机程序排成队列 | ⚠️ `ActionService`/`FlowRunner` 有"启动程序/结束进程"动作，但队列语义是新增 | 低优先；形态与 FlowRunner 重叠，先收敛再决定 |
| **仓库 / 脚本分发**（Repository + Gitlog） | 订阅远端脚本装到本机 | ❌ SoulLink 无订阅/授权码体系，这是 myorg 生态特有 | 低优先；只在自己做脚本分发时再抄 |
| **日志关键词编排**（LogKeywordAutomation） | 日志出现关键词→触发动作 | ⚠️ `PlcLogMatcher` + `FlowGraphRules` 的日志条件已有，但"编排"UI 是流程编辑的一部分 | 并入流程编辑（WEB-EXTENSION-PLAN），不单独做 |
| **归档查询**（Archive） | 跨天看历史运行 | ⚠️ BGI 日志按天滚动、SoulLink 不持久化历史，需新建归档存储 | 低优先；先想清楚"要存档什么"再建，别为归档而归档 |

### 1.3 不该集成（华而不实 / 数据拿不到 / 维护成本高）

| myorg 模块 | 为什么不该抄 |
|---|---|
| **祈愿记录 GachaLog** | ❌ 米游社 API。SoulLink 不读米游社，无数据源 |
| **背包统计 / 我的背包**（BagStatistics + MyBag） | ❌ 米游社背包同步。同上 |
| **摩拉收益札记**（Morale，旅行札记） | ❌ 米游社旅行札记。注意区分：SoulLink 的"今日摩拉"是**狗粮日志**里报的，与米游社旅行札记是两码事，别混 |
| **角色养成计划**（CharacterPlan + MysTool 词条） | ❌ 米游社角色面板/圣遗物数据 |
| **料理进度**（CookingProgress） | ❌ 游戏内库存数据，拿不到 |
| **采集管理/路线冲突**（CollectionManagement） | ❌ 虽然路线文件在磁盘可读，但"材料冲突筛选/AI 分析"依赖游戏内容语义，价值低、维护高 |
| **矿产看板**（AbundantOre） | ❌ BGI 脚本私有输出格式，SoulLink 日志里没有对应锚点 |
| **钓鱼/锄地一条龙**（AutoFishingTeyvat / AutoHoeingOneDragon / ZzzOneDragon） | ❌ 游戏内脚本，SoulLink 只**监控**脚本执行、不**实现**游戏脚本；要跑让用户跑 BGI |
| **任务计算器**（CalculateTaskEnabledList，体力预算） | ❌ 游戏内容，与"多账号挂机监控"无关 |
| **回血复活统计**（RedBloodStats） | ❌ 极细的游戏内统计，SoulLink 日志读不到对应锚点，且价值边际 |
| **材料趋势**（MaterialTrend） | ❌ 依赖背包统计（米游社），根上就拿不到 |
| **周报**（StoredReport） | ❌ 华而不实；用户要的是"现在怎么样"，不是"上周总结" |
| **AI 聊天 / AI 技能**（AiChat + Skills） | ❌ LLM 集成，SoulLink 无；维护成本（模型路由/密钥/提示词）远高于价值，且与"监控"无关 |
| **MAA 挂机**（Maa） | ❌ 另一款挂机框架（明日方舟），与 Genshin BGI 无关 |
| **CD 自动采集 / 一条龙计划 / 地图追踪**（CDAwareAutoGather / OneLongPlan / Pathing） | ❌ 游戏内脚本配置；SoulLink 要的是"用户跑哪个组"的状态，不是"帮用户配采集" |
| **米游社账户/签到/工具**（MysAccounts / MysSignIn） | ❌ 需要用户把 CK/SK 交给程序，安全风险高、与挂机监控无关 |
| **自动拾取名单 / BGI 配置编辑**（BgiConfig） | ❌ 直接改 BGI 的 config.json，与 SoulLink 的"只读监控"定位冲突（SoulLink 读 config.json 是为了显示快捷键，不是为了改它） |

**小结**：myorg 是"单机 Genshin 脚本全家桶"，SoulLink 是"多账号 RDP 挂机监控"。前者 56 个模块里 80% 是**游戏内容/米游社数据**，SoulLink 一项都拿不到；真正该抄的只有**运维监控那一小撮**——而这些 SoulLink 已经实现了一大半，剩下的是**把数据排进主页 + 加一个按需看画面的入口**。

## 2. 主页信息架构（核心交付物）

### 2.0 设计原则（对应用户原话）

| 用户原话 | 设计回应 |
|---|---|
| "主界面入口做的太杂了，显示的信息又少" | 反着来：**入口收到最少（一个账号卡片只有一个主操作），信息密度拉满（卡片上直接显示状态/进度/报错/收益）** |
| "状态监控为主" | 全局概览横条 + 账号卡片，全是状态字段，零图表、零缩略图墙 |
| "看画面选择性打开" | 画面**永远不默认加载**；点卡片"▶ 进入远程"→ **整页跳转**到独立远程页，才拉 `/live`（§2.5） |
| "通过按钮打开某些功能" | 按钮按使用频率排，手机上每个账号只给 2~3 个 |
| "不要默认抓缩略图（开销大）" | 主页列表**不发起任何 `/live` 请求**；缩略图墙明确砍掉 |
| "每个号独立隔开，不要混在一起" | 总览区与账号区**视觉分离**；每个账号一张独立卡片，边界清晰（间距+边框，不靠颜色细微差异）；手机端同逻辑（总览在上、卡片纵向堆叠，不改成表格式） |
| "界面一定要做的好看" | 见 §2.6 视觉规范：卡片层级、字号、留白、状态色语义全部定死，两套主题通用，纯 CSS 变量实现（**不引入框架/UI 库**） |
| "0 收益 / 报错的路线要一眼看出来" | 见 §2.7 健康度 + 报警入口：卡片上直接给"X 组失败 / Y 组 0 收益"数字，点进去就是列表；健康度用"正常/异常/严重"三态，不让人自己算 |

**要点**：
- **总览区与账号区是两块独立区块**：总览是单独一个带边框的大卡片（`--card` 渐变 + `--border` 1px），账号区是另一段纵向列表。二者**靠"区块边界 + 24px 间距 + 各自圆角边框"分离**，不是同一张表里混排。
- **每个账号一张独立卡片**：卡片之间 16px 间距 + 各自 1px 边框 + 左缘 4px 状态色条（`border-left`），扫一眼就能定位"这是哪个号"。账号名用 15px 加粗、状态/进度用 12.5px 次级文字，层级清晰。
- 卡片**不渲染任何 `<img>`/`<video>`**，不存在"默认抓缩略图"。
- 点卡片展开"今日配置组 + 报错日志尾窗"（数据已在快照里，展开只是渲染，不发起新请求，或最多一次 `GET .../stats/today`）。
- **健康度三态（🟢正常/🟡异常/🔴严重）直接印在卡片第一行**，判定规则见 §2.7，用户不用自己算。

**手机端要点**：
- **总览区单卡片置顶**，下面账号卡片**纵向堆叠**，一屏 2~3 张，绝不挤成两列表格。

- 左缘状态条在手机上尤其重要——竖屏扫过时，**不用读字、只看左缘颜色条就能知道哪些号红了**。

### 2.2 账号卡片字段（按重要性排序，手机/网页同构）

> 排序依据：**"先看有没有出事，再看做得怎么样"**。掉线/报错/停止是必须一秒看见的红灯，进度/收益是绿灯细节。

| 优先级 | 字段 | 数据来源（核实） | 展示形态 | 说明 |
|---|---|---|---|---|
| **1** | 在线状态 | `AccountState.SessionId>0 && relay.IsConnected`（`ApiSessions` 已给 `online`） | 状态色点 ●绿/○灰/✕红 | 最高优先。离线=一切免谈 |
| **2** | BGI/脚本在跑 | `AccountState.BgiRunning` + `CurrentGroup.Length>0`（`GroupRunning`） | 胶囊 `[在跑]`/`[已停止]`/`[无BGI]` | "在跑"≠"有会话"，两者分开显示 |
| **3** | 跑到哪一步 | `BgiStatus`：`RoundDisplay`（第 X/Y 轮·角色）+ `RouteDisplay`（路线[进度]）+ `CurrentAction`（当前动作） | 卡片第二行（可能两行截断） | 这是 myorg 主页缺的"SoulLink 该给的信息密度" |
| **4** | 报错 | `ErrorCount/FailCount` + `BgiStatus.ProblemText`（配置组失败/异常/任务结束） | 红字 `⚠ 错误2·失败1` | 红灯。有失败直接顶到卡片醒目位 |
| **5** | 停止时刻 | `StoppedAt` + `LastGroup` | `14:32 停止 · 最后:XXX` | 区分"跑完了"和"跑挂了"（用户明确要求停止后不残留运行状态） |
| **6** | 今日收益 | `DailyStats.DogfoodExp/DogfoodMora` + `PickTotal` | 灰字 `今日 63000经验·19986摩拉·拾取270` | 挂机成果，绿字不抢戏 |
| **7** | 日志空闲时长 | `bgiLogIdleMinutes`（`ApiSessions` 已给） | 仅在"在跑但 >N 分钟无日志"时黄字提示 | 抓"在跑但卡死"的隐性故障 |
| **8** | 一条龙/配置组名 | `OneDragon` / `ConfigGroup` | 折叠区 | 上下文信息，不占首屏 |

**明确不放进卡片**：缩略图、CPU/内存、复杂图表、抽卡/背包等游戏内容。

### 2.3 快捷操作按钮清单（按使用频率排序，手机每账号 ≤3 个）

| 频率 | 按钮 | 动作 | 数据/通道（核实） | 说明 |
|---|---|---|---|---|
| ★ 最高 | **▶ 进入远程** | 整页跳转该账号远程模式（独立页面） | hash 路由 `#/remote/<id>`，进入才 `startLive()` 拉 `/live?token=…`（`directPort` 已下发） | 唯一的主操作。整页跳转，不是展开面板（§2.5） |
| ★★ 高 | **停止当前脚本** | 发停止快捷键 | `BgiDataCenter.CancelTaskHotkey`（已解析出按键）→ `/api/input` key 动作 | 出错了最想按的 |
| ★★ 高 | **发送截图** | 拉一帧当前画面存图/发到手机 | `GetLatestJpeg()` 单帧 | 比看视频省流量，先确认"是不是卡死" |
| ★★★ 中 | **重启 BGI** | 结束+重启该账号 BGI | `ProcessService.KillAsync` + 启动链（控制面） | myorg 也有"重启"，但要走安全门槛 |
| ★★★ 中 | **启动一条龙** | 触发一条龙/配置组 | `BgiTaskPreparer`/`FlowRunner`（控制面） | 低优先，先做只读监控 |
| ★ 低频 | 注销会话 | 注销该 Windows 会话 | `WtsSessionQuery` | 只在详情页，不占卡片 |

**手机端布局**：卡片主区域 = 状态信息；右下角一个 **"▶ 进入远程"**（整页跳转）；长按卡片或点 `⋯` 弹 **"停止脚本 / 发截图 / 重启"** 三个。**绝不把 6 个按钮平铺在卡片上**——用户明说"按钮不能太多"。

### 2.4 全局概览显示什么

顶部横条只放 **4 个只读计数**（数据全在 `AccountStateCenter.All()` / `ApiSessions()` 返回列表里，前端 reduce 一下，零后端新增）：

| 计数 | 定义（核实） | 触发 |
|---|---|---|

### 2.5 远程模式 = 独立页面（页面流转 + 拉画面生命周期）

> 用户硬要求：「要做独立页面才行，一个按钮进入远程模式」。**主页与远程画面是两个独立页面**，不是主页里的面板/抽屉/弹层。

#### 2.5.1 页面流转（主页 → 远程模式 → 返回）

```
┌─────────────────────┐        点账号卡片「▶ 进入远程」        ┌──────────────────────────┐
│     主页（状态总览）  │ ─────────────────────────────────────► │   远程模式（独立页/视图）   │
│  总览区 + 账号卡片区  │       整页切换，不是展开面板            │  全屏画面 = 绝对主体       │
│                     │                                        │  控件 = 可收起浮动层       │
│   不拉任何 /live     │  ◄─────────────────────────────────────│  进入即 startLive 拉帧    │
└─────────────────────┘    「← 返回主页」/ 浏览器后退 / Esc       └──────────────────────────┘
                                   退出 = 显式 stopLive，立即停帧
```

**远程模式页面结构**：
- **画面是绝对主体**：`<video>`/`<img>` 占满整个可视区（`position:fixed; inset:0`），没有侧栏挤占。
- **控件收进可收起浮动层**：顶栏一个透明工具条（返回 / 画质 / 冻结 / 发送按键），默认半透明悬浮在画面上，点一下才展开；不操作几秒自动淡出。
- **手机端尤其关键**：画面占满整屏，虚拟修饰键/触控板/软键盘都**浮在画面上**（`MOBILE-REMOTE-PLAN §4` 的手势层），不占固定侧栏。退出按钮常驻左上角（拇指可及的返回）。

#### 2.5.2 拉画面生命周期（技术要点，必须显式，不能靠页面隐藏兜底）

| 时机 | 动作 | 落点 |
|---|---|---|
| **进入远程页** | `startLive()` 开始拉帧 | 只在这一刻才发起 `GET /live`（`directBase(sess)` + `?token=`） |
| **退出/返回主页** | `stopLive()` **显式**停帧 | `frameGen++`（作废在途请求）+ `clearTimeout(liveHandle)`；现有 `stopLive()`（`web-index.html` L710-714）已具备此语义 |
| **浏览器后退** | `popstate` 监听里 `stopLive()` | 现有单文件**无 popstate 监听**（grep 无匹配），本次必须补：后退离开远程页时显式停帧 |
| **手机切后台** | `visibilitychange → hidden` → `stopLive()` | 画面不在前台就没必要拉帧 |
| **手机回前台** | **建议：不自动恢复，回到远程页顶部提示"画面已暂停，点击恢复"** | 理由见下 |
| **切账号 / 掉线** | `stopLive()` + `frameGen++`，丢弃过期在途请求 | 防止串画面（`web-index.html` L712 注释已点名） |

**手机回前台"是否自动恢复"的建议：不自动恢复，手动一键恢复。** 理由：
1. 切后台可能已经过了很久，BGI 画面早已变化/账号已掉线，**盲目续拉的第一帧会闪旧画面**，体验差且浪费一次请求；
2. 自动恢复在"手机频繁锁屏/切 App"时会反复建立/断开拉流，与"按需不空转"的性能红线冲突；
3. 手动恢复 = 用户明确表达"我还在看"，语义清晰，实现也只需一个可见的"▶ 继续"悬浮按钮，不引入 `online` 事件的复杂状态机。

> 唯一例外：桌面浏览器在**同页内**切账号标签（若未来保留"远程页内换号"），换号本身是显式动作，允许 `startLive()` 直接续拉新号，但旧号的在途请求必须先 `frameGen++` 作废。

#### 2.5.3 与单文件 `web-index.html` 的关系（HANDOFF §5 约束下的实现）

现状已是**单文件 + `?view=` 独立窗口**双模式（`web-index.html` L1162-1208 `bootViewerMode` + L651 `window.open('?view=…')`），不是从零做路由。在此约束下，独立页面的实现：

| 方案 | 做法 | 结论 |
|---|---|---|
| **hash 路由（推荐）** | `#/` = 主页，`#/remote/<accountId>` = 远程模式；`hashchange` 驱动视图切换 + `stopLive()` | ✅ **首选**。不刷新整页、不拆文件、天然可前进后退（popstate/hashchange 都有事件）、状态（账号 Id）在 URL 里可刷新可分享，仍是一个 HTML 文件 |
| 多文件 | 拆 `index.html` + `remote.html` | ❌ 破坏"单文件同步链"（`sync-webpages.ps1` 现在同步单文件），且共享 JS/CSS 要再抽公共文件，收益不抵成本 |
| 现状 `?view=` + `window.open` | 保持"新窗口独立画面" | ⚠️ 可保留作"桌面多开看多个号"的辅助，但**手机 App（WebView 单窗口）无法依赖 `window.open`**，所以远程模式必须有一份 hash 路由实现，`?view=` 只是它的别名 |

**结论**：在单文件里用 **hash 路由**实现"主页 ↔ 远程模式"两个视图（`#/` 与 `#/remote/:id`），`?view=` 作为桌面新窗口的兼容入口。**不引入框架、不拆文件、不引 UI 库**——就是一段 `location.hash` 的读写 + `hashchange`/`popstate` 里各调一次 `stopLive()`。这同时满足第 4 条要求的"浏览器后退也能正确停帧"。

**实现要点（照做即可）**：
1. `router()` 读 `location.hash`，`#/remote/<id>` 渲染远程视图并 `startLive()`，其余渲染主页视图。
2. `window.addEventListener('hashchange', router)` 与 `popstate` 都触发同一个 `router()`；`router()` 每次先判断"当前是否在远程视图"，不在就 `stopLive()`。
3. 主页视图**永不调用** `startLive()`；远程视图**卸载（离开）必调** `stopLive()`。
4. `visibilitychange → hidden` 补一次 `stopLive()`（手机切后台停帧）。
5. 远程页退出按钮 = `location.hash = '#/'`，走 hashchange 自然回到主页 + 停帧。

**明确砍掉**：**实时缩略图墙**（N 个账号并发 `/live` = 带宽/CPU 灾难，用户已点名"开销大"）；**主页内嵌画面面板/抽屉/弹层**（用户第 4 条明确拒绝）。

### 2.6 视觉规范（"好看"怎么落地，纯 CSS 变量，两套主题通用）

> 约束：**不引入任何前端框架/UI 库**（现有单文件 `web-index.html`）。现有配色已是 CSS 变量 + `data-theme="dark|light"`（`web-index.html` L23-66），本规范**全部复用/少量新增变量**，不换配色体系。

#### 2.6.1 状态色语义（四类，语义唯一、不靠颜色细微差异区分）

| 语义 | 含义 | 变量（复用现有） | 暗色值 | 亮色值 | 用于 |
|---|---|---|---|---|---|
| 🟢 **正常/在线** | 会话在线、脚本在跑、无报错 | `--mint`（+ `--mint-bg`/`--mint-border`） | `#41f0c0` | `#008869` | 状态点绿、`[在跑]` 胶囊、左缘绿条 |
| 🟡 **异常/告警** | 停止/空闲/0收益/仅告警（可恢复） | **新增 `--amber`**（+ `--amber-bg`/`--amber-border`） | `#ffb84d` | `#b26a00` | `[已停止]` 胶囊、0收益组、黄字提示 |
| 🔴 **严重/报错** | 离线/失败/ERR/Fail | `--rose`（+ `--rose-bg`/`--rose-border`） | `#ff6b8b` | `#c02753` | 状态点红、报错红字、左缘红条、离线 |
| 🔵 **信息/主色** | 强调、可点、进度、主操作按钮 | `--accent`（+ `--accent-bg`/`--accent-border`） | `#4fe3ff` | `#0087a7` | 账号名高亮、进度数字、"▶ 进入远程"主按钮 |

> ★ 唯一需要新增的是 `--amber` 一组（黄/告警色）——现有调色板没有"黄色"这一档，而"停止/0收益"需要区别于红绿的中间态。只需在两套主题里各加 3 行变量，**仍是纯 CSS 变量，不引库**。其余全部复用现有 `--mint/--rose/--accent`。

**为什么四色够、不要更多**：状态语义收敛到"正常/异常/严重/信息"四类，正好对应 `mint/amber/rose/accent`。再多一档（比如"超严重"）用户就要靠颜色细微差异分辨，反而回到"不好看、分不清"的老路。

#### 2.6.2 卡片布局与层级（实现者照此做）

| 元素 | 规格 | 说明 |
|---|---|---|
| 总览区外层 | 圆角 `16px`、`1px` 边框 `--border`、内边距 `20px`、与账号区 `24px` 间距 | 总览是一个独立大卡片，视觉上硬隔离 |
| 账号卡片 | 圆角 `14px`、`1px` 边框 `--border`、卡片间距 `16px`、左缘 `4px` 状态色条 | 每号一张，边界清晰 |
| 账号名 | `15px` + `font-weight:600` | 第一视觉锚点 |
| 状态胶囊 | `11.5px`、`padding 3px 10px`、圆角 `999px`、`--X-bg` 底 + `--X` 字 | `[在跑]` 绿 / `[已停止]` 黄 / `[离线]` 红 |
| 进度行 | `12.5px`、`--txt2` | 卡片第二行，最多两行截断 |
| 报错/收益行 | `12px`，报错用 `--rose`、收益用 `--txt3` | 报错顶到醒目位、收益灰字不抢戏 |
| 健康度徽标 | 复用状态胶囊样式，放第一行右侧 | 🟢正常 / 🟡异常 / 🔴严重，判定见 §2.7 |

#### 2.6.3 留白与间距（两套主题通用，保证"呼吸感"）

- 页面左右内边距 `20px`（桌面）、`12px`（手机）。
- 卡片内边距 `16px`（上下）/`16px`（左右）；行间距 `8px`（卡片内部三行之间）。
- 数字用等宽/加粗（`font-variant-numeric: tabular-nums`），保证"4/6"这种对齐不跳。
- 状态色点 `10px` 直径圆点，与账号名 `8px` 间距。

> 一句话：**好看 = 层级（字号三档）+ 留白（间距统一 8 的倍数）+ 语义色（四色唯一）+ 圆角统一（14/16px）**，四样都靠 CSS 变量和几个类名实现，不堆功能。

### 2.7 健康度 + 报警入口（"0收益/报错一眼看出来"——用户最痛的痛点）

> 用户原话：「0 收益的路线、报错的路线不能快速分析出来，要在一个个配置组里面翻找」。解决：**在卡片上直接给报警数字，点进去就是列表**；健康度三态让人一眼判断，不自己算。

#### 2.7.1 健康度三态（卡片第一行右侧，判定规则）

| 健康度 | 判定（数据来源） | 卡片表现 |
|---|---|---|
| 🟢 **正常** | `errorLevel==0 且 无失败组 且 无0收益组` | 绿色徽标；左缘绿条 |
| 🟡 **异常** | `errorLevel==1`（仅告警）**或** 已停止**或** 存在 0 收益组 | 黄色徽标；左缘黄条 |
| 🔴 **严重** | 离线 **或** `errorLevel>=2`（有 ERR/Fail）**或** 存在失败组 | 红色徽标；左缘红条；卡片置顶到"异常列表"最上 |

**数据从哪来**（当前与未来两条线，标注清楚）：

- **已存在**：`BgiStatus.ErrorLevel`（0/1/2/3，来自 `ErrorCount/WarnCount/FailCount`）+ `AccountState.GroupRunning/StoppedAt`（停止判定）+ `ScriptGroupTracker`（`Failed` 状态组）。
- **需要"配置组收益台账"补**（你已另派成员实现，JSONL 落盘 + 多日查询）：见 §2.7.3，这是"0 收益组"的唯一可靠来源。

#### 2.7.2 卡片上的报警入口（直接数字，点进去是列表）

卡片第三行放两个**可点击的报警数字**（0 时不显示，避免噪音）：

| 报警项 | 卡片显示 | 点击后 | 数据来源 |
|---|---|---|---|
| 失败组 | `🔴 失败 2` | 弹该账号"今日配置组列表"，失败项红字、排在顶部 | `ScriptGroupTracker`（`State==Failed`）+ 台账 `status` |
| 0 收益组 | `🟡 0收益 1` | 弹该账号"今日配置组列表"，0收益项黄字、排在顶部 | **配置组收益台账**（`earnings<=0 且 state==finished`） |

**要点**：
- 报警数字**就是入口**——点它直接进"今日配置组"列表，列表按"失败 > 0收益 > 正常"排序，异常项置顶，用户不用翻找。
- 列表项展示 `组名 / 状态(成功/失败/0收益) / 收益(经验+摩拉) / 耗时 / 失败原因`，字段来自 §2.7.3 台账。
- 全局概览区的"报错 X"计数应**包含**失败组数 + ERR 账号数，两者任一条命中即计入（见 §2.4 口径扩展）。

#### 2.7.3 "配置组收益台账"需要提供的字段与接口形态（给实现方预留）

> 台账是"0 收益组"判定的唯一可靠来源（`DailyStats` 只有账号级合计、没有"每组收益"，`ScriptGroupTracker` 只有状态没有收益数字）。台账按"账号 → 业务日 → 配置组"落盘 JSONL，主页只需读"今天"。

**每条记录必含字段**（JSON 一条一行，追加写）：

```json
{
  "accountId": "acc_a2",
  "day": "2026-11-22",
  "group": "联机锄地-混合精英",
  "state": "finished",            // finished | failed | cancelled | interrupted
  "expGained": 63000,             // 该组本次狗粮经验（0 = 0收益候选）
  "moraGained": 19986,
  "durationSec": 1982,            // 耗时秒
  "failReason": "",               // 失败原因原文，非 failed 为空
  "endedAt": "2026-11-22T14:32:00+08:00"
}
```

**接口形态（主页只读，主程序提供，不经过账号代理端口）**：

```
GET /api/bgi/accounts/{accountId}/groups?day=2026-11-22&include=alerts
```

响应（只回"今天 + 含报警"的摘要，不整表下发，避免大 payload）：

```json
{
  "ok": true,
  "accountId": "acc_a2",
  "day": "2026-11-22",
  "failedCount": 2,
  "zeroEarningsCount": 1,
  "groups": [                       // 只回异常组，正常组按需分页再取
    { "group": "联机锄地-混合精英", "state": "failed", "failReason": "识别失败", "durationSec": 1982, "endedAt": "..." },
    { "group": "每日采集-全采集", "state": "finished", "expGained": 0, "moraGained": 0, "durationSec": 120, "endedAt": "..." }
  ]
}
```

**"0 收益"判定口径（需实现方对齐）**：`state==finished` **且** `expGained==0 且 moraGained==0` 才算 0 收益组。注意：**采集类组天然可能收益为 0 但正常**（捡的是材料不是狗粮），所以 0 收益只对**狗粮类组**做红色/黄色报警，采集类组用"拾取件数"兜底判断——这个口径要在台账里带上 `groupKind`（`dogfood | gather | other`）字段，否则会把正常采集组误报成 0 收益。

> 结论：健康度/报警入口**不需要新的前端框架**，就是在卡片上加两个"失败 N / 0收益 N"的可点数字 + 一个三态徽标；数据侧需要"配置组收益台账"补上"每组收益"这一个缺口（当前 `ScriptGroupTracker` 有状态无收益、`DailyStats` 有收益无分组）。

## 3. CPU/内存显示要不要做（回应"会吃性能吗"）

### 3.1 采集这些数据的真实开销（AGENTS.md 教训）

| 采集方式 | 单次开销 | 出处 | 结论 |
|---|---|---|---|
| `Process.HandleCount` | **3~5ms** | AGENTS.md §性能约束 | ⚠️ 挂在 1Hz 循环里自己吃 20% CPU，**禁用** |
| `GetProcessHandleCount`（P/Invoke） | 微秒级 | AGENTS.md §性能约束 | ✅ 正确的句柄数采集方式 |
| 枚举全进程 `Process.GetProcesses()` | **23.7ms** | `BgiLogCenter.cs` L349 注释 | ⚠️ 只该在"必须"时做一次，不周期做 |
| `Process.GetProcessById(pid)` | **0.012ms** | `BgiLogCenter.cs` L350 注释 | ✅ 已知 PID 时判活的正确方式 |
| `Process.WorkingSet64` | 零点零几 ms 级 | `SessionSlimmer.cs` L286 已用 | ✅ 内存可用这个，但同样是"按需" |

### 3.2 结论

1. **全局概览不需要进程级数据**：在线/在跑/报错/收益全部来自 `AccountStateCenter` 快照（会话号、BgiRunning、CurrentGroup、ErrorCount、DailyStats），这些字段**已经随 1 秒快照在维护，主页读它们零额外开销**。

2. **要做，只做"按需单账号详情"**：在账号详情页放一个"系统占用"区块，**用户点它才查一次** `GetProcessHandleCount(pid)` + `WorkingSet64`（BGI 进程的 PID 已在 `AccountState.BgiPid`），查完显示、**不缓存、不周期刷新、不在后台循环**。这样每次点击开销 <1ms，对 CPU 零负担。

3. **绝不做**：① 周期性采集所有账号的 CPU/内存（那是把 `HandleCount` 的坑复刻一遍）；② 主界面卡片常驻 CPU/内存数字；③ 实时曲线图。

4. **真要"持续监控性能"的正确路径**：不是采集进程，而是**复用已有哨兵**——`BgiLogCenter.ResidentChars()`（数据中心常驻字符量，已在快照里）和 `AccountState.LogBytes`（日志文件长度）是现成的"资源哨兵"，够判断"是不是又吃内存了"，且零新增采集。

> 一句话回应用户："会吃性能吗？" —— **默认的做法（周期采集）会，所以不做；按需点击才查的做法不吃，可以做。**

## 4. 网页 vs 安卓 APP 分工（考虑手机操作手感）

| 能力 | 网页（桌面浏览器） | 安卓 APP（Capacitor 壳，复用 web-index.html） |
|---|---|---|
| **全局概览 + 账号列表** | ✅ 主战场：大屏信息密度高，表格/多列布局 | ✅ 竖屏卡片流：一次只看 1~2 个账号，左右滑切换 |
| **看画面（远程控制）** | ✅ 全屏画面 + 鼠标键盘 | ✅ **这才是 APP 的主战场**：触摸手势/软键盘/虚拟修饰键/触控板（MOBILE-REMOTE-PLAN §4 全套） |
| **一键操作（停止/重启/截图）** | ✅ 鼠标点 | ✅ 大按钮（拇指可达），每账号 ≤3 个 |
| **日志查看/搜索** | ✅ 大屏适合逐行读日志 | ⚠️ 手机只给"最近 N 行 + 报错行"，不做全文搜索（手感差） |
| **配置/流程编辑** | ✅ 流程画布/JSON 编辑（WEB-EXTENSION-PLAN） | ❌ 手机不做编辑，只读 |
| **掉线/报错推送** | ⚠️ 需浏览器开着才看得到 | ✅ **必须在 APP**：系统通知（掉线/报错/脚本停止），这是"监控为主"在手机上的核心价值 |

**分工原则**：**网页 = 看全量 + 配置 + 读日志；APP = 收告警 + 看一眼状态 + 远程救急**。手机上不要堆网页的功能全集，只保留"看见红灯 → 点进画面 → 按一个键"这条最短路径。

**为什么"推送"是 APP 独有、且最高价值**：用户在手机上打开 SoulLink 的频率远低于"手机弹一条'A3 脚本停止'"。这一条是 APP 相对网页不可替代的增量，应作为 APP 的 P0 特性，优先级高于"远程控制手感"。

## 5. 不要做的（诱人但该砍）

| 砍掉 | 理由 |
|---|---|
| **实时缩略图墙**（N 账号并发拉帧） | 用户点名"开销大"；带宽/CPU 灾难，与"选择性打开"直接冲突 |
| **复杂图表**（收益折线/趋势/饼图） | 用户要"现在怎么样"，不要"历史曲线"；图表需要历史存储（SoulLink 没有） |
| **AI 助手 / AI 聊天** | LLM 集成维护成本高、与监控无关、且拿不到 myorg 那套米游社/游戏内上下文 |
| **米游社全家桶**（祈愿/背包/摩拉札记/角色养成/签到） | SoulLink 不读米游社，根上无数据源；且让用户交 CK/SK 是新增安全风险 |
| **游戏内容模块**（料理/矿产/钓鱼/任务计算器/回血统计） | 拿不到数据，且 SoulLink 定位是"监控脚本"，不是"游戏脚本实现器" |
| **周报 / 材料趋势 / 采集冲突** | 华而不实 / 依赖砍掉的数据源 |
| **主页平铺一堆功能入口** | 这正是 myorg 被用户点名的缺点，别复刻 |
| **周期采集 CPU/内存** | `HandleCount` 教训，见 §3 |
| **主页默认自动刷新所有账号详情** | 只刷新概览计数（读快照）；账号详情展开才取，隐藏页零请求（WEB-EXTENSION-PLAN §2.1 口径） |

## 7. 给实现的一句话建议（非代码）

- **后端几乎不用动**：主页字段 80% 已在 `ApiSessions()`；缺的是 ① 概览计数（前端 reduce 即可）、② 今日收益 `DogfoodExp/Mora/PickTotal` 透出（快照里有，补进 JSON）、③ 账号详情的"今日配置组/报错日志"接口（WEB-EXTENSION-PLAN 的 `/stats/today`、`/logs?afterSeq` 已设计好）。
- **前端是主体**：把 `web-index.html` 用 **hash 路由**做成"主页 `#/`（状态总览）→ 远程模式 `#/remote/:id`"两个独立视图；主页不拉帧，远程模式进入才 `startLive()`、离开显式 `stopLive()`（§2.5）。账号详情（今日配置组/报错日志）是主页内的折叠区，按需取数。
- **APP 增量 = 推送 + 触摸远程**，其余复用同一份网页。
- **先做只读，后做控制**：停止/重启/启动一条龙这类"控制按钮"必须在安全门槛（令牌非空 + CORS 收窄 + 二次认证）之后才暴露，否则是把提权桌面的控制面交到公网。
