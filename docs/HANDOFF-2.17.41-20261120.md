## 1. 用户需求（原文）

> 「定时时刻里应该增加一个 **下次执行延时**，然后还要一个 **复位周期**，
>   多少天可用清空这个延时。
>   比如 4:00 4:01 4:02 4:03...多少天后重置为 4:00。**时刻需要精确到秒**」

## 2. 实现

### 2.1 新增参数

| 参数 | 含义 | 默认 |
|---|---|---|
| `time` | 基准时刻，**HH:mm:ss**（也兼容 HH:mm） | `04:00:00` |
| `stepSeconds` | **下次执行延时**：每触发一次，下次往后推这么多秒 | `0`（固定时刻） |
| `resetAfter` | **复位周期**：递增多少次后回到基准时刻 | `0`（永不复位） |
| `catchUpHours` | 补跑窗口（原有） | `12` |

### 2.2 计算方式

```
第 N 次触发时刻 = 基准时刻 + N × stepSeconds
N 达到 resetAfter 后归零 → 回到基准时刻
```

例（基准 04:00:00、步长 60 秒、复位 3 次）：

```
第1次 04:00:00
第2次 04:01:00
第3次 04:02:00
第4次 04:00:00   ← 复位
第5次 04:01:00
...
```

### 2.3 持久化（关键）

新增两个字段：

```csharp
public Dictionary<string,int>    ScheduleFireCount { get; set; }  // 已触发次数
public Dictionary<string,string> ScheduleCycleDay  { get; set; }  // 所属业务日
```

**为什么要持久化**：重启程序后不能把"已经递增到第几次"忘掉，
否则重启就跳回 04:00，延迟策略直接失效。

跨业务日（`DayBoundaryHour`）时自动清零，第二天重新从基准时刻开始。

### 2.4 严格的时刻解析（`TryParseClock`）

用户要求精确到秒，所以**不能用 `TimeSpan.TryParse`** —— 它会把 `"4"` 解析成 **4 天**，
是个实实在在的陷阱。改为严格按 `时:分[:秒]` 解析：

| 输入 | 结果 |
|---|---|
| `04:00:00` `4:00:00` `04:00` | 接受 |
| `23:59:59` `00:00:00` | 接受 |
| `24:00:00` `04:60:00` `04:00:60` | 拒绝（越界） |
| `"4"` | **拒绝**（旧写法会当 4 天） |
| `abc` `04:00:00:00` | 拒绝 |

### 2.5 编辑器运行进度提示

选中「定时·时刻」节点时，参数面板下方显示：

```
本轮第 2 次 · 本次时刻 04:01:00 · 递增 1/3 次，下次回到 04:00:00
```

或（未设延时）：`固定时刻 04:00:00（未设延时）`

否则用户设了延时和复位却看不到运行中的效果。

## 3. 验证（真实引擎，非纯推算）

### 3.1 时刻解析（11 组用例全部符合预期）

```
'04:00:00' → 接受 ✓    '4:00:00' → 接受 ✓    '04:00' → 接受 ✓
'23:59:59' → 接受 ✓    '00:00:00' → 接受 ✓
'24:00:00' → 拒绝 ✓    '04:60:00' → 拒绝 ✓   '04:00:60' → 拒绝 ✓
'4'        → 拒绝 ✓（旧 TimeSpan 会把它当 4 天）
'abc'      → 拒绝 ✓    '04:00:00:00' → 拒绝 ✓
```

### 3.2 递增 + 复位（步长 60 秒、复位 3 次，连跑 7 次）

```
第1次 fireCount=0 → 目标 04:00:00  引擎判定=触发 ✓
第2次 fireCount=1 → 目标 04:01:00  引擎判定=触发 ✓
第3次 fireCount=2 → 目标 04:02:00  引擎判定=触发 ✓
第4次 fireCount=3 → 复位 fc=0 → 04:00:00  触发 ✓
第5次 ... 04:01:00 ✓
第6次 ... 04:02:00 ✓
第7次 复位 → 04:00:00 ✓
```

### 3.3 边界

```
03:59:59（未到 04:00:00）→ 不触发 ✓
步长 0（固定时刻）→ 每次都触发，fireCount 保持 0 ✓
```
